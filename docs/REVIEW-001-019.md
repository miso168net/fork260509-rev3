## 方法

- **Workflow fan-out**：19 個 spec-compliance reviewer（pipeline、~10-16 並發）→ 每個 critical/high finding 派獨立 **對抗式 verifier**（預設懷疑、優先駁回）→ 主線綜合。

- **oracle 嚴格＝spec.md**（FR/SC/US/Edge/Assumptions/Clarifications）；`plan.md`/`data-model.md` 僅供定位 as-built code、**不作驗收標準**（避免 plan 自我循環）。
- **靜態審查**：讀碼 / grep / 讀既有測試檔評估覆蓋 / `git show`(唯讀)；**不執行 cargo / pnpm / CDP**（19 reviewer 並發會壞共用 rust target——刻意護欄）。需執行才能定的項標 **needs-runtime-verification**、不當缺陷。
- **supersession-awareness**：as-built 與 spec 不符時，查本 spec `## Clarifications`、`DECISIONS §1` 拍板表、`CHECKLIST §5` 拍板項索引、後續 feature spec `## Clarifications` 判定是否為合法後續演進。
- **執行註**：首輪 19 reviewer 中 3 個大 feature（007/008/017）因輸出過大致 StructuredOutput JSON 截斷失敗、1 個（016）回退化佔位答案，皆以精簡輸出 / fresh agent 補審通過。
