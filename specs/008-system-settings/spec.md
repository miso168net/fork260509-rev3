## User Scenarios & Testing *(mandatory)*

### User Story 1 - 超級管理員讀全站設定 (Priority: P1) 🎯 MVP

超級管理員要能在後台一覽全站的系統設定——每筆設定的鍵、目前值、值型別與用途說明——以便掌握系統目前的組態（例如全站「單一登入裝置」預設是開或關）。

**Why this priority**: 「能看到目前組態」是管理設定的最小前提；沒有讀就無從談改。它是本刀最小可交付核心，且可獨立先行。

**Independent Test**: 以超級管理員身分登入後呼叫「讀系統設定」→ 取得全部設定列（含 `single_session_default` 那筆，顯示鍵/值/型別/說明）；不依賴改、不依賴前端頁即可驗證。

**Acceptance Scenarios**:

1. **Given** 以超級管理員憑證，**When** 請求讀系統設定，**Then** 回傳全部設定列、每列含鍵/目前值/值型別/說明。
2. **Given** 系統目前種子只有一筆設定（`single_session_default`），**When** 讀取，**Then** 至少含該筆且其值為目前持久化的值。

---

### User Story 2 - 超級管理員改設定值且變更被完整審計 (Priority: P2)

超級管理員要能修改某一設定的值（例如把 `single_session_default` 由 `off` 切到 `on`），且**每一次變更都被完整且不可竄改地記錄**——是誰、何時、從哪個真實來源 IP、改了哪個鍵、改前改後的值——供日後問責與鑑識。

**Why this priority**: 「可改」是設定管理的核心動作；而設定屬敏感組態，變更**必須**留審計軌。建立在 US1（可讀）之上。

**Independent Test**: 以超級管理員改一筆設定 → 該設定的值被持久化更新；同時系統留下**恰一筆**對應的操作審計紀錄（操作者、真實來源 IP、關聯 id、變更前後值）；變更與其審計**同成同敗**（審計寫入若失敗，設定變更亦不留）。

**Acceptance Scenarios**:

1. **Given** 超級管理員與一個既有設定鍵，**When** 送出合法新值，**Then** 該設定值被更新，且留下恰一筆審計紀錄（操作者 id／操作者真實來源 IP／關聯 id／變更前值／變更後值）。
2. **Given** 變更處理進行中其審計紀錄寫入失敗，**When** 發生，**Then** 設定變更與審計紀錄**一起不留**（原子；不存在「改了卻沒被審計」的變更）。
3. **Given** 改一個**不存在**的設定鍵，**When** 送出，**Then** 明確失敗、回可讀錯誤，不靜默、不新增該鍵。

---

### User Story 3 - 僅超級管理員可存取（越權防護） (Priority: P2)

系統設定是敏感的全站組態，**只有超級管理員**能讀或改；任何其他身分——包括已登入的一般管理員或一般使用者——讀或改設定一律被拒絕（不洩漏設定內容）。

**Why this priority**: 設定誤改/外洩的風險高；這是本刀作為「全專案第一個受權限治理的業務端點」必須先立穩的防線（並建立日後所有受治理端點共用的授權樣式）。可獨立以對抗式測試驗收。

**Independent Test**: 以非超級管理員（已認證的一般管理員/使用者）讀或改設定 → 一律被拒（HTTP 403/權限不足）、且回應不含設定值；以未認證請求 → 被既有認證守門拒絕。

**Acceptance Scenarios**:

1. **Given** 已認證但**非**超級管理員，**When** 讀或改系統設定，**Then** 回 403 權限不足、回應不洩漏任何設定值。
2. **Given** 授權判定，**When** 進行，**Then** 依**系統當下**的角色判定（不採信憑證內嵌的角色宣告）——即便憑證內嵌過期/被竄改的角色，亦不影響判定。
3. **Given** 未帶/無效憑證，**When** 存取設定端點，**Then** 被既有認證守門拒絕（與既有受保護端點一致）。

---

### User Story 4 - 設定值型別驗證 (Priority: P3)

改設定時，新值必須符合該設定宣告的型別（例如 `single_session_default` 是 `on`/`off` 列舉）；不符的值被明確拒絕、回可讀且在地化的錯誤訊息，不被靜默接受或寫入髒值。

**Why this priority**: 防止無效組態進入系統的加值防護；非核心存取的必要條件，故 P3。

**Independent Test**: 對一個列舉型設定送出非列舉值（如對 `on/off` 設定送 `maybe`）→ 被拒、回在地化錯誤、設定值不變。

**Acceptance Scenarios**:

1. **Given** 一個列舉型設定，**When** 送出不在列舉內的值，**Then** 被拒、回可讀在地化錯誤、原值不變、無審計變更紀錄。
2. **Given** 送出合法列舉值，**When** 改，**Then** 成功更新並審計（同 US2）。

---

### Edge Cases

- **改不存在的設定鍵**：明確失敗、回可讀錯誤、不靜默、不新增鍵。
- **非法值型**：拒絕、回在地化錯誤、不寫入、無審計變更。
- **非超級管理員（已認證）讀/改**：403、不洩值。
- **未認證讀/改**：被既有認證守門拒絕。
- **審計寫入失敗**：設定變更與審計**一起回滾**（原子；非「盡力而為」——設定屬資料異動，異動與其審計同 txn）。
- **設定的熱套用**：本刀只**持久化＋審計**變更；變更**即時影響系統行為**（如 single-session 模式即時切換）**不在本刀**（後續波次接）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓超級管理員讀取全部系統設定列（每列：鍵、目前值、值型別、說明）。
- **FR-002**: 系統 MUST 讓超級管理員修改既有設定鍵的值。
- **FR-003**: 系統 MUST 對每次設定變更**原子地**連同寫入一筆不可竄改的審計紀錄（操作者 id／操作者真實來源 IP／關聯 id／變更前值／變更後值／時間）；變更與其審計同成同敗（不存在未被審計的設定變更）。
- **FR-004**: 系統 MUST 將讀與改系統設定限定為**超級管理員**；其他身分（含已認證之非超級管理員）MUST 被拒絕（HTTP 403），且回應 MUST NOT 洩漏設定值。
- **FR-005**: 授權判定 MUST 以**系統當下**的角色為準，MUST NOT 採信憑證內嵌的角色宣告。
- **FR-006**: 改設定時的新值 MUST 符合該設定宣告的值型別（如列舉 `on`/`off`）；不符 MUST 被拒、回可讀且在地化的錯誤、且 MUST NOT 寫入。
- **FR-007**: 改一個不存在的設定鍵 MUST 明確失敗、不靜默、不新增該鍵。
- **FR-008**: 系統 MUST 確保每個受保護的業務端點都實際掛上對應的授權檢查、且其授權策略在策略註冊齊備（無端點繞過授權／無漏設策略）；此守恆 MUST 由自動化檢查驗證。
- **FR-009**: 本功能 MUST NOT 變更任何既有資料結構（schema），MUST NOT 回歸既有登入／身分／權限守門／健康探針行為。
- **FR-010**: 設定變更的**即時行為套用**（hot-apply，如即時切換 single-session 模式）NOT in scope；本功能僅須正確**持久化並審計**變更（即時消費由後續波次接）。
- **FR-011**: 系統 MUST 提供超級管理員可用的後台「系統設定」管理介面（讀全站設定、改值），錯誤與成功訊息 MUST 在地化顯示。

### Key Entities *(資料層一覽；逐欄定義屬 plan 期 data-model)*

| 實體 | 角色 | 說明 |
|---|---|---|
| 系統設定 `system_settings` | 全站 KV 組態 | 鍵（唯一）／值／值型別／說明＋審計欄。已於既有基線建齊並種子（含 `single_session_default='off'`、型別 `enum:on,off`）。本刀只**讀**與**改值**，**不增刪鍵**。 |
| 設定變更審計 | 資料異動稽核 | 每次改值留一筆既有操作日誌紀錄：操作者／操作者來源 IP／關聯 id／變更前後值／時間。與變更同一不可分割交易。 |
| 系統設定管理頁 | 超級管理員後台介面 | 新增的後台頁面：列出全站設定、就型別提供合適編輯（如列舉用切換）、改值並顯示在地化結果。 |
| 端點授權守恆檢查 | 安全保證 | 自動化守恆：受保護端點 ↔ 授權檢查 ↔ 授權策略三者一致；防端點漏掛授權／漏設策略。 |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 超級管理員讀設定 100% 取得全部設定列；非超級管理員讀/改 100% 被拒（403）且回應不洩設定值——由活體＋瀏覽器驗證證實。
- **SC-002**: 超級管理員每次改設定 100% 同時留下恰一筆審計紀錄（操作者／真實來源 IP／關聯 id／變更前後值）；審計寫入失敗時設定變更亦 100% 不留（原子）——由活體驗證證實。
- **SC-003**: 非法設定值 100% 被拒、回在地化錯誤、且 100% 不寫入——由單元＋活體驗證證實。
- **SC-004**: 受保護端點授權守恆 100% 通過（無端點漏掛授權／無漏設策略）——由自動化守恆檢查證實。
- **SC-005**: 超級管理員可於後台設定頁讀取並修改設定、錯誤/成功訊息在地化顯示——由瀏覽器端到端驗證證實。
- **SC-006**: 既有登入／身分／權限守門／健康探針行為 100% 零回歸；本功能**零 schema 變更**——由活體驗證＋變更比對證實。
- **SC-007**: 讀設定 p95 < 300ms、改設定（含同交易審計）p95 < 500ms——對齊既有效能保守預設。

## Assumptions

- **授權以系統當下角色為準**（不信憑證內嵌角色）；本功能為**全專案第一個受權限治理的業務端點**，所建立的「認證守門＋授權檢查分層」樣式供後續所有受治理端點沿用。
- **設定的即時行為套用（hot-apply）延後**：`single_session_default` 等設定變更被本刀正確持久化＋審計，但「變更即時影響系統行為」（含其背後的即時失效通知機制）屬後續波次（行為島/session 機器）；本刀不引入該即時通知基礎設施。
- **多鍵的記憶體熱快取屬設計變更、延後**：目前只有單一熱鍵的設計；推廣為多鍵快取為日後設計變更、非本刀。
- **既有基礎已就緒、本刀套用不重建**：系統設定的資料結構與種子（含 `single_session_default`）、統一回應信封與業務錯誤碼/在地化鍵規約、資料異動的同交易審計機制、認證守門與授權策略 seam、稽核上下文（操作者/真實來源 IP/關聯 id）皆已由前序波次建妥；本刀**不改 schema、不重建這些機制**，只新增本功能的讀/改/前端與授權接線。
- **讀回形為扁平全列**：設定列數極少，讀端回扁平全部列（不分頁、不過濾）；分頁/過濾面首次由後續較重的清單型功能（如使用者管理）行使。
- **前端頁為新增**：既有後台無系統設定頁；新增一個依設定值型別呈現/編輯的後台頁（如列舉用切換），沿既有後台管理頁慣例與在地化機制。
- **值型別目前涵蓋列舉**（如 `on`/`off`）；其他型別（數值/字串/結構化）的驗證隨需要擴充。
- **本刀範圍邊界（OUT）**：設定即時套用（後續波次）／多鍵熱快取（設計變更）／增刪設定鍵（無此路徑）／分頁過濾（後續清單型功能首行）。
