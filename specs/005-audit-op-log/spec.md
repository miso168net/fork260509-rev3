## User Scenarios & Testing *(mandatory)*

### User Story 1 - 統一 mutation 原子審計機制 (Priority: P1) 🎯 MVP

每一次對資料的「變更（mutation）」都**自動、且與業務寫入綁在同一筆交易**記下一筆操作審計：變更成功則審計一起落地、變更失敗則審計一起消失——兩者**不可分割**。後續每個會「寫」的業務切片只要宣告自己這次變更的審計內容（操作別、目標、變更前後快照），即繼承此機制、無須各自重寫審計接線。

**Why this priority**: 這是整個「寫端審計面」的核心地基——之後每個會變更資料的業務切片（使用者／角色／選單／設定…）都站在「業務寫＋審計寫同一交易」之上。沒有它，每個切片各自手寫審計接線、且「業務寫成功但審計漏記」或「審計記了業務卻回滾」的不一致隨時可能發生。原子性是它的全部價值。

**Independent Test**: 對一個採用此機制的變更路徑，在交易內執行變更 → 同交易內可見一筆對應審計（操作別／目標／前後快照／操作者）；對同一路徑注入失敗 → 業務變更與審計**一起不留**。

**Acceptance Scenarios**:

1. **Given** 一筆會成功的變更，**When** 經此機制執行，**Then** 業務變更與一筆對應審計**在同一交易**落地（審計含操作別、目標表＋id、變更前後快照、操作者、追蹤碼）。
2. **Given** 變更過程中發生失敗，**When** 交易回滾，**Then** 業務變更與審計**雙雙不留**（不出現「業務改了但無審計」或「有審計但業務沒改」）。
3. **Given** 一個新的寫端業務切片，**When** 它要做變更，**Then** 只需宣告自己這次的審計內容、復用同一機制，**無須改動機制本體**。

---

### User Story 2 - 敏感欄遮蔽 (Priority: P2)

審計記錄的「變更前後快照」對敏感欄位（如密碼）**遮蔽**為固定佔位值，使審計軌跡可保留完整變更歷史、卻**永不外洩機密**。

**Why this priority**: 審計快照若原樣記錄敏感欄，等於把機密寫進一個刻意「不可竄改、長期保存」的日誌——審計面本身變成洩漏面。遮蔽必須隨機制一起 ship、且可證實際生效。

**Independent Test**: 對含敏感欄的實體取其審計快照 → 敏感欄為遮蔽佔位值（如 `"<redacted>"`）、其餘欄保留原值。

**Acceptance Scenarios**:

1. **Given** 一個含密碼欄的實體，**When** 產生其審計快照，**Then** 密碼欄值為 `"<redacted>"`、其餘欄原值保留。
2. **Given** 一筆軟刪變更的審計，**When** 檢視其前後快照，**Then** 兩份快照的密碼欄皆已遮蔽。

---

### User Story 3 - append-only 審計完整性 ＋ facade 唯一管道 (Priority: P3)

操作審計日誌為 **append-only**（只新增、無更新／刪除路徑），且其寫入**只能**經由既有的 facade 存取閘——延續前一刀「繞不過 facade」的守恆，使審計記錄不可被應用層竄改。

**Why this priority**: 審計的價值建立在「不可被竄改」之上。append-only ＋ facade 唯一管道讓「篡改審計」在程式層面就沒有入口。此為前瞻性完整性保證，隨機制一起就位、後續切片自始受其約束。

**Independent Test**: 檢視審計 sink 的對外能力——只有「新增」一種；對審計實體的存取僅出現於 facade 路徑（繞過 facade 的直接存取由既有 build-failing 守恆檢查擋下）。

**Acceptance Scenarios**:

1. **Given** 審計 sink，**When** 檢視其可呼叫能力，**Then** 只有 append（新增）、無 update／delete。
2. **Given** 機制本體（非 facade 層）程式碼，**When** 跑既有 facade 守恆檢查，**Then** 通過（機制本體不直接觸碰審計實體、不破守恆）。

---

### Edge Cases

- **no-op 變更**：目標不存在（如以不存在的 id 觸發變更）→ **不寫審計、亦不視為錯誤**（回傳「無目標」、交易正常結束、無副作用）。
- **操作者未知**：無／壞憑證情境下操作者可為 null（審計容忍 system／seed actor、不驗操作者存在）。
- **操作者來源網路位址**：本刀操作者的網路位址**尚無來源**（請求情境抽取屬後續刀）→ 此面以「不帶位址」記錄，由後續刀回填；型別一次對到最終型、不留轉換債。
- **機制中立性**：機制本體對「是哪張表的變更」中立——新增寫端不得迫使機制本體修改。
- **原子性偽證防護**：原子性 MUST 可證——驗證 MUST 同時涵蓋「成功落地」與「失敗回滾」兩路徑，不得只測成功路徑而淪為 vacuous。
- **活體驗證不污染**：活體驗證以交易回滾對既有種子資料進行、不持久變更（機制內部自行 commit，故驗證端須以交易隔離）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供**單一可重用的變更-審計機制**，使每次經其執行的變更，與一筆對應操作審計**寫入同一筆交易**——兩者同時 commit 或同時 rollback（原子、不可分割）。
- **FR-002**: 該機制 MUST **對實體中立／可重用**——新的寫端路徑只需宣告自己這次的審計內容（操作別、目標表＋id、變更前後快照），**無須修改機制本體**。
- **FR-003**: 審計的變更前後快照 MUST 對指定敏感欄（密碼）**遮蔽**為固定佔位值（`"<redacted>"`），其餘欄保留原值。
- **FR-004**: 操作審計日誌 MUST 為 **append-only**——無更新／刪除路徑；其寫入 MUST 只經由既有 facade 存取閘（繼承前一刀的 build-failing 守恆）。
- **FR-005**: 每筆審計 MUST 記錄：操作別（取自封閉詞彙集）、目標實體表名＋id、變更前快照、變更後快照、操作者（id ＋ 網路位址，皆可空）、追蹤碼（可空）。
- **FR-006**: no-op 變更（目標不存在）MUST **不**寫審計、且 MUST **不**視為錯誤。
- **FR-007**: 機制本體（非 facade 層）MUST **不**直接觸碰審計／業務實體型別——審計實體的構造與寫入只發生於 facade 層（守既有 facade 唯一管道）。
- **FR-008**: 本刀操作者身分 MUST 由呼叫端**顯式提供**（自請求情境自動抽取屬後續刀）。
- **FR-009**: 本刀 MUST **不**引入業務端點、HTTP 中介層、審計 overlay sink（存取／登入日誌）、執行期資料連線啟動接線、schema 變更／migration、或錯誤信封映射——各歸其後續刀。
- **FR-010**: 機制 MUST 由**單一代表性寫端路徑**（使用者軟刪）端到端演練為 proof；其餘寫端路徑由各自消費刀加入。

### Key Entities *(資料層一覽；逐欄定義屬 plan 期 data-model)*

| 實體 | 角色 | 說明 |
|---|---|---|
| 操作日誌 `sys_operation_log` | 審計 sink（archetype B append-only）| 每筆變更一列；含操作別／目標表＋id／前後快照／操作者 id＋ip／追蹤碼／建立時間。**實體已於前一刀（004）建齊、本刀不動 schema** |
| 審計事件內容（audit event）| 機制與 sink 間的審計資料載體 | 描述「一次被審計的變更」：操作別、目標、前後快照、操作者、追蹤碼。純資料、對實體中立 |
| 操作者（audit operator）| 審計事件的行為者 | 操作者 id（可空）＋網路位址（可空、本刀不帶、後續刀回填）|

（操作別為封閉詞彙集〔新增／更新／軟刪／還原〕；本刀僅用「軟刪」、其餘為前瞻保留、隨消費刀漸用。）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 經機制執行的變更，100% 在**同一交易**寫入恰一筆對應審計——由活體測試證實。
- **SC-002**: 變更失敗時，業務變更與審計**雙雙不持久**達 100%——由活體回滾測試證實（原子性非 vacuous）。
- **SC-003**: 審計快照的敏感欄（密碼）100% 遮蔽——由純單元測試在落地前證實。
- **SC-004**: 操作審計日誌對外能力只有 append、無 update／delete（append-only 成立）。
- **SC-005**: 範圍邊界守住——本刀新增業務端點數 ＝ 0、schema migration 數 ＝ 0、schema 變更 ＝ 0。
- **SC-006**: 機制對實體中立——新增一條寫端路徑**無須改動機制本體**（由單一 proof ＋設計審查證實）。
- **SC-007**: 既有 dev stack 零回歸——健康探針不受影響、新碼編入執行中服務（無端點／router 改動）。

## Assumptions

- **schema／實體已就緒**：審計 sink 表（`sys_operation_log`）與其實體反射已於前一刀（004）建齊（含 JSONB 快照欄、INET 操作者位址欄）→ 本刀**無** migration、不建表、不動 entity、不改依賴清單。
- **操作者位址型別**：機制以「最終型」記錄操作者網路位址，但本刀**不帶實值**（傳「不帶」）；真實位址由後續「請求情境／overlay」刀回填——一次對最終型、避免日後改型 retrofit 與型謊。
- **遮蔽清單**：本刀敏感欄遮蔽 ＝ 使用者實體的密碼欄；其餘實體的遮蔽由其消費刀於套用時宣告。
- **活體驗證**：以交易回滾對既有種子資料（使用者 Super／Admin／User）進行、不持久變更；機制內部自行 commit，故驗證端以交易隔離達成不污染。
- **無執行期資料連線接線**：本刀服務入口不變、不接執行期 DB 啟動接線；活體驗證自行連線。
- **facade 守恆繼承**：機制本體不直接觸碰實體型別、續守前一刀建立的 facade 唯一管道（build-failing 守恆）。
- **操作者來源延後**：自請求情境（bearer verify→操作者 id／追蹤碼）自動抽取屬後續「audit overlay／Auth 島」刀；本刀以顯式參數帶入。
- **支援平台 ＝ 既有 dev/prod 容器堆疊**；活體測試於容器內進行。
