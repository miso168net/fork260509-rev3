## Clarifications

### Session 2026-06-19

- Q: 批次刪除若同時選了一個父選單與它的子選單（或父選單仍有 active 子）行為要？ → A: 嚴格逐項驗證、整批拒——批次內任一選單仍有 active 子選單（即使該子同批被選）即整批拒、不部分執行；要刪子樹須先刪葉、分次進行（不在批次內做深度排序/cascade；最一致於「不可刪有子父」單筆規則）。
- Q: 前端 hasAuth 寫入鈕顯隱（D1 button gating）本刀範圍？ → A: 一併 retroactive gate 既有使用者管理（009）/系統設定（008）頁的寫入鈕（連同本刀選單頁）；以各頁按鈕權限碼已 seed 為前提——plan 須 grep 驗證，已 seed 之頁本刀 gate（零 migration 守恆）、任一所需按鈕碼未 seed 之頁須 surface 決定（補按鈕碼 seed＝minimal 例外 vs 該頁 gating 延後），不擅自破零-migration。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 登入後依角色呈現動態選單 (Priority: P1) 🎯 MVP

任何登入使用者進入後台後，左側選單**依其當下角色動態呈現**——只顯示該角色有權存取的選單項，無權項一律不顯示。可見性由**後端依系統當下角色判定**，前端不自行過濾。登入/找不到頁/無權頁這類「常數頁」與角色無關、恆在。

**Why this priority**: 「選單反映權限」是 DB 驅動選單的最小價值前提，並一次收掉波 1／波 2 在 static 模式下「非超級管理員仍看得到使用者/系統設定等管理選單」的破口（過去靠 API 層 403 擋、但選單仍可見）。此故事不依賴選單編輯即可獨立交付，是本刀最小可交付核心。

**Independent Test**: 以超級管理員、一般管理員、一般使用者分別登入 → 三者左側選單內容不同（超管最全、管理員為其子集、一般使用者最小）；無權角色看不到對應管理選單。不依賴新增/修改/刪除即可驗證。

**Acceptance Scenarios**:

1. **Given** 超級管理員，**When** 登入進入後台，**Then** 左側選單呈現其有權的全部選單項（含使用者/角色/選單/系統設定等管理項）。
2. **Given** 一般管理員，**When** 登入，**Then** 看得到被授予的選單（如使用者管理）、但**看不到**僅限超管的選單（角色管理/選單管理/系統設定）。
3. **Given** 一般使用者，**When** 登入，**Then** 只看到最小選單（如首頁/功能示例）、看不到任何管理選單。
4. **Given** 任一角色，**When** 進入應用，**Then** 常數頁（登入/404/403）恆可運作、不因角色或選單異動而改變。
5. **Given** 動態選單載入失敗（後端異常），**When** 使用者進入後台，**Then** 系統安全回退（導回登入而非白屏），不殘留半套狀態。

### User Story 2 - 超級管理員瀏覽選單樹（含已刪除統一清單） (Priority: P2)

超級管理員要能在選單管理頁以**樹狀**瀏覽全部選單；**已軟刪除與未刪除的選單同列於同一清單**、以「已刪除」狀態欄區分，讓使用者在同一處同時掌握選單結構與回收桶內容。

**Why this priority**: 管理選單的前提是看得到全貌（含可復原的已刪項）；建立在 US1 之上。統一清單避免在「現役」與「回收桶」兩個分離畫面間切換。

**Independent Test**: 以超級管理員開啟選單管理頁 → 樹狀列出現役與已刪除選單、已刪除項以狀態欄清楚標示並提供復原入口。

**Acceptance Scenarios**:

1. **Given** 超級管理員，**When** 開啟選單管理頁，**Then** 以父子層級樹狀列出全部選單，每列顯示名稱/類型/路由/狀態/**是否已刪除**。
2. **Given** 清單中含已軟刪除的選單，**When** 檢視，**Then** 該等項以「已刪除」標示、且提供「復原」操作；現役項提供「編輯/新增子項/刪除」操作。
3. **Given** US1 的側欄選單，**When** 比對，**Then** 側欄**永不**含已刪除選單（已刪除只出現在管理頁的統一清單）。

---

### User Story 3 - 超級管理員新增/修改選單（含搬移守門） (Priority: P2)

超級管理員要能新增選單、修改既有選單，包含**搬移父層（re-parent）**；選單的路由名在未刪除選單中必須唯一；搬移須通過守門：目標父選單必須**存在且啟用**、必須是**「目錄」型**、不可搬成**自身的後代**（防止成環）、**受保護的種子選單**其父層固定不可搬移。每次異動都被完整審計。

**Why this priority**: 編輯選單是管理核心動作；搬移守門防止樹結構被破壞（成環、孤兒、破壞系統種子結構）。

**Independent Test**: 新增一個選單 → 出現於樹；改名/合法搬移 → 生效；搬到非目錄/成環/受保護種子父 → 被拒、回在地化錯誤、不執行；以已存在的路由名新增 → 被拒。

**Acceptance Scenarios**:

1. **Given** 超級管理員與合法選單表單，**When** 新增，**Then** 建立選單、出現於樹、留下恰一筆審計。
2. **Given** 路由名與某現存（未刪除）選單重複，**When** 新增，**Then** 被拒、回可讀在地化錯誤、不建立、且**不以系統內部錯誤呈現**（含並發競態）。
3. **Given** 修改選單並搬移父層，**When** 目標父不存在/已刪/非目錄型/為自身後代/該選單受保護，**Then** **整筆被拒**、回對應在地化錯誤、不執行；合法搬移則生效並審計。
4. **Given** 修改不存在/已刪除的選單，**When** 送出，**Then** 明確失敗、不靜默。

---

### User Story 4 - 超級管理員刪除/復原選單（軟刪＋回收桶） (Priority: P2)

超級管理員要能**軟刪除**選單（單筆或批次，刪除後不再出現於側欄、移入統一清單的「已刪除」狀態）；但**受保護的種子選單不可刪**、**仍有啟用中子選單的父選單不可刪**（須先處理子選單）——違反一律**整筆拒絕、不部分執行**。已刪除選單可**復原**；若其父層已被刪除，則復原至**頂層**（由超管再自行搬移），不產生孤兒。每次刪除/復原都被審計。

**Why this priority**: 刪除是高風險動作、回收桶提供可復原語意；「有啟用子選單拒刪」保證現役選單樹永無孤兒（側欄/動態路由恆完整）。

**Independent Test**: 刪一個葉選單 → 入回收桶（已刪除狀態）、側欄不再現；刪「有啟用子選單的父」→ 被拒；刪「受保護種子選單」→ 被拒；復原已刪選單 → 回現役；復原父已刪的選單 → 置於頂層。

**Acceptance Scenarios**:

1. **Given** 超級管理員與一個葉選單（非受保護），**When** 軟刪除（單筆或批次），**Then** 該選單移入已刪除狀態、不再出現於側欄、留下審計。
2. **Given** 一個受保護種子選單、或一個仍有啟用子選單的父選單，**When** 刪除，**Then** **整筆**被拒、回在地化錯誤、**無任何**選單被刪。
3. **Given** 一個已刪除選單，**When** 復原，**Then** 回到現役（出現於側欄、受 US1 角色可見性規則約束）、留下審計。
4. **Given** 一個已刪除選單其父層也已被刪除，**When** 復原，**Then** 該選單被置於頂層（parent 清空）、不產生孤兒。

---

### User Story 5 - 依角色授權存取選單管理（越權防護） (Priority: P2)

選單管理是敏感操作：**新增/修改/刪除/復原/瀏覽管理清單限超級管理員**；**動態選單查詢限已登入者**且結果**依當下角色過濾**。任何不具權限者（含已登入的其他身分）一律被拒、不洩漏資料；授權一律依**系統當下**角色判定（不採信憑證內嵌的角色宣告）。

**Why this priority**: 沿用波 0-2 的「受治理端點」防線；選單結構/可見性誤改風險高，須以對抗式測試驗收。

**Independent Test**: 以一般管理員或一般使用者呼叫選單管理（新增/刪除/瀏覽管理清單）→ 被拒；以未認證請求 → 被既有認證守門拒；動態選單查詢以不同角色 → 回各自過濾後的選單。

**Acceptance Scenarios**:

1. **Given** 已認證但非超級管理員者，**When** 存取選單管理（瀏覽管理清單/新增/修改/刪除/復原），**Then** 回 403 權限不足、不洩漏選單資料。
2. **Given** 動態選單查詢，**When** 由不同角色發起，**Then** 各回該角色當下有權的選單集（依系統當下角色、非憑證內嵌宣告）。
3. **Given** 未帶/無效憑證，**When** 存取任一選單管理或動態選單查詢，**Then** 被既有認證守門拒絕。

---

### User Story 6 - 選單管理頁寫入鈕依權限顯隱 (Priority: P3)

選單管理頁的新增/修改/刪除等寫入鈕，依使用者的**按鈕層權限**顯隱（無該權限者不顯示該鈕）。授權仍由後端強制（前端顯隱僅為操作體驗、**非安全邊界**）。

**Why this priority**: 體驗層優化；後端授權（US5）已是安全邊界，故列 P3。一併收掉波 1／波 2（系統設定/使用者頁）同家族的前端按鈕顯隱待辦（在按鈕權限碼已就緒的範圍內）。

**Independent Test**: 以具/不具對應按鈕權限的身分開選單管理頁 → 寫入鈕顯/隱對應；無權者即便看到頁面也無寫入鈕（且即便繞過，後端仍 403）。

**Acceptance Scenarios**:

1. **Given** 具選單寫入權限的超級管理員，**When** 開選單管理頁，**Then** 顯示新增/修改/刪除鈕。
2. **Given** 不具該按鈕權限者，**When** 開該頁，**Then** 不顯示對應寫入鈕；後端授權仍獨立強制（US5）。

---

### Edge Cases

- **搬移守門**：目標父不存在/已刪除/非目錄型/為自身後代（成環）/受保護種子選單父固定 → 整筆拒、在地化錯誤、不執行。
- **刪除守門**：受保護種子選單、或仍有啟用子選單的父選單 → 整筆拒、不部分執行。
- **批次含父與其子**：批次逐項獨立驗證——批內父選單仍有 active 子（即使該子同批被選）即整批拒；不在批內做深度排序/cascade（刪子樹須先刪葉、分次）。
- **重複路由名**：新增時與現存（未刪除）選單路由名撞名（含並發競態）→ 被拒、回在地化錯誤、不建立、不得以系統內部錯誤呈現。
- **修改不存在/已刪除選單** → 明確失敗、不靜默。
- **復原孤兒**：復原父已刪的選單 → 置於頂層、不產生孤兒。
- **動態選單載入失敗** → 安全回退（導回登入、不白屏）。
- **常數頁**（登入/404/403）→ 與角色/選單異動無關、恆在。
- **動態模式切換回歸**：切換為動態後，既有使用者/系統設定管理頁對非超管於側欄隱藏（D1 兌現），但該等頁面本身行為不回歸。
- **非授權（已認證）讀/寫** → 403、不洩資料；**未認證** → 認證守門拒。
- **選單異動與審計不可分割** → 審計失敗時選單異動一起回滾（不存在未被審計的異動）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 在使用者登入後，依其**系統當下角色**提供動態選單，且 MUST 由後端過濾（前端零過濾）——無權角色 MUST NOT 取得對應選單；常數頁（登入/404/403）MUST 與角色無關恆在。
- **FR-002**: 動態選單查詢失敗時，系統 MUST 安全回退（不白屏、導回登入），MUST NOT 殘留半套路由狀態。
- **FR-003**: 超級管理員 MUST 能以樹狀瀏覽全部選單；**已刪除與未刪除 MUST 同列於統一清單並以「已刪除」狀態區分**；現役側欄/動態選單 MUST NOT 含已刪除選單。
- **FR-004**: 超級管理員 MUST 能新增選單；選單路由名在現存（未刪除）選單中 MUST 唯一，重複（含並發競態）MUST 被拒、回可讀在地化錯誤、不建立，且 MUST NOT 以系統內部錯誤呈現此業務衝突。
- **FR-005**: 超級管理員 MUST 能修改選單（含**搬移父層**）；搬移 MUST 通過守門——目標父須**存在且啟用**、須為**目錄型**、**不可為自身後代**（防環）、**受保護種子選單父層固定**；任一違反 MUST 整筆拒、回在地化錯誤、不執行；修改不存在/已刪除選單 MUST 明確失敗、不靜默。
- **FR-006**: 超級管理員 MUST 能單筆/批次**軟刪除**選單（刪後不現於側欄、移入已刪除狀態）；**受保護種子選單 MUST NOT 可刪**、**仍有啟用子選單的父選單 MUST NOT 可刪**——違反一律**整筆拒、不部分執行**。**批次語意**（Clarification 2026-06-19）：批次採**逐項獨立驗證**——批次內任一選單為受保護、或仍有 active 子選單（**即使該子選單同批被選**），整批拒、不部分執行；MUST NOT 在批次內做深度排序或 cascade；刪子樹須先刪葉、分次進行。
- **FR-007**: 超級管理員 MUST 能**復原**已刪除選單；若其父已刪除，MUST 復原至頂層（不產生孤兒）。
- **FR-008**: 每次選單新增/修改/刪除/復原 MUST **原子地**連同寫入一筆不可竄改的審計（操作者／真實來源 IP／關聯 id／時間／異動內容）；選單異動與其審計 MUST 同成同敗。
- **FR-009**: 系統 MUST 依角色授權——選單管理（瀏覽管理清單/新增/修改/刪除/復原）限超級管理員；動態選單查詢限已認證者且依當下角色過濾；非授權者（含已認證之其他身分）MUST 被拒（403）且回應 MUST NOT 洩漏選單資料；授權判定 MUST 依系統當下角色、MUST NOT 採信憑證內嵌角色宣告。
- **FR-010**: 後台選單管理頁的新增/修改/刪除/復原 MUST 實際對後端發出請求並反映結果（MUST NOT 僅顯示成功提示而未實際異動）；錯誤與成功訊息 MUST 在地化顯示。
- **FR-011**: 寫入鈕 MUST 依使用者按鈕層權限顯隱（無權不顯示）；**範圍涵蓋本刀選單管理頁＋既有使用者管理（009）/系統設定（008）頁的寫入鈕（retroactive，Clarification 2026-06-19）**，以各頁按鈕權限碼已就緒為前提（未就緒者依 Assumptions 之 surface 規則處理）；惟此顯隱為體驗層、授權 MUST 仍由後端獨立強制（FR-009）。
- **FR-012**: 本功能 MUST NOT 變更任何既有資料結構（schema）、MUST NOT 回歸既有登入／身分／權限守門／健康探針／使用者管理／系統設定／角色查詢行為；切換為動態選單模式 MUST NOT 破壞既有頁面本身運作。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 三種角色（超管/一般管理員/一般使用者）登入後的動態選單差異 100% 正確——超管最全、管理員為子集、一般最小、無權項不顯示——由活體＋瀏覽器驗證證實。
- **SC-002**: 動態選單查詢失敗時 100% 安全回退（導回登入、不白屏）——由瀏覽器驗證證實。
- **SC-003**: 超級管理員可於統一清單瀏覽全部選單（現役＋已刪除、狀態區分）100% 正確；側欄/動態選單 100% 不含已刪除——由活體＋瀏覽器驗證證實。
- **SC-004**: 選單新增/修改/刪除/復原全鏈 100% 實際對後端發出請求並反映結果（無「假成功」）、訊息在地化——由瀏覽器端到端驗證證實。
- **SC-005**: 搬移守門四情境（目標不存在/非目錄/成環/受保護父）100% 被擋；刪除守門（受保護/有啟用子）100% 被擋——由活體驗證證實。
- **SC-006**: 路由名重複 100% 被拒且不建立、且不以系統內部錯誤呈現——由活體驗證證實。
- **SC-007**: 復原 100% 生效（含父已刪→置頂層、無孤兒）——由活體驗證證實。
- **SC-008**: 非授權讀/寫 100% 被拒（403）且不洩選單資料；授權 100% 依系統當下角色判定——由活體＋瀏覽器驗證證實。
- **SC-009**: 每次選單異動 100% 連同恰一筆審計（操作者／真實來源 IP／關聯 id）原子寫入——由活體驗證證實。
- **SC-010**: 受保護端點授權守恆 100% 通過（含本刀新增選單端點、無漏掛授權/漏設策略）——由自動化守恆檢查證實。
- **SC-011**: 既有登入／身分／權限守門／健康探針／使用者管理／系統設定行為 100% 零回歸；本功能**零 schema 變更**；切換動態模式後既有頁面本身不回歸——由活體驗證＋變更比對證實。

## Assumptions

- **既有基礎已就緒、本刀零重建**：選單實體（含自我參照樹、受保護旗標、軟刪除＋審計欄）、選單種子（含 demo 全集與基線管理選單）、選單可見性授權策略、選單管理端點的授權策略、按鈕權限碼、統一回應信封與業務錯誤碼/在地化鍵規約、資料異動的同交易審計機制、認證守門＋授權檢查分層、稽核上下文（操作者/真實來源 IP/關聯 id）皆已由前序波次建妥；本刀**不改 schema、不重建這些機制**，只新增選單 CRUD 的讀/寫/動態路由/前端接線與授權接線（**零 migration**）。
- **scope 拍板＝一刀整包 Menu**：選單 CRUD＋統一回收桶＋動態路由＋動態模式切換＋前端 hasAuth gating 為單一 feature；實作階段仍拆多個獨立可審的執行單元。
- **Role×Menu 授權留 Role 刀**：「指派哪些角色看哪些選單」的角色側維護介面（menu-auth-modal）與相關端點屬後續 Role 刀；本刀的動態選單可見性靠既有的角色×選單可見性種子策略即可運作。
- **動態選單模式切換為高風險、排最後**：切換為動態後全應用路由依賴動態選單查詢；故先驗證動態查詢正確（含三角色）再切換，並倚賴既有的載入失敗安全回退。
- **常數頁前端寫死**：登入/404/403 與選單無關、不納入動態選單治理。
- **demo 選單可見性策略**：demo 全集初始僅授超級管理員，可見性由角色×選單授權層治理（隱藏機制不啟用）。
- **復原孤兒→頂層**：復原父已刪的選單時置於頂層、由超管再搬移（避免孤兒）。
- **新增選單的可選頁面來源於既有選單已用頁面集**：本刀不引入「登錄全新前端頁面」的能力（新頁面需另行前端開發＋種子）。
- **前端按鈕顯隱範圍（Q2 拍板＝retroactive 含 user/settings）**：本刀寫入鈕顯隱涵蓋選單頁＋既有使用者管理（009）/系統設定（008）頁；以各頁按鈕權限碼已 seed 為前提——plan 須 grep 驗證，已 seed 之頁本刀 gate（**零 migration 守恆**）；任一所需按鈕碼未 seed 之頁須 **surface** 給拍板（補按鈕碼 seed＝minimal 例外 vs 該頁 gating 延後），**不擅自破零-migration**。（註：系統設定頁為超管限定、動態模式下對非超管於選單即隱藏，其按鈕 gating 多為冗餘但無害。）
- **識別碼前後端一致呈現、不型別漂移**（沿既定識別碼序列化拍板：選單於路由語境與管理語境各依其介面契約呈現）。
- **前端為既有頁接線＋模式切換**（非新頁）：將既有選單管理頁由示意（mock）接上真實後端，並將選單來源由本地 static 切到動態。
- **本刀範圍邊界（OUT）**：Role×Menu 授權與角色首頁維護（Role 刀）／iframe 內嵌頁復原（現以外開連結呈現）／選單查詢/搜尋的進階優化／既有頁按鈕顯隱中按鈕碼未就緒者（延後）。
