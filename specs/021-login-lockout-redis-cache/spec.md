# Feature Specification: 登入鎖定快取層（login-lockout-redis-cache — 防鎖定機制在攻擊下放大成資源耗竭）

**Feature Branch**: `021-login-lockout-redis-cache`

**Created**: 2026-06-28

**Status**: Draft

**Input**: User description: 見 `docs/superpowers/021-login-lockout-redis-cache.md`（Phase 0 brainstorm spec-design）。源：Redis 使用全盤調查 → 發現 019-login-lockout 在分散式攻擊下的 DB 讀取/寫入放大風險 → user 親決「鎖定後把判定快取起來、原設計多加一層」。承接 019-login-lockout（被硬化的機制）；帳號-DoS／IP 信任白名單／CAPTCHA 為獨立 future feature（019 §4.2）、不在本刀。

## Clarifications

### Session 2026-06-28

- Q: 鎖定期間的節流鑑識摘要是否須含 distinct-source 來源廣度（需額外的 HLL 計數 primitive）？ → A: 否——必需「壓制次數」即足以滿足 SC-004 可觀測/告警；distinct-source 來源廣度為**可選/遞延**（YAGNI、未來鑑識增益），不列為硬需求、不需 HLL。
- Q: FR-011／SC-004 的「可告警」是否須本刀附帶具體告警規則？ → A: 否——本刀只**發出可被告警的結構化訊號**（必需、滿足 SC-004）；具體告警規則之配置**遞延給維運/obs**、不在本刀範圍。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 分散式登入攻擊下系統維持穩定（鎖定成本有界） (Priority: P1) 🎯 MVP

身為平台維運者／資安關係人，當有人以**分散式**手法（大量不同來源）對**同一個帳號**（如超級管理員）狂試登入時，登入鎖定機制本身**不得**因此把資料庫拖垮、進而拖垮整個系統。一旦某帳號或某來源已被判定鎖定，後續每一次嘗試的「評估成本」必須是**有上限的固定量**，與攻擊量無關——攻擊打 100 次或 100 萬次，每次評估成本相同。

**Why this priority**: 這是本功能要修的核心缺陷——防爆破機制在分散式攻擊下成本與攻擊量成正比，反而變成「資料庫資源耗竭」的放大器，會癱瘓**全系統**（非僅登入）。單獨交付即封住此放大、是最小可交付核心。

**Independent Test**: 對一個已鎖定的鍵（帳號或來源）持續送出大量登入嘗試 → 量測每次嘗試的後端資料庫工作量（查詢/寫入數），確認其為**固定常數、不隨累積攻擊量增長**，且系統其他功能在攻擊期間維持回應。

**Acceptance Scenarios**:

1. **Given** 某帳號已因失敗次數達門檻被判定鎖定，**When** 該帳號持續收到大量登入嘗試，**Then** 每次嘗試以固定常數成本被拒，**不**對每次嘗試重新執行隨窗成長的資料掃描或寫入。
2. **Given** 分散式攻擊散佈於大量不同來源、聚合衝同一帳號，**When** 帳號維度達門檻被鎖，**Then** 後續來自**任何**來源的該帳號嘗試皆即時被短路（不因「來源是新的」而重新觸發昂貴的帳號維度偵測）。
3. **Given** 系統正承受對某鎖定帳號的持續攻擊，**When** 同時有其他正常操作進行，**Then** 其他操作不因登入鎖定的資料庫負擔而劣化或失敗。

---

### User Story 2 - 鎖定期間稽核負擔有界、且攻擊訊號保留 (Priority: P2)

身為資安關係人，當攻擊持續時，被壓制（鎖定中）的嘗試**不得**以「每次一列」的方式灌爆稽核儲存（否則攻擊者順手把稽核資料庫也 DoS 掉）；但「正在遭受攻擊」的鑑識訊號（量級、來源廣度）**必須**以**有上限的節流摘要**形式保留，供監控與告警。

**Why this priority**: 兼顧「不被攻擊者灌爆稽核儲存」（次級 DoS 面）與「攻擊仍可被觀測/究責」。次於 US1（核心穩定性）、但為「可被信任地運作且可究責」所需。

**Independent Test**: 對一鎖定鍵持續洪水嘗試 → 確認稽核儲存的成長**有上限**（非每次嘗試一列），且存在一份節流摘要記錄「期間壓制次數＋來源廣度」可供查詢/告警。

**Acceptance Scenarios**:

1. **Given** 某鍵鎖定中且持續被洪水攻擊，**When** 嘗試不斷到來，**Then** 稽核儲存的成長有固定上限（每鍵每時間單位至多一筆摘要）、不與攻擊量成正比。
2. **Given** 鎖定期間的壓制摘要已產生，**When** 維運者查詢監控，**Then** 可見「該鍵在此期間被壓制 N 次／來源廣度」的訊號、並可據以告警。
3. **Given** 一連串嘗試逐步累積到觸發鎖定的那一刻，**When** 稽核被檢視，**Then** 觸發鎖定前的完整嘗試過程**與**觸發鎖定那一發皆完整留存（上鎖前的歷程不丟）。

---

### User Story 3 - 自動恢復、韌性降級、零回歸 (Priority: P3)

身為平台維運者，鎖定硬化不得引入「永久鎖死」「單點故障」或「破壞既有登入行為」：(a) 攻擊停止後鎖定須在設定時窗內**自動解除**、無需人工介入；(b) 加速層若不可用，鎖定仍須由既有機制照常執行（韌性降級、不破壞正確性）；(c) 未被鎖定的正常登入行為（成功與一般失敗）須與現行**完全一致**。

**Why this priority**: 確保硬化不引入新的可用性風險（永久鎖、單點故障）與回歸，是本功能可被信任部署的前提，且為獨立可驗的屬性。

**Independent Test**: (a) 觸發鎖定後停止攻擊 → 確認時窗內自動解鎖、無需人工；(b) 令加速層不可用 → 確認鎖定仍被執行、登入正確性不變；(c) 跑既有正常登入流程 → 行為與現行一致。

**Acceptance Scenarios**:

1. **Given** 某鍵已鎖定，**When** 攻擊停止且經過設定時窗，**Then** 該鍵自動恢復可登入、無需維運者手動解鎖。
2. **Given** 加速層（快取層）不可用，**When** 登入嘗試進來，**Then** 鎖定仍依既有偵測機制正確執行（達門檻仍鎖、未達門檻仍放行）、登入正確性不破。
3. **Given** 一個未被鎖定的使用者，**When** 以正確或錯誤密碼登入，**Then** 結果與現行機制完全一致（成功放行／一般化失敗訊息／該次嘗試照常稽核）。

---

### Edge Cases

- **分散式打單帳號（帳號維度）**：聚合速率可遠超任一來源的上游速率限制 → 鎖定的「服務成本」必須由帳號維度的快取短路擋下，而非每次重新偵測。
- **單一來源洪水（來源維度）**：上游速率限制為第一線；本機制為第二線，鎖定後同樣以固定成本服務。
- **加速層不可用**：退回既有偵測機制（鎖定不失效、只是少了加速）；個別加速操作失敗時降級放行/略過、不阻斷主流程。
- **攻擊停止後**：鎖定須自動老化解除（時窗內），不得因加速層快取而被無限延長成「永久鎖」。
- **觸發鎖定的那一發**：屬「上鎖事件」、須完整稽核（與壓制中的後續嘗試區分）。
- **合法使用者被鎖（帳號-DoS）**：屬鎖定**政策**本身既有性質（達門檻即鎖該帳號）；本功能**不**改變此政策、亦**不**在此提供豁免——受信任來源豁免（白名單）為獨立 future feature。本功能把鎖定執行得更可靠，故須在文件明記此既有風險升高、宜緊接排程緩解。
- **正常成功/失敗登入**：完全沿用既有流程，不受本層影響。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 對「已被判定鎖定」之鍵的後續登入嘗試，系統評估該嘗試的成本 MUST 為**有上限的固定量、與已累積的攻擊量無關**（不得對每次嘗試重新執行隨時窗成長的資料掃描或每次寫入持久稽核列）。
- **FR-002**: 鎖定判定 MUST 同時涵蓋**來源維度與被攻擊帳號維度**兩者；當攻擊散佈於大量來源、聚合衝同一帳號時，帳號維度的鎖定 MUST 能短路後續來自任意來源的該帳號嘗試（僅以來源維度快取不足以擋住分散式打單帳號）。
- **FR-003**: 一旦某帳號或來源被判定鎖定，後續嘗試 MUST 能在**不重新承擔完整偵測成本**下被即時拒絕。
- **FR-004**: 鎖定期間，系統 MUST NOT 為每一次被壓制的嘗試寫入一筆持久稽核列（防稽核儲存被攻擊量灌爆）。
- **FR-005**: 鎖定期間，系統 MUST 保留一份**有上限的節流鑑識記錄**（必需含**壓制次數**；distinct-source 來源廣度為**可選**、非硬需求），使攻擊在被壓制時仍可被觀測與告警。
- **FR-006**: 評估至「觸發鎖定那一發」（含）為止的所有嘗試，其稽核記錄 MUST 完整保留（上鎖前歷程＋上鎖事件不丟）。
- **FR-007**: 鎖定 MUST 在攻擊停止後於設定時窗內**自動解除**、無需人工/管理介入（不得成為可被持續維持的永久鎖）。
- **FR-008**: 加速層 MUST 為**非權威**：其不可用時，鎖定 MUST 仍由既有偵測機制正確執行、登入正確性不破（fail-safe 降級、單點不阻斷）。
- **FR-009**: 未被鎖定的登入嘗試（成功與一般失敗）行為 MUST 與既有機制**完全一致**（零回歸：相同結果、相同一般化鎖定訊息、該次嘗試照常稽核）。
- **FR-010**: 鎖定**政策**（何時觸發鎖定的門檻與時窗）MUST 維持與現行一致；本功能只改變「已生效的鎖定如何被服務」，不改變「何時觸發鎖定」。
- **FR-011**: 鎖定期間的節流鑑識記錄 MUST 以**可被告警的結構化訊號**形式發出、可供維運者監控；本刀交付該訊號（必需），**具體告警規則之配置遞延給維運/obs、不在本刀範圍**。
- **FR-012**: 本功能 MUST 與未來「受信任來源豁免（白名單）」相容——在鎖定判定鏈的最前端**保留可插入豁免的位置**，惟本功能**不實作**該豁免（屬獨立 future feature）。

### Key Entities *(include if feature involves data)*

- **登入嘗試（Login Attempt）**：一次帳號＋來源的登入請求；既有資料。本功能在其被評估前先以鎖定快取短路、並決定是否寫入稽核。
- **鎖定狀態（Lockout State）**：對某「鍵」（帳號維度／來源維度）的「已鎖定」判定，具**有限存活時長**（時窗）、攻擊停止後自動老化解除。為加速層快取之內容，**非**鎖定真相之唯一來源（真相仍在既有偵測機制）。
- **壓制鑑識記錄（Suppression Forensic Record）**：鎖定期間被壓制嘗試的**節流聚合**（**壓制次數**為必需；來源廣度可選；含時窗），供監控/告警；非逐筆、有上限成長。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在對某鎖定帳號的**持續分散式攻擊**下，系統所有功能（登入與其他操作）維持可用、無因資源耗竭導致的劣化或失敗。
- **SC-002**: 對已鎖定鍵的每次嘗試評估成本為**固定常數**——攻擊累積 100 次與 100 萬次時，單次評估的後端工作量（資料查詢/寫入數）相同；持久資料記錄**不**隨被壓制嘗試數成正比成長。
- **SC-003**: 鎖定期間，稽核/鑑識儲存的成長**有固定上限**（每鍵每時間單位至多一筆摘要）、非與攻擊量成正比。
- **SC-004**: 「正在遭受攻擊」的訊號（**壓制次數**為必需；來源廣度可選）在壓制期間 100% 可被觀測並可告警。
- **SC-005**: 攻擊停止後，被鎖定的帳號/來源於設定時窗內 100% 自動恢復可登入、零人工介入。
- **SC-006**: 當加速層不可用時，鎖定執行與登入正確性 100% 不變（fail-safe）。
- **SC-007**: 未被鎖定的登入流程相對既有機制 0 行為回歸。

## Assumptions

- **承接 019-login-lockout**：鎖定**政策值**（per-帳號／per-來源 失敗門檻、滑動時窗）沿用 019 既定值、不在本功能調整（runtime 可調為 019 §4.2 future）。本功能擴充的是「已生效鎖定的服務方式」，沿用既有偵測（資料庫滑動窗失敗計數）為鎖定真相。
- **加速層＝既有快取基礎設施**：系統已具備一個可被重用的快速鍵值快取層（與既有 session 即時撤銷同源），作為非權威的鎖定判定快取；本功能不引入新的外部相依、不新增資料表。
- **鑑識摘要落觀測層**：節流鑑識記錄以結構化事件落既有可觀測性管線（集中式 log／可在儀表板告警），**非**寫入既有登入嘗試稽核表（避免污染鎖定計數並免去資料表結構變更）。
- **既有上游速率限制不變**：反向代理層既有的 per-來源 速率限制維持為第一線；本功能為其無法涵蓋的「聚合 per-帳號」面補強。
- **fail-OPEN 一致**：沿 019，鎖定相關的偵測/快取於失敗時降級放行（縱深防禦、非強一致），由持久層兜底。
- **帳號-DoS 為既有政策性質、緩解另案**：per-帳號鎖定使「以失敗灌爆鎖死特定帳號」成為既有可能；本功能把鎖定執行得更可靠（更不易因負載 fail-open 而漏鎖）→ 此風險升高。受信任來源豁免（白名單）／CAPTCHA 軟挑戰為**獨立 future feature**（019 §4.2 已登記）、本功能僅保留相容接縫（FR-012）。
- **v1 不做（defer）**：受信任來源豁免/白名單／CAPTCHA／帳號-DoS 緩解；runtime 可調門檻；鎖定專屬稽核欄；distinct-來源 精確計數（可選鑑識增益、非必要）；**具體告警規則配置**（本刀只發可告警訊號、規則交 ops/obs）。
