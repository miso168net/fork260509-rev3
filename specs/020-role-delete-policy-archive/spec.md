# Feature Specification: 角色刪除授權歸檔（role-delete-policy-archive — 防角色重建繼承舊授權）

**Feature Branch**: `020-role-delete-policy-archive`

**Created**: 2026-06-27

**Status**: Draft

**Input**: User description: 見 `docs/superpowers/020-role-delete-policy-archive.md`（Phase 0 brainstorm spec-design）。源：CHECKLIST §3.K（P-011-1、2026-06-26 CDP 第2輪全測 HIGH 發現）／011-role-management `data-model.md` deferral 前提被推翻／015-policy-governance＋016-button-endpoint-policy（撤銷→歸檔→復原機制承接）。user 親決：修向＝角色刪除時把該角色授權「歸檔」（非硬刪）、回收桶顯示但標示來源且不可手動復原。

現況：刪除一個角色只把角色標記為已刪，**未清除該角色的授權**。由於角色授權以「角色識別碼（role code）」為鍵、且系統允許用同一識別碼重建角色，導致**重建同識別碼的新角色會靜默繼承已刪角色的選單／按鈕／端點授權**——一個本應是乾淨白板的新角色，憑空獲得舊角色的存取權（按鈕／端點維度即等同 API 存取權）。本功能讓角色刪除即同步移除其全部授權，使重建不繼承；被移除的授權完整歸檔以供稽核，並在授權回收桶中透明顯示、標示來源、但不可誤復原。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 角色刪除即清授權、重建同識別碼不繼承（防靜默權限繼承） (Priority: P1) 🎯 MVP

身為資安關係人／超級管理員，當我刪除一個角色、日後又以**同一識別碼**重建角色時，新角色必須是**乾淨白板**——不得繼承那個已刪角色的任何授權（選單／按鈕／端點存取）。授權應在角色刪除當下即被移除，使「刪除→重建同識別碼」這條路徑無法復活舊權限。

**Why this priority**: 這是本功能要修的核心安全缺陷——靜默權限繼承。按鈕／端點維度的繼承等同未經授予的 API 存取權，屬權限提升風險。單獨交付即封住此路徑、有獨立可驗的安全價值，是最小可交付核心。

**Independent Test**: 建一個拋棄式角色、授予選單＋按鈕＋端點 → 刪除該角色 → 以同一識別碼重建 → 查新角色的選單／按鈕／端點授權皆為**空**。不依賴回收桶顯示軌即可驗。

**Acceptance Scenarios**:

1. **Given** 角色 X 已被授予一組選單／按鈕／端點授權，**When** 刪除角色 X，**Then** 角色 X 的所有 active 授權即被移除（其重建後無可繼承之物）。
2. **Given** 角色 X 已刪、其授權已移除，**When** 以同一識別碼重建一個新角色，**Then** 新角色的選單／按鈕／端點授權查詢皆回空（0 繼承）。
3. **Given** 一次批次刪除含多個角色，**When** 批次刪除執行，**Then** 每個被刪角色的授權都被移除（與批次同生共死）。

### User Story 2 - 已刪角色授權在回收桶透明可查、標示來源、不可手動復原 (Priority: P2)

身為超級管理員，當角色因刪除而被移除授權時，我要能在**授權回收桶**看到這些被歸檔的授權列（知道刪了什麼、可稽核），且每列以**欄位明確標示**其來源是「角色刪除」（與「手動撤銷」的可復原列區分）；同時這些「角色刪除」列**不可經回收桶手動復原**，以免誤把舊授權裝回、又在重建同識別碼時造成繼承。

**Why this priority**: 透明性（看得到刪了什麼、可稽核）與安全性（不可誤復原）兼顧。次於 US1（核心修復）、但為「資料不丟＋可被信任操作」所需。

**Independent Test**: 刪一個有授權的角色 → 開授權回收桶 → 看到該角色被歸檔的授權列、來源欄標示「角色刪除」、且這些列沒有可用的「復原」操作；嘗試強行復原其中一列 → 被拒。

**Acceptance Scenarios**:

1. **Given** 角色 X 因刪除被移除授權，**When** 超管開啟授權回收桶，**Then** 看到 X 原有授權的歸檔列、每列以欄位標示來源為「角色刪除」、可在地化顯示。
2. **Given** 回收桶中一列標示為「角色刪除」來源，**When** 超管查看該列的操作，**Then** 該列**無**可用的「復原」控制（停用／不顯示）。
3. **Given** 有人嘗試（繞過介面）對一列「角色刪除」歸檔發起復原，**When** 系統處理該請求，**Then** 被拒、回一般化業務錯誤、零授權被裝回（後端拒絕為安全邊界，非僅前端隱藏）。

---

### User Story 3 - 不傷害既有治理流程、資料不丟、刪除原子 (Priority: P3)

身為治理功能的維護者，角色刪除歸檔不得破壞既有的「手動撤銷單一授權→回收桶→可復原」流程（仍照常可復原）；被移除的角色授權雖不可復原但須**完整歸檔保存**（非硬刪丟失，可稽核）；且授權移除與角色刪除須為**單一原子操作**（全部成功或全部回滾），不留半完成狀態。

**Why this priority**: 確保修復不引入回歸、不丟資料、不留不一致狀態，是本功能可被信任部署的前提，且為獨立可驗的屬性。

**Independent Test**: (a) 既有「手動撤銷一條授權」→ 該列在回收桶仍可復原（restorable）；(b) 角色刪除的歸檔列存在且內容完整；(c) 模擬刪除中途失敗 → 角色狀態與其授權狀態一致（要嘛都還在、要嘛都已清，無半完成）。

**Acceptance Scenarios**:

1. **Given** 既有「手動撤銷單一授權」流程，**When** 撤銷後於回收桶復原該列，**Then** 復原照常成功（零回歸、該類列仍可復原）。
2. **Given** 角色 X 被刪、其授權被歸檔，**When** 稽核查詢回收桶，**Then** X 原有授權的歸檔列內容完整可查（資料不丟）。
3. **Given** 角色刪除過程在授權移除與角色軟刪之間發生失敗，**When** 操作回滾，**Then** 角色與其授權回到刪除前的一致狀態（無半完成）。

---

### Edge Cases

- **批次刪除多角色**：每個被刪角色的授權各自歸檔、與批次同一原子邊界（批次守門擋下時零變更）。
- **無授權的角色**：刪除一個從未被授予任何授權的角色——無授權可歸檔（no-op），不影響刪除本身。
- **重用識別碼的時點**：刪除與重建之間，無 active 角色持該識別碼、其授權已歸檔故無殘留；重建即乾淨。
- **角色刪除守門先行**：種子角色／使用中角色／操作者自身角色不可刪的守門，於**任何授權移除之前**先檢查；守門擋下時不移除也不歸檔任何授權。
- **受保護授權**：角色刪除情境下，該角色的受保護授權亦一併歸檔（整個角色將不存在，「防誤撤核心存取」的保護不適用於整角色刪除）。
- **角色刪除為單向**：角色本身不可復原（軟刪單向）→ 其授權歸檔為不可復原與此語意一致。
- **存取即時生效**：授權移除後，存取判定即時反映（已刪角色授權不再放行；含多副本一致）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 刪除一個角色（含批次刪除）時，系統 MUST 同步移除該角色的**所有** active 授權（選單、按鈕、端點各維度），使其以同一識別碼重建後不繼承任何授權。
- **FR-002**: 被移除的角色授權 MUST 完整歸檔保存（非硬刪丟失）、可供稽核查詢。
- **FR-003**: 「授權移除」與「角色軟刪」MUST 為單一原子操作——全部成功或全部回滾，不留半完成狀態。
- **FR-004**: 因角色刪除而歸檔的授權列 MUST 出現在授權回收桶，並以**欄位**明確標示其來源為「角色刪除」（與「手動撤銷」列可區分）。
- **FR-005**: 因角色刪除而歸檔的授權列 MUST NOT 可經回收桶手動復原；嘗試復原此類列 MUST 被拒並回一般化業務錯誤（後端拒絕為安全邊界，不得僅靠前端隱藏）。
- **FR-006**: 回收桶每一列 MUST 明確標示其是否可復原，供前端據以顯示或停用「復原」控制。
- **FR-007**: 既有「手動撤銷單一授權→歸檔→復原」流程 MUST 維持不變（該類列仍可復原、零回歸）。
- **FR-008**: 角色刪除情境下，該角色的**受保護（protected）授權**亦 MUST 一併歸檔移除（整個角色將不存在，防誤撤核心存取的保護不適用於整角色刪除）。
- **FR-009**: 角色刪除既有守門（種子角色／使用中／操作者自身角色不可刪）MUST 維持不變，且 MUST 在任何授權移除之前先檢查；守門擋下時零變更（不移除、不歸檔）。
- **FR-010**: 授權移除後，存取判定 MUST 即時反映該移除（已刪角色的授權不再生效，含多副本環境一致）。
- **FR-011**: 回收桶中「角色刪除」列的來源標示 MUST 依使用者所選語言在地化呈現（至少 zh-CN／en-US）。

### Key Entities *(include if feature involves data)*

- **角色授權（Role Authorization）**：一個角色（以唯一識別碼 role code 標識）對資源的存取授予，分**選單／按鈕／端點**三維度。既存資料；本功能在角色刪除時移除並歸檔之。
- **授權回收桶歸檔（Policy Archive Entry）**：被移除授權的歸檔紀錄，含原授權內容、**來源**（手動撤銷 vs 角色刪除）、**是否可復原**、歸檔時間／歸檔者。既存結構；本功能新增「角色刪除」來源類與「可復原」標示。
- **角色（Role）**：以唯一識別碼（code）標識；軟刪為**單向**（不可復原角色本身）。其識別碼可於刪除後重用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 刪除一個已授權角色後、以同識別碼重建，新角色的選單／按鈕／端點授權查詢**皆為空**（0 繼承）。
- **SC-002**: 角色刪除後，該角色原有授權在回收桶 100% 可查、且每列標示來源為「角色刪除」。
- **SC-003**: 對回收桶中「角色刪除」列的手動復原嘗試 100% 被拒（回一般化業務錯誤、零授權被裝回）。
- **SC-004**: 既有「手動撤銷→復原」流程成功率與行為不變（零回歸）。
- **SC-005**: 角色刪除為原子——於授權移除與角色軟刪之間注入失敗時，角色與其授權狀態 100% 一致（無半完成）。
- **SC-006**: 授權移除後，已刪角色的授權於存取判定即時不再放行（無快取殘留放行）。

## Assumptions

- 角色授權已由既有治理層（手動撤銷→歸檔→復原，015／016）管理；本功能**擴充其於「角色刪除」情境的行為**，沿用既有歸檔儲存——**不新增資料表、不新增 migration、不新增元件**。
- 角色軟刪為**單向**（不可復原角色本身）→ 角色刪除歸檔之授權設為不可復原與此語意一致。
- 現有環境**無孤兒授權殘留**（已驗為 0 列）→ 本功能為 fix-forward，**不含**對既有殘留的一次性清理。
- 回收桶「角色刪除」列的來源標示沿用既有後端訊息在地化機制（後端回語言無關識別、前端在地化翻譯）。
- **v1 不做（defer）**：禁止識別碼重用（保留可重用、現已安全）／既有孤兒一次性清理 migration（現為 0）／角色本身復原（軟刪單向）／回收桶依來源過濾器（本功能只做欄位標示＋不可復原）。
