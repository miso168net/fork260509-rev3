# Feature Specification: Observability（波 4）

**Feature Branch**: `018-observability`

**Created**: 2026-06-24

**Status**: Draft

**Input**: User description: 見 `docs/superpowers/018-observability.md`（Phase 0 brainstorm spec-design）。源：INTEGRATION-CHECKLIST §2 波 4／DESIGN §8.2 包覆全體 Observability（rev2 031/032/033 對應物）。一刀三執行單元 obs-min(log)→obs-full(metrics)→dashboard，rev2 對等＋hindsight 修正。

本系統目前無集中觀測能力——各服務 log 散落（需逐一翻容器輸出）、無指標可查、無告警。本功能補上一個**完全選用（opt-in）、預設不啟**的維運觀測層，讓維運者在需要時集中查 log、查指標、收基線告警、看預配置儀表板，且 log 能關聯回既有資料庫審計列。觀測層為內網維運用途、**非終端使用者業務介面**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 集中式日誌彙整與審計關聯 (Priority: P1)

身為維運者，當啟用觀測層的**日誌軌**時，我要能在單一介面集中查詢所有服務容器的 log（不必逐一翻容器輸出），且每筆服務 log 能關聯回它對應的資料庫審計列（同一關聯鍵），以便故障診斷與資安追溯。

**Why this priority**: 日誌彙整是觀測的地基；現況 log 散落、且 log 流與資料庫審計列**無共用關聯鍵**，診斷與追溯都受阻。先交付它即有獨立、可用的觀測價值。

**Independent Test**: 啟用日誌軌 → 對系統發數個請求 → 在日誌查詢介面查到對應 log 行，並能用關聯鍵 join 回該請求的審計列。不依賴指標軌/儀表板。

**Acceptance Scenarios**:

1. **Given** 日誌軌啟用，**When** 任一服務容器輸出 log，**Then** 該 log 於集中查詢介面可見（含來源服務/容器標籤）。
2. **Given** 一個已認證請求產生了審計列，**When** 在日誌介面以該請求的關聯鍵查詢，**Then** 查得對應 log 行，且其關聯鍵等於該審計列的關聯鍵。
3. **Given** 日誌軌未啟用（一般啟動），**When** 系統正常運行，**Then** 無任何觀測元件運行、無額外資源占用。
4. **Given** log 已超過保留期（72 小時），**When** 查詢更舊的 log，**Then** 過期 log 不再保留（容量受控、非無限增長）。

---

### User Story 2 - 指標可觀測與依賴健康 (Priority: P2)

身為維運者，當啟用觀測層的**指標軌**時，我要能查詢系統與服務指標——請求率/延遲/錯誤、權限判決（allow/deny）數、資料庫與快取依賴健康、清理作業結果——以量化系統健康與容量趨勢。

**Why this priority**: 指標是 log 之外的第二觀測軌，讓維運者量化健康/容量/趨勢。次於日誌（地基）、但為告警與儀表板的前提。

**Independent Test**: 啟用指標軌 → 查得後端服務的請求/延遲/錯誤指標、權限判決計數、資料庫/快取依賴健康、清理作業結果指標。不依賴儀表板。

**Acceptance Scenarios**:

1. **Given** 指標軌啟用且系統收到請求，**When** 查請求指標，**Then** 見各端點的請求數、延遲分佈、回應狀態。
2. **Given** 系統發生權限 allow 與 deny 判決，**When** 查權限判決指標，**Then** 見依判決結果（allow/deny）分類的計數。
3. **Given** 資料庫或快取依賴異常，**When** 查依賴健康指標，**Then** 反映該依賴不可用。
4. **Given** 清理作業執行過一次，**When** 查清理指標，**Then** 見上次成功時間與刪除列數。
5. **Given** 指標端點，**When** 從公網經反向代理路徑存取指標端點，**Then** 被擋（不對外暴露；內網採集不受影響）。

---

### User Story 3 - 基線告警 (Priority: P3)

身為維運者，當啟用指標軌時，我要有預設的基線告警規則——核心服務 down、依賴採集端 down、伺服器錯誤率過高——在條件成立時於觀測介面標示為「告警中」。

**Why this priority**: 告警把被動查詢轉為主動偵測，建於指標軌之上。價值高但依賴 US2。v1 僅規則可見、**不投遞通知**（送信 channel 延後）。

**Independent Test**: 啟用指標軌 → 觀測介面見 3 條 baseline 規則；模擬核心服務持續 down → 對應規則轉為「告警中」。

**Acceptance Scenarios**:

1. **Given** 指標軌啟用，**When** 開啟告警規則檢視，**Then** 見 3 條 baseline 規則（核心服務 down／依賴採集端 down／高 5xx 率）。
2. **Given** 核心服務持續 down 超過門檻時間，**When** 評估告警，**Then** 對應規則轉為告警中（critical）。
3. **Given** 伺服器錯誤率持續超過 5%，**When** 評估告警，**Then** 高 5xx 規則轉為告警中（warning）。
4. **Given** 某規則轉為告警中，**Then** 該規則於介面可見為告警中，但 v1 不對外投遞通知（已知 v1 範圍）。

---

### User Story 4 - 預配置觀測儀表板 (Priority: P3)

身為維運者，當啟用觀測層時，我要能直接打開預先配置好的儀表板（總覽／後端服務／資料庫／快取／審計日誌／清理作業），無需手動建立資料源或拼 panel。

**Why this priority**: 儀表板把 log 與指標收斂成可讀視圖、是維運體驗的收尾，建於 US1+US2 的資料源之上。

**Independent Test**: 啟用觀測層 → 打開儀表板介面 → 6 片預配置儀表板皆載入、資料源已自動接妥、panel 有資料或正確空態。

**Acceptance Scenarios**:

1. **Given** 觀測層啟用，**When** 打開儀表板介面，**Then** 6 片儀表板（總覽／後端服務／資料庫／快取／審計日誌／清理作業）皆存在，且資料源已自動接好。
2. **Given** 重建觀測層（重啟/重拉持久卷），**When** 配置重新套用，**Then** 無 crash-loop、資料源與儀表板冪等重建。
3. **Given** 審計日誌儀表板，**When** 開啟，**Then** 正確顯示**本工作區**（非並存的其他工作區）的 log。

---

### Edge Cases

- 一般啟動（未啟用任何觀測軌）→ 零觀測元件運行、零額外資源占用、零對外暴露。
- 觀測層重建/重拉卷 → 配置冪等套用、無資料源識別碼衝突導致的 crash-loop。
- 非結構化（純文字）log 行混入結構化 log 流 → 儀表板查詢不因解析失敗而整片空白或報錯。
- 指標端點 → 內網採集可達，但經公網反向代理路徑被擋（不對外暴露）。
- 清理作業推送指標失敗（觀測層未啟或不可達）→ 不影響清理結果與退出碼（best-effort）。
- 告警條件成立但 v1 無通知 channel → 規則於介面可見為告警中、不投遞（已知 v1 範圍）。
- log 保留期（72 小時）/指標保留期（15 天）屆滿 → 過期資料不再保留（容量受控）。
- 僅啟用指標軌（未啟日誌軌）或僅啟用日誌軌 → 兩軌可各自獨立啟用、互不依賴。

## Requirements *(mandatory)*

### Functional Requirements

**全域：選用與隔離**

- **FR-001**: 觀測層 MUST 完全選用（opt-in）、預設不啟——一般啟動（未啟用觀測）MUST 不啟動任何觀測元件、不產生額外資源占用或對外暴露。
- **FR-002**: 日誌軌與指標軌 MUST 可各自獨立啟用、互不依賴。
- **FR-003**: 觀測層 MUST 為內網維運用途，MUST NOT 作為終端使用者業務介面。
- **FR-004**: 本功能 MUST NOT 改動前端、MUST NOT 改動資料庫結構（零 migration）。

**日誌軌（US1）**

- **FR-005**: 啟用日誌軌時，系統 MUST 集中採集所有服務容器的標準輸出 log，供單一介面查詢。
- **FR-006**: 每筆後端服務 log MUST 攜帶可關聯回對應資料庫審計列的關聯鍵（同一請求的 log 行與審計列共用該鍵）。
- **FR-007**: 採集到的 log MUST 限定為本工作區的容器（不混入並存的其他工作區）。
- **FR-008**: log MUST 有有限保留期（72 小時），過期不再保留。

**指標軌（US2）**

- **FR-009**: 啟用指標軌時，系統 MUST 提供後端服務指標：各端點請求數、延遲分佈、回應狀態。
- **FR-010**: 系統 MUST 提供權限判決指標，依判決結果（allow／deny）分類計數。
- **FR-011**: 系統 MUST 提供資料庫與快取依賴的健康指標。
- **FR-012**: 系統 MUST 提供清理作業結果指標（上次成功時間、刪除列數）；清理作業推送指標 MUST 為 best-effort，推送失敗 MUST NOT 影響清理本身的結果與退出碼。
- **FR-013**: 後端服務的指標端點 MUST 僅供內網採集、MUST NOT 經公網反向代理對外暴露；該端點以指標公開格式回應、不套用標準 API 回應信封（constitution envelope 例外）。
- **FR-014**: 指標 MUST 有有限保留期（15 天）。

**告警（US3）**

- **FR-015**: 啟用指標軌時，系統 MUST 提供 3 條 baseline 告警規則：核心服務 down、依賴採集端 down、伺服器錯誤率過高（5xx > 5%）。
- **FR-016**: 告警規則 MUST 在條件持續成立超過門檻時間後轉為告警中。
- **FR-017**: v1 MUST NOT 投遞告警通知（規則於介面可見即可；送信 channel 延後）。

**儀表板（US4）**

- **FR-018**: 啟用觀測層時，系統 MUST 預先配置資料源與 6 片儀表板（總覽／後端服務／資料庫／快取／審計日誌／清理作業），無需維運者手動設定。
- **FR-019**: 觀測層配置套用 MUST 冪等、重建無 crash-loop。

**安全/認證**

- **FR-020**: 觀測介面 MUST 受存取保護（管理憑證）；憑證以既有 secret 注入機制提供。
- **FR-021**: 依賴採集端 MUST 復用既有資料庫/快取憑證、MUST NOT 引入新的依賴憑證。

**跨切（不可回歸）**

- **FR-022**: 既有後端業務端點、審計、與前端行為 MUST 維持不變（零回歸）。

### Key Entities *(include if feature involves data)*

- **日誌記錄（Log record）**：每筆容器輸出一行，含來源服務/容器標籤、時間、結構化欄位（後端服務 log 含關聯鍵）。
- **指標（Metric）**：時間序列量測——請求數/延遲/回應狀態、權限判決計數、依賴健康、清理作業結果。
- **告警規則（Alert rule）**：條件＋門檻時間＋嚴重度；條件持續成立轉告警中。
- **觀測儀表板（Dashboard）**：預配置的 log/指標視圖集合（6 片）。
- **關聯鍵（Correlation key）**：同一請求的後端服務 log 行與資料庫審計列共用之識別碼（值既已於審計層產生）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一般啟動（未啟用觀測）時，運行中的觀測元件數 = 0、對外暴露的觀測端點 = 0。
- **SC-002**: 啟用日誌軌後，維運者能在單一介面查到任一服務容器的 log（容器涵蓋率 100%）。
- **SC-003**: 維運者能以關聯鍵把一筆後端服務 log 行 join 回其對應的資料庫審計列（關聯成功）。
- **SC-004**: 啟用指標軌後，維運者能查到全部指標類別（請求/延遲/錯誤、權限判決、依賴健康、清理作業結果）。
- **SC-005**: 核心服務持續 down 超過門檻時間後，對應 baseline 告警規則轉為告警中。
- **SC-006**: 觀測層重建後，配置 100% 冪等套用、無 crash-loop。
- **SC-007**: 6 片儀表板於啟用後皆載入、資料源自動接妥、無需手動設定。
- **SC-008**: 經公網反向代理路徑存取指標端點被擋（不對外暴露）；內網採集正常。
- **SC-009**: 既有後端業務端點、審計、與前端行為零回歸。

## Assumptions

- 觀測層技術棧與版本鎖定於設計文件（DESIGN §1.6／brainstorm spec-design）與後續 plan.md；本 spec 描述能力與成效、不綁定特定產品。
- 日誌結構化（含關聯鍵）所需的少量後端變更（per-request log span ＋ 結構化 log 輸出）屬本功能範圍——關聯鍵值既已於審計層算出，僅需令其上至 log 軌。
- 指標 in-process 埋點（指標端點 ＋ 權限判決計數 ＋ 清理作業推送）為本「包覆刀」一次定，前面 entity 刀不留埋點債（DESIGN §8.6）。
- 觀測介面管理憑證以既有 secret 注入機制**新增一個管理密碼 secret**（設計藍圖原列為波 4 補項，as-built 尚未建立）；依賴採集端復用既有資料庫/快取憑證、不新增依賴憑證。
- 觀測軌由維運者明確啟用；一般啟動不啟任何觀測。
- 觀測為內網維運用途；prod 對外暴露/拓樸細節（觀測端點 internal-only 落實）屬部署期、非本功能 v1。
- 後端服務、資料庫、快取、清理作業均為本專案既有元件（指標/log 採集對象既存）。

## Out of Scope

- 告警通知投遞 channel（contact point/notification policy）——v1 僅規則可見，送信延後。
- 採集器非-root 硬化——prod security pass 處理。
- 三個資料庫日誌表（操作異動／API 存取／登入嘗試）的保留期/清除政策——與日誌保留政策一併，延後（⚠️n）。
- 模糊文字搜尋索引優化（pg_trgm/GIN）——規模相關，延後。
- prod 對外暴露/拓樸細節（觀測端點 internal-only 落實）——部署期處理。
- 觀測層水平擴展/多副本——v1 不做。
