## User Scenarios & Testing *(mandatory)*

### User Story 1 - 帳密登入取得通行憑證 (Priority: P1) 🎯 MVP

使用者提供帳號與密碼，系統驗證後發給一組**通行憑證**（一個存取用、一個換發用），使前端能攜帶它存取受保護資源。這是整個認證地基的核心價值：沒有它，任何受保護端點都無法被合法存取，後續所有寫端刀都無從談「誰在操作」。

**Why this priority**: 認證是所有受保護功能的前提，也是前端登入流程接上真後端的起點（在此之前前端只能對 mock）。即使本刀不含任何業務端點，「能登入、能取得憑證」本身即交付可驗收的地基價值。

**Independent Test**: 以既有種子使用者（`Super`／密碼 `123456`）登入，確認回應含一組通行憑證（存取＋換發）；再以錯誤密碼／不存在帳號登入，確認得到一致的登入失敗、且不發任何憑證。

**Acceptance Scenarios**:

1. **Given** 一個存在且啟用的種子使用者，**When** 以正確帳密登入，**Then** 回成功信封、內含一組通行憑證（存取＋換發），形狀符合前端契約。
2. **Given** 帳號不存在／密碼錯誤／帳號已停用，**When** 登入，**Then** 回一致的登入失敗、不發任何憑證、且回應**無法**用以區分失敗發生在哪一步（防帳號枚舉）。
3. **Given** 後端因系統問題（如資料存取失敗）無法完成登入，**When** 登入，**Then** 回系統錯誤（與「帳密失敗」可區分）、不發憑證。

### User Story 2 - 受保護端點依即時角色授權 (Priority: P2)

對受保護端點，系統依**請求者的即時角色**對「該請求路徑＋方法」做授權判定：具權限才放行，否則擋下；憑證缺失或失效則要求重新認證。這讓後續每一個受保護寫端刀都站在「per-route 授權守門就位」的前提上。

**Why this priority**: 授權是受保護資源的守門；它依附 US1（必先有憑證才談授權）。以「即時角色」（而非憑證內嵌的角色快照）為主體，使角色／權限變更能即時生效、不被舊憑證旁路。

**Independent Test**: 對一條受保護的證明端點，分別以「具該端點權限的角色」憑證、「無對應權限的角色」憑證、「無／失效」憑證存取，確認三者分別得到放行／權限不足／要求重新認證。

**Acceptance Scenarios**:

1. **Given** 持有效憑證且其即時角色具該端點權限，**When** 存取受保護端點，**Then** 放行。
2. **Given** 持有效憑證但其即時角色無該端點權限，**When** 存取，**Then** 拒絕（權限不足）。
3. **Given** 無憑證／憑證失效，**When** 存取受保護端點，**Then** 要求重新認證（不視為權限不足）。
4. **Given** 授權判定過程中即時角色查詢因系統問題失敗，**When** 存取，**Then** 回系統錯誤（與「權限不足」可區分、不誤判為拒絕）。

---

### User Story 3 - 取當前使用者資訊與換發憑證 (Priority: P3)

持有效憑證者可取得自己的**身分摘要**（識別碼、顯示名、角色、可用按鈕）供前端啟動載入；憑證接近過期時，可用**換發憑證**換得新的一組通行憑證，免重新登入。

**Why this priority**: 身分摘要是前端載入使用者狀態的必要資料；換發維持長時工作階段的可用性。兩者皆依附 US1（先登入取得憑證）。

**Independent Test**: 持有效憑證取使用者資訊，確認回識別碼／顯示名／角色／按鈕（按鈕清單此刻可為空）；再以換發憑證呼叫換發，確認取得新的一組通行憑證。

**Acceptance Scenarios**:

1. **Given** 持有效存取憑證，**When** 取當前使用者資訊，**Then** 回身分摘要：識別碼（**字串**）／顯示名（暱稱優先、無則帳號）／角色清單／按鈕清單。
2. **Given** 持有效換發憑證，**When** 呼叫換發，**Then** 回新的一組通行憑證。
3. **Given** 憑證失效，**When** 取使用者資訊或換發，**Then** 要求重新認證。

---

### Edge Cases

- **憑證過期／竄改／受眾不符**：一律當未認證、要求重新認證；過期判定**不寬限**（剛過期亦拒）。
- **登入失敗原因不外露**：查無帳號／密碼錯／帳號停用對外呈現**一致**，回應無法區分失敗原因（防帳號枚舉）。
- **識別碼超安全整數範圍**：使用者識別碼對外為字串；若數值超過前端安全整數範圍（2^53）→ 必須 **fail-loud**（不靜默截斷成錯值）。
- **角色查詢系統錯誤 ≠ 權限不足**：授權判定時若即時角色查詢因資料存取問題失敗，須回系統錯誤、不可誤判為「權限不足」。
- **換發為無狀態**：本刀換發不偵測重用、不綁工作階段；有狀態防護（重用偵測／單一工作階段）屬後續刀。
- **按鈕清單可空**：按鈕權限資料尚未種子化 → 使用者資訊的按鈕清單現為空陣列（誠實，非錯誤）。
- **不繞過存取閘**：認證／授權基礎設施不得繞過既有存取閘直接觸碰資料表（沿用既有建置期守恆）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供帳密登入，驗證帳號＋密碼後發給一組通行憑證（一存取用、一換發用）；回應形狀對齊前端契約。
- **FR-002**: 登入失敗（帳號不存在／密碼錯／帳號停用）MUST 回一致的失敗結果、不發任何憑證、且不洩露失敗發生於哪一步（防帳號枚舉）；系統錯誤導致的失敗 MUST 與帳密失敗可區分。
- **FR-003**: 系統 MUST 提供以通行憑證驗證身分的機制，並對受保護端點施行 **per-route 授權**（依請求路徑＋方法判定）。
- **FR-004**: 授權判定 MUST 以請求者的**即時角色**為主體（不信憑證內嵌的角色快照）——使角色／權限變更即時生效。
- **FR-005**: 授權結果 MUST 明確分為三類且互不混淆：放行（具權限）／拒絕（權限不足）／要求重新認證（憑證缺失或失效）；且「即時角色查詢的系統錯誤」MUST 與「權限不足」可區分。
- **FR-006**: 系統 MUST 提供「取當前使用者資訊」，回識別碼（字串）／顯示名（暱稱優先、否則帳號）／角色清單／可用按鈕清單。
- **FR-007**: 系統 MUST 提供「換發憑證」，接受換發憑證並發新的一組通行憑證；本刀為**無狀態換發**（不偵測重用、不綁工作階段）。
- **FR-008**: 通行憑證 MUST 自帶過期；驗證 MUST 拒絕過期（**不寬限**）／竄改／受眾不符的憑證。
- **FR-009**: 本刀對外回應 MUST 採既有統一回應信封（含成功、錯誤碼、訊息）；新引入端點 MUST 經此信封，並對「要求重新認證」「權限不足」採對應錯誤碼。
- **FR-010**: 使用者識別碼對外 MUST 以字串呈現；當其數值超過前端安全整數範圍（2^53）時 MUST fail-loud（不靜默產生錯值）。
- **FR-011**: 授權所用之角色與權限資料 MUST 取自既有種子的權限資料；本刀 MUST NOT 新增 schema 或遷移。
- **FR-012**: 認證／授權基礎設施 MUST NOT 繞過既有存取閘直接觸碰資料表（沿用既有建置期守恆）。
- **FR-013**: 本刀 MUST NOT 含：有狀態 token 輪替鏈／重用偵測／單一工作階段／工作階段模式切換／工作階段快取、操作審計寫入（存取日誌／登入嘗試）、動態選單路由端點、替代登入流程、業務 CRUD 端點。

### Key Entities *(include if feature involves data)*

| 實體 | 要點 |
|---|---|
| 通行憑證對 | 一存取用、一換發用；**無狀態**、自帶身分摘要與過期；不對應任何伺服器端工作階段紀錄 |
| 認證宣告（憑證內身分摘要） | 使用者識別碼／角色／過期／受眾；本刀最小化、**不含工作階段欄**（工作階段識別等屬後續刀） |
| 授權判定器 | 以「角色／路徑或目標／方法」三元組對既有權限資料做**精確比對**的單例；無萬用字元 |
| 受保護端點守門（per-route） | 對受保護端點，先驗憑證取**即時角色**、再做授權判定；輸出放行／拒絕／要求重新認證 |
| 使用者身分摘要 | 識別碼（字串）／顯示名（暱稱優先）／角色清單／按鈕清單 |
| 授權證明端點（proof） | 本刀唯一受 per-route 守門的端點，純為證明授權機制（非業務端點、可僅存於驗證情境） |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 以種子使用者正確帳密登入 → 取得含一組通行憑證的成功信封；對正確憑證的登入成功率為 100%、對錯誤憑證發出憑證的次數為 **0**。
- **SC-002**: 受保護證明端點對三類請求各自正確、互不混淆：具權限角色→放行／無權限角色→拒絕（權限不足）／無或失效憑證→要求重新認證；且「角色查詢系統錯誤」不被誤判為「權限不足」。
- **SC-003**: 登入失敗（查無／密碼錯／停用）對外呈現一致、**無法**由回應區分失敗原因（帳號枚舉防護）。
- **SC-004**: 取使用者資訊回識別碼（**字串**）／顯示名／角色／按鈕；識別碼以字串呈現、超 2^53 時 fail-loud（可在不連資料庫下以純驗證確認字串化與守衛行為）。
- **SC-005**: 過期（不寬限）／竄改／受眾不符 之憑證一律被拒（要求重新認證）；換發端點以有效換發憑證發出新的一組通行憑證。
- **SC-006**: 前端經其代理層真實登入 → 其攔截器正確讀取信封的成功／錯誤碼與資料（憑證被儲存、身分摘要被解析）——前端↔後端 runtime 對齊以瀏覽器實測確認（驗至取使用者資訊＋信封解析為止）。
- **SC-007**: 加入認證／授權基礎設施後後端建置成功；既有存取閘守恆維持綠；健康檢查端點不退化。
- **SC-008**: 殘留檢查——本刀新寫來源中前代專案 token 出現次數為 **0**（以「前代」描述參照）。

## Assumptions

- 凍結權威為不可違反邊界、本 spec 與之一致（衝突序：DECISIONS §1 ＞ DESIGN ＞ 本 spec）：DESIGN §5.3（`casbin_rule` 三維、per-route enforce、**主體為即時角色**、三欄精確相等無萬用字元、enforcer 單例）＋§8.3（Auth 島最小段＝login＋enforce_mw 為各刀共同前提）＋§1.5（auth domain primitive／enforce middleware／handler 分層）＋波 0 出口「login→getUserInfo→enforce 最小鏈 curl 通」；⚠️g（rust-api 全新寫、rev2 受控參照讀允許拷貝禁止）；⚠️r（識別碼逐欄忠實前端契約、2^53 fail-loud）。
- **wire 權威**＝base-web 前端契約：登入回「存取＋換發」兩憑證、使用者資訊含識別碼（字串）／顯示名／角色／按鈕、且存在「換發」端點——本刀回應形狀與之逐欄對齊。
- 既有種子（使用者 `Super`／`Admin`／`User` ＋角色／權限資料）為驗收真實來源；本刀**無 migration、無 schema 變動**。
- 通行憑證之簽章秘密由**既有部署秘密**（檔案形）提供；本刀不新增秘密。
- **stateless 邊界**：有狀態 token 輪替鏈／重用偵測／單一工作階段／工作階段模式切換／工作階段快取，皆為**後續刀**（波 3 行為島）；本刀憑證無狀態、宣告不含工作階段欄、授權與取資訊不做工作階段守門。
- 操作審計寫入（存取日誌／登入嘗試／來源地解析）為**緊接的下一刀**（007）；本刀建立的認證鏈（驗憑證取操作者、登入端點）為其消費點。
- 動態選單路由端點（含登入後動態掛載）、替代登入流程、業務 CRUD 端點皆為**後續刀**（波 2 Menu／波 3／波 1）。
- 按鈕權限資料尚未種子化 → 使用者資訊之按鈕清單現為空陣列（誠實，後續刀種子化後填）。
- 本刀為**首個對外 HTTP handler 刀**與**首個統一回應信封的實際消費者**；驗收含前端瀏覽器實測（驗至「取使用者資訊＋信封解析」為止；登入後的動態路由掛載依賴選單路由端點、屬後續刀）。
