## User Scenarios & Testing *(mandatory)*

### User Story 1 - 帳密登入取得會話憑證 (Priority: P1) 🎯 MVP

使用者以帳號＋密碼登入；憑證正確即取得一組可用的會話憑證（含後續換發用的續期憑證），用於之後所有需要身分的請求。憑證錯誤時得到單一、不洩漏帳號是否存在的失敗結果。

**Why this priority**: 這是整個 Auth 島的地基——沒有「登入取得憑證」，getUserInfo／受保護資源／單一登入全都無從談起；它也是後端 runtime 骨幹（資料連線、狀態、政策引擎）第一次被真正接起來的觸發點。沒有它，前端連登入畫面之後一步都走不了。

**Independent Test**: 對既有種子帳號（`Super`/`123456`）送登入請求 → 取得會話憑證對（存取＋續期）；對錯誤密碼或不存在帳號送登入 → 取得單一登入失敗結果（canonical 碼 `1000`、可在地化訊息 key），且兩種錯誤回應無法區分「帳號是否存在」。

**Acceptance Scenarios**:

1. **Given** 種子帳號 `Super`／正確密碼，**When** 送出登入，**Then** 回成功信封含會話憑證對（存取憑證＋續期憑證字串），且系統內已建立此次登入的會話紀錄與該使用者的「目前會話」指標。
2. **Given** 種子帳號 `Super`／**錯誤**密碼，**When** 送出登入，**Then** 回單一登入失敗（碼 `1000`、訊息為可在地化 key），不揭露帳號是否存在。
3. **Given** **不存在**的帳號，**When** 送出登入，**Then** 回**與情境 2 無法區分**的單一登入失敗（同碼、同訊息形）。

### User Story 2 - 取得登入者身分資訊 (Priority: P2)

持有效存取憑證者，能取得自己的身分資訊：使用者識別碼、顯示名稱、所屬角色代碼集、可用按鈕權限代碼集——供前端決定可見的功能與操作。

**Why this priority**: 前端登入後第一步就是取身分資訊以建立工作階段（顯示使用者、依角色/按鈕權限控制 UI）。沒有它，登入了也是空殼。它驗證了「角色／權限來源」這條從種子資料到前端的縱切是否真的通。

**Independent Test**: 以 US1 取得的存取憑證呼叫身分資訊端點 → 取得該帳號的角色代碼集（如 `Super` → 超級管理員角色）與按鈕權限代碼集（種子政策實有按鈕權限），且使用者識別碼以字串呈現、顯示名稱套用既有 alias 規約（`User`→`User01`）。

**Acceptance Scenarios**:

1. **Given** US1 取得的有效存取憑證，**When** 呼叫身分資訊端點，**Then** 回成功信封含 `{使用者識別碼(字串), 顯示名稱, 角色代碼集, 按鈕權限代碼集}`，內容與該帳號的種子角色／政策一致。
2. **Given** 帳號 `User`，**When** 取身分資訊，**Then** 顯示名稱回 `User01`（alias 規約）。
3. **Given** 角色與按鈕權限取自系統當下紀錄，**When** 取身分資訊，**Then** 反映的是即時資料（非僅憑證內嵌值）。

### User Story 3 - 受保護資源權限守門 (Priority: P2)

對任何需要身分的資源，系統以統一守門：未帶／無效／過期憑證一律擋下；帶有效憑證但**無對應權限**者亦擋下（且與「未認證」用不同結果區分）；有效且有權者放行。此守門機制即後續所有業務端點共用的授權地基。

**Why this priority**: 審計與授權的價值建立在「擋得住」之上；沒有統一守門，每個端點各自為政、漏洞百出。本刀把守門機制一次立起、由最小面（身分資訊端點＋拒絕測）證實，後續業務端點直接站在其上。它也是波 0 出口條件「login→getUserInfo→enforce 鏈通」的「enforce」段。

**Independent Test**: 對受保護端點：(a) 不帶憑證 / 帶壞憑證 / 帶過期憑證 → 一律 `3333`（token-expired）擋下；(b) 帶有效憑證但角色無該資源權限 → `5003`（permission-denied、HTTP 403）擋下；(c) 帶有效且有權憑證 → 放行。授權決策以系統當下角色為準。

**Acceptance Scenarios**:

1. **Given** 受保護端點，**When** 不帶或帶無效/過期憑證請求，**Then** 回 `3333`（token-expired）、不放行。
2. **Given** 有效憑證但角色缺該資源權限，**When** 請求，**Then** 回 `5003`（permission-denied、HTTP 403）、不放行。
3. **Given** 有效且有權憑證，**When** 請求，**Then** 放行至資源。
4. **Given** 一個被改動角色的帳號，**When** 其下次請求被守門，**Then** 授權依**當下**角色判定（不信任憑證內嵌的舊角色）。

### User Story 4 - 單一裝置登入 (Priority: P3)

同一使用者在他處重新登入後，先前那次登入的會話即失效——之後該舊會話對受保護資源的請求被以「他處登入」結果擋下。會話指標讀取暫時失效時，採「放行優先」避免誤踢。

**Why this priority**: 單一登入是安全與合規常見要求，且其「指標真相＋fail-OPEN＋他處登入訊號」是凍結的行為不變式；本刀先把最小段（建指標＋守門）立起、與後續完整會話狀態機 forward-compatible，避免日後 retrofit。屬 P3：登入/身分/守門可獨立先行，單一登入是其上的會話政策。

**Independent Test**: 帳號 `Super` 先登入取得憑證 A → 同帳號再次登入（取得憑證 B、覆蓋目前會話指標）→ 以憑證 A 呼叫受保護端點 → 被以單一登入碼 `7777` 擋下；憑證 B 仍正常。

**Acceptance Scenarios**:

1. **Given** 帳號先後登入兩次（憑證 A 後 B），**When** 以**舊**憑證 A 請求受保護資源，**Then** 回 `7777`（他處登入），不放行。
2. **Given** 同情境，**When** 以**新**憑證 B 請求，**Then** 正常放行。
3. **Given** 會話指標 backing store 暫時讀取失敗，**When** 守門檢查目前會話，**Then** **放行優先**（不誤踢有效使用者）。

---

### Edge Cases

- **帳號不存在 vs 密碼錯誤**：兩者 MUST 收斂為**同一**登入失敗結果（同碼 `1000`、同訊息形）→ 不洩漏帳號是否存在。
- **過期/竄改/缺漏憑證**：守門一律 `3333`（token-expired）擋下（不分「過期」與「壞簽」對外結果）。
- **續期憑證無消費端**：本刀登入仍**簽發**續期憑證字串（滿足前端介面型），但**不**提供換發端點 → 存取憑證過期後下一請求得 `3333`、前端重新登入（可接受）。
- **fail-OPEN vs fail-CLOSED 方向**：會話指標檢查 fail-**OPEN**（可用性優先、不誤踢）；憑證驗證 fail-**CLOSED**（安全優先、驗不過即擋）——兩者方向相反、不得搞反。
- **登入失敗訊息顯示**：登入失敗 MUST 以可在地化 key 回傳、由前端翻譯為在地化文字顯示（非後端硬編語言）。
- **零回歸**：本刀新增端點，但既有健康探針與既有路由行為不得改變。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 接受「帳號＋密碼」登入請求，憑證正確時回傳一組會話憑證（存取憑證＋續期憑證字串）。
- **FR-002**: 密碼驗證 MUST 以不可逆雜湊比對既有種子雜湊（不以明文存取、不回傳密碼）。
- **FR-003**: 登入失敗（帳號不存在／停用／密碼錯誤）MUST 一律收斂為**單一**結果（canonical 碼 `1000`、可在地化訊息 key），**不**洩漏帳號是否存在。
- **FR-004**: 持有效存取憑證者 MUST 能取得自身身分資訊：使用者識別碼、顯示名稱、角色代碼集、按鈕權限代碼集。
- **FR-005**: 使用者識別碼 MUST 以**字串**序列化（對齊 wire 型權威）；顯示名稱 MUST 套用既有 alias 規約（`User`→`User01`）。
- **FR-006**: 角色代碼集 MUST 取自系統當下的使用者-角色關聯；按鈕權限代碼集 MUST 取自系統當下的授權政策（種子政策實有按鈕權限、非空殼）。
- **FR-007**: 受保護資源 MUST 經**統一守門**：缺/無效/過期憑證 → `3333`（token-expired）；憑證有效但權限不足 → `5003`（permission-denied、HTTP 403）；有效且有權 → 放行。
- **FR-008**: 授權決策（守門與身分資訊）MUST 以系統當下角色為準——**不信任**憑證內嵌的角色（防角色過期授權漂移）。
- **FR-009**: 系統 MUST 對每位使用者僅維持一個有效會話：新登入取代前一會話的「目前會話」指標；被取代會話對受保護資源的請求 MUST 以 `7777`（他處登入）擋下。
- **FR-010**: 「目前會話」指標的真相 MUST 落於系統持久紀錄；指標讀取失敗時守門 MUST **fail-OPEN**（不誤踢）。
- **FR-011**: 登入時的「會話憑證紀錄寫入」與「使用者目前會話指標更新」MUST 與登入**原子一致**（同時成功或同時不留）。
- **FR-012**: 會話憑證紀錄 MUST 帶換發鏈識別（供後續換發/重用偵測刀），本刀 MUST NOT 實作換發/重用偵測邏輯。
- **FR-013**: 登入失敗訊息 MUST 為可在地化的訊息 key（非後端硬編字串），由前端翻譯顯示。
- **FR-014**: 憑證簽署密鑰 MUST **優先**取自檔案式 secret、以環境變數為 fallback（密鑰不落純環境變數為首選）。
- **FR-015**: 業務錯誤回應 MUST 遵既有信封與凍結碼矩陣（業務錯誤走 HTTP 200 信封；權限不足 `5003` 為 HTTP 403 例外）；任何續期端點相關碼（`3333`/`9999`/`9998`）MUST NOT 由本刀發出（本刀無換發端點）。
- **FR-016**: 本刀 MUST NOT 引入：換發端點消費邏輯、動態選單路由（getUserRoutes）、登入事件審計、多會話政策設定（三態/熱切換）、替代登入流程、login lockout——各歸後續刀；但登入 MUST 仍**簽發**續期憑證字串以滿足前端介面型。
- **FR-017**: 本刀 MUST NOT 變更資料 schema 或新增 migration（既有實體已就緒）；MUST 保持既有健康探針與既有路由零回歸。

### Key Entities *(資料層一覽；逐欄定義屬 plan 期 data-model)*

| 實體 | 角色 | 說明 |
|---|---|---|
| 使用者 `sys_user` | 認證主體 | 帳號／不可逆密碼雜湊／**目前會話指標**／審計欄。實體已於 002 建齊、本刀不動 schema |
| 會話憑證紀錄 `sys_token` | 登入簽發的會話紀錄 | 每次登入一列；帶會話/換發鏈識別、狀態、簽發/到期時間。本刀只**新增**（不做換發/重用偵測）。002 建齊 |
| 角色 `sys_role` ／ 使用者-角色關聯 `sys_user_role` | 角色來源 | 角色代碼（`R_SUPER`/`R_ADMIN`/`R_USER_COMMON`）；getUserInfo／授權的角色來源。002 建齊+seed |
| 授權政策 `casbin_rule` | 權限來源 | 角色 × 資源 × 維度（按鈕/端點/選單）；本刀用按鈕維度（getUserInfo buttons）與端點維度（守門）。002 建齊+seed |
| 身分資訊（UserInfo）| getUserInfo 回應載體 | `{使用者識別碼(字串), 顯示名稱(alias), 角色代碼集, 按鈕權限代碼集}` |
| 會話憑證對（LoginToken）| login 回應載體 | `{存取憑證, 續期憑證字串}` |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 有效帳密 100% 能登入並取得可用會話憑證對；無效帳密（不存在/錯密碼）100% 以單一 `1000` 失敗擋下、且兩者回應**無法區分**帳號是否存在——由活體驗證證實。
- **SC-002**: 對種子三帳號（`Super`/`Admin`/`User`），身分資訊回的角色代碼集與按鈕權限代碼集 100% 符合其種子角色／政策；使用者識別碼為字串、`User`→`User01` alias 生效——由活體驗證證實。
- **SC-003**: 受保護資源守門：未/壞/過期憑證 100% 以 `3333` 擋下、權限不足 100% 以 `5003`（HTTP 403）擋下、有效且有權 100% 放行——由活體驗證證實。
- **SC-004**: 同帳號二次登入後，**舊**會話對受保護資源的請求 100% 以 `7777` 擋下、**新**會話正常——由活體驗證證實（單一登入 first-mount 成立）。
- **SC-005**: 授權一律以系統當下角色決定（憑證內嵌角色僅作提示、不作授權依據）——由設計審查＋即時角色生效驗證證實。
- **SC-006**: 登入失敗訊息在前端經 i18n 顯示為在地化文字（非後端硬編字串）——由瀏覽器端到端驗證證實（i18n 顯示路徑首個檢核點）。
- **SC-007**: 既有健康探針零回歸、既有路由不破；本刀**零 schema 變更、零 migration**；新碼編入執行中服務——由活體驗證＋變更比對證實。
- **SC-008**: 登入的「會話憑證紀錄寫入」與「目前會話指標更新」原子一致（同成同敗）達 100%——由資料層檢視／測試證實。
- **SC-009**: 範圍邊界守住——本刀**無**換發端點消費邏輯、**無**動態選單路由、**無**登入事件審計、**無**多會話政策設定、**無**替代登入/lockout（皆遞延後續刀）——由 diff／設計審查證實。

## Assumptions

- **schema／實體已就緒**：`sys_user`/`sys_token`/`sys_role`/`sys_user_role`/`casbin_rule` 與授權政策 seed 皆於 002 建齊 → 本刀**無** migration、不建表、不動 entity。
- **預設帳號已 seed**：`Super`/`Admin`/`User`（密碼 `123456`、不可逆雜湊）已隨 002 落地，live 驗證有真資料；角色 `R_SUPER`/`R_ADMIN`/`R_USER_COMMON` 與按鈕政策已 seed。
- **base-web 實碼為 wire 唯一權威**（§I.1/§I.3）：login／getUserInfo 的端點路徑、請求/回應型（`LoginToken`/`UserInfo`、`userId`=字串）以 base-web 現行實碼為準；rust-api 對齊、不更動 base-web inline。
- **runtime 骨幹本刀第一次立起**：rust-api 服務入口此前無資料連線/狀態/政策引擎接線；本刀首次接起並 bootstrap（這是 005 之前各刀刻意延後的「執行期資料連線接線」）。
- **單一登入指標走持久紀錄真相**：快取層（提升每請求指標讀取效能）為後續優化、本刀不接（不阻塞正確性，fail-OPEN）。
- **完整會話狀態機遞延**：token 換發/重用偵測/grace/cleanup、多會話政策三態與熱切換 → 後續「Auth/Token/Session 合刀」。
- **動態選單遞延**：動態路由模式與 getUserRoutes/選單授權 → 後續「Menu 刀」；本刀維持既有靜態路由模式即足以完成登入。
- **登入事件審計遞延**：誰幾時自哪來源登入的存取/登入日誌 → 後續「audit overlay 刀」；本刀登入寫入不入操作審計（op-log）。
- **支援平台 ＝ 既有 dev/prod 容器堆疊**；活體驗證於容器內進行，瀏覽器端到端驗證 i18n 顯示面。
