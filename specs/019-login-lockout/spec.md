# Feature Specification: 登入鎖定（login-lockout — 登入失敗節流／暴力破解・撞庫防護）

**Feature Branch**: `019-login-lockout`

**Created**: 2026-06-25

**Status**: Draft

**Input**: User description: 見 `docs/superpowers/019-login-lockout.md`（Phase 0 brainstorm spec-design）。源：DECISIONS §1 ⚠️w（已拍板「做」）／007-audit-overlay（誕生脈絡、真 IP 解析刻意為此功能備）／rev2 FR-008（原始需求意圖）。本功能為**下游唯讀消費**：消費既備的登入嘗試紀錄與兩複合索引，在登入入口前置跑「滑動時窗內失敗數計數」gate，超門檻即擋。雙軌 both（per-ip ＋ per-user）。0 新表／0 migration／0 新元件。

現況登入入口對「同一帳號被反覆猜密碼」或「同一來源對大量帳號撞庫」沒有任何節流——攻擊者可近乎無限次嘗試。本功能在登入入口前置一道**失敗次數節流 gate**：當某帳號或某來源在滑動時窗內的登入失敗數達到門檻，後續登入即被擋下並回一則一般化提示，時窗滑過後自動解除。判定所需資料（每次登入嘗試的成敗，以及經防偽解析的真實來源）已由既有審計層備齊，本功能純為其下游唯讀消費者，**不新增任何資料儲存**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 帳號層暴力破解防護（per-user 鎖） (Priority: P1) 🎯 MVP

身為一個受保護帳號的擁有者／資安關係人，當有人對「我的帳號」反覆猜密碼時，系統要在連續失敗達門檻後擋下對該帳號的後續登入嘗試（不論來自哪個來源 IP），並回一則不洩漏細節的一般化提示，使單帳號密碼爆破無法持續。

**Why this priority**: 針對特定帳號的密碼猜測是登入入口最根本的威脅；per-user 鎖直接封住它，且天然兼具防帳號枚舉（真假帳號鎖法與訊息一致）。單獨交付即有獨立、可驗的防護價值——是最小可交付核心。

**Independent Test**: 對一個拋棄式帳號連續送 5 次失敗登入 → 第 6 次（即使帶正確密碼）被擋、回一般化提示；對另一個帳號同時不受影響（per-user 隔離）。不依賴 per-ip 軌即可驗。

**Acceptance Scenarios**:

1. **Given** 帳號 Foo 在 15 分鐘內已失敗 5 次，**When** 再次送出對 Foo 的登入（不論密碼對錯），**Then** 被擋下、回一般化「登入失敗次數過多，請稍後再試」、不進入帳密驗證。
2. **Given** 帳號 Foo 已被鎖，**When** 同時間送出對另一帳號 Bar 的登入，**Then** Bar 不受影響、照常驗證（鎖以帳號為界）。
3. **Given** 一個不存在的帳號被連續嘗試 5 次，**When** 第 6 次送出，**Then** 一樣被鎖、回**與真實帳號完全相同**的提示（攻擊者無法藉鎖定行為分辨帳號是否存在）。

### User Story 2 - 來源層暴力破解防護（per-ip 鎖） (Priority: P2)

身為資安關係人，當單一來源 IP 對「大量不同帳號」撞庫（每帳號試幾次、橫掃）時，系統要在該來源累積失敗達（較高的）門檻後擋下其後續登入，封住「換帳號規避 per-user 鎖」的橫向掃描。來源以**經防偽解析的真實 client IP** 為準，不可由偽造的轉發標頭規避。

**Why this priority**: per-user 鎖擋不住「每帳號只試幾次、橫掃多帳號」的撞庫；per-ip 鎖補上這層。次於 per-user（最常見威脅）、但為完整縱深防禦所需。門檻刻意設較高，以避免誤鎖整間辦公室共用的對外 IP。

**Independent Test**: 自同一來源對多個帳號累計送 20 次失敗 → 第 21 次（任一帳號）被擋、回一般化提示。可用「多帳號各自未達 per-user 門檻」觸發，故不依賴 per-user 軌。

**Acceptance Scenarios**:

1. **Given** 來源 IP X 在 15 分鐘內跨多帳號累積失敗 20 次，**When** 自 X 再送任一登入，**Then** 被擋、回一般化提示。
2. **Given** 來源 X 被鎖，**When** 另一來源 Y 送出登入，**Then** Y 不受影響（鎖以來源為界）。
3. **Given** 攻擊者在轉發標頭塞入偽造來源 IP，**When** 系統判定來源，**Then** 以防偽解析後的真實 IP 為準、偽造值無法規避 per-ip 鎖。

---

### User Story 3 - 合法使用者不受傷害（自動解鎖／非枚舉／不誤殺） (Priority: P3)

身為一個偶爾打錯密碼的合法使用者，當我短時間內失敗幾次後，我不該被永久鎖死——只要停手讓失敗紀錄隨時窗滑出，登入即自動恢復、無需找管理員解鎖；同時系統不因內部短暫故障就把整個登入入口鎖死、也不因鎖定行為洩漏我的帳號是否存在。

**Why this priority**: 防護不能以傷害合法使用者為代價。自動解鎖（免人工）、不誤殺（後端抖動時不擋合法登入）、不枚舉（鎖定提示一般化）三項保護，是本功能可被信任部署的前提，且為獨立可驗的安全屬性。

**Independent Test**: (a) 帳號達門檻被鎖 → 等失敗紀錄滑出 15 分鐘窗 → 登入自動恢復、無人工介入；(b) 當系統暫時無法評估鎖定狀態時，合法登入仍照常進行（不被擋）。

**Acceptance Scenarios**:

1. **Given** 帳號 Foo 因 5 次失敗被鎖，**When** 停止嘗試、最舊的失敗逐一滑出 15 分鐘窗使窗內失敗數低於門檻，**Then** 登入自動恢復、無需管理員手動解鎖。
2. **Given** 持續攻擊者在鎖中仍不斷嘗試，**When** 這些被擋的嘗試發生，**Then** 它們本身亦計入失敗數 → 鎖定持續、唯有停手滿一個時窗才解（sticky；攻擊者無法靠繼續打縮短鎖定）。
3. **Given** 系統暫時無法取得失敗計數，**When** 合法使用者登入，**Then** 登入照常進行（鎖定為縱深防禦層、不得使登入入口不可用）。
4. **Given** 任一達門檻被鎖情境，**When** 回應送出，**Then** 鎖定提示為靜態一般化文字、不透露是 per-ip 或 per-user 觸發、不透露剩餘時間、不透露帳號是否存在。

---

### Edge Cases

- **雙維度同時達標**：per-user 與 per-ip 門檻同時觸發時，任一達標即鎖（OR 語意）、回同一般化提示、不區分哪維度。
- **門檻邊界**：剛好達門檻（第 N 次失敗後的下一次嘗試）即鎖；低於門檻不鎖。
- **成功登入不重置計數**：時窗內若有成功登入夾在失敗之間，既有失敗仍計入、隨時窗自然滑出（v1 不做 reset-on-success）。
- **失敗紀錄 best-effort**：偶有紀錄漏寫可接受（鎖定為縱深防禦層、不要求強一致）。
- **鎖中帶正確密碼**：仍被擋（鎖定先於帳密驗證、不因密碼正確而放行）。
- **NAT／共用對外 IP**：per-ip 門檻刻意較高以降低整辦公室誤鎖風險；極端共用情境仍可能誤鎖（per-IP 信任白名單為 v1 defer）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 在某帳號於滑動 15 分鐘時窗內的登入**失敗**數達到 5 次後，擋下對該帳號的後續登入嘗試。
- **FR-002**: 系統 MUST 在某來源於滑動 15 分鐘時窗內的登入**失敗**數達到 20 次後，擋下來自該來源的後續登入嘗試。
- **FR-003**: 一次登入嘗試 MUST 在 per-user **或** per-ip 任一門檻達標時即被擋（OR 語意）。
- **FR-004**: 來源判定 MUST 以經防偽解析的真實 client IP 為準，使偽造的轉發標頭無法規避 per-ip 鎖。
- **FR-005**: 門檻計數 MUST 只計**失敗**的登入嘗試；成功嘗試不計入。
- **FR-006**: 鎖定 MUST 隨時窗滑動自動解除——當時窗內失敗數因舊紀錄滑出而低於門檻，登入即自動恢復，無需任何人工解鎖動作。
- **FR-007**: 成功登入 MUST NOT 重置既有失敗計數（計數僅隨時間滑出時窗；v1 不做 reset-on-success）。
- **FR-008**: 被鎖定擋下的嘗試本身 MUST 亦計入失敗數、並留下審計痕跡（sticky lockout——持續攻擊使鎖定延續，唯有停手滿一個時窗才解；鎖定列與真實失敗列無從區分，維持審計完整與防枚舉一致）。
- **FR-009**: 當帳號或來源處於鎖定中，系統 MUST 直接回鎖定回應、不評估所送帳密（鎖中嘗試一律被擋、與密碼是否正確無關）。
- **FR-010**: 當系統暫時無法評估鎖定狀態時，MUST 放行該次登入照常進行（鎖定為縱深防禦層、MUST NOT 使登入入口不可用）。
- **FR-011**: 鎖定回應 MUST 與「帳號是否存在」無關地保持一致——攻擊者無法藉鎖定行為枚舉帳號。
- **FR-012**: 鎖定提示 MUST 為靜態一般化文字（語意如「登入失敗次數過多，請稍後再試」），MUST NOT 透露觸發維度（per-ip／per-user）、剩餘時間、或帳號存在與否。
- **FR-013**: 鎖定提示 MUST 依使用者所選語言在地化呈現（至少 zh-CN／en-US）。
- **FR-014**: 門檻未達標時，既有登入行為（成功、與各既有登入失敗結果）MUST 維持不變（零回歸）。
- **FR-015**: 對「不存在帳號」的登入嘗試 MUST 與真實帳號的失敗同等納入 per-user／per-ip 失敗計數（試不存在帳號 N 次一樣會被鎖、回一樣的提示——使攻擊者無法以「帳號是否會被鎖」推斷帳號是否存在；此為 FR-011 防枚舉得以成立的機制）。

### Key Entities *(include if feature involves data)*

- **登入嘗試紀錄（Login Attempt）**：每次登入嘗試的既有審計紀錄——含目標帳號名、成敗、經防偽解析的真實來源 IP、發生時間。**既存資料、本功能唯讀消費**（不新增欄位、不新增表）。鎖定判定即對此資料在時窗內做失敗數計數。
- **鎖定政策（Lockout Policy）**：各維度的門檻與時窗值（per-user：5 次／15 分；per-ip：20 次／15 分）。v1 為固定值（runtime 可調為 defer）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 對單一帳號連續 5 次失敗（15 分鐘內）後，第 6 次嘗試（即使密碼正確）被擋；另一帳號同時不受影響。
- **SC-002**: 自單一來源跨任意帳號累積 20 次失敗（15 分鐘內）後，該來源後續嘗試被擋；另一來源不受影響。
- **SC-003**: 被鎖的帳號／來源於停止嘗試後、最遲 15 分鐘內（失敗紀錄滑出時窗）自動恢復登入，全程無需管理員手動介入。
- **SC-004**: 對「存在帳號」與「不存在帳號」的鎖定回應，除帳號本身存在與否外，其餘可觀測欄位（回應碼、提示訊息、是否被擋、回應狀態）完全一致——攻擊者無法由回應差異推斷帳號是否存在（枚舉不可行）。
- **SC-005**: 門檻以下的合法使用者，登入體驗零變化（成功與既有錯誤行為皆不變）。
- **SC-006**: 鎖定狀態暫時無法評估時，合法登入被誤擋的次數為 0（登入入口可用性不受鎖定機制影響）。
- **SC-007**: 持續攻擊者在鎖中繼續嘗試，無法縮短鎖定時長（鎖定不早於「停手滿一時窗」解除）。

## Assumptions

- 每次登入嘗試（成功與失敗皆然）已由既有審計層記錄，且含一個經防偽強化（不可由請求標頭偽造）解析出的真實 client IP；本功能為其下游唯讀消費者，**不新增任何資料儲存**。
- 失敗紀錄寫入為 best-effort（偶有漏寫可接受）；鎖定定位為縱深防禦的一層，非強一致的硬性保證。
- 政策值（per-user 5 次／15 分、per-ip 20 次／15 分）v1 為固定值；runtime 可調門檻、per-IP 信任白名單皆為 defer。per-ip 門檻刻意設高，以降低共用／NAT 對外 IP（如整間辦公室）被整體誤鎖的風險。
- 鎖定提示沿用既有的後端訊息在地化機制呈現（後端回語言無關的訊息、前端在地化翻譯）；登入錯誤路徑預期已走既有的統一錯誤提示通道（待設計階段以實碼確認）。
- **v1 不做（defer）**：管理員手動解鎖介面、動態「剩 N 分鐘」倒數提示、鎖後 CAPTCHA、per-IP 信任白名單、鎖定事件專屬審計欄（區分 lockout-blocked vs 真 auth-fail 及觸發維度）、reset-on-success。
