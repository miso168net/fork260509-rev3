# Feature Specification: Button-Endpoint 授權治理（三維 RBAC runtime 編輯：操作按鈕＋API 端點授權＋受保護核心防誤鎖＋統一回收桶＋跨副本收斂）

**Feature Branch**: `016-button-endpoint-policy`

**Created**: 2026-06-22

**Status**: Draft

**Input**: User description: "`docs/superpowers/016-button-endpoint-policy.md`（Phase 0 brainstorm spec-design）：把 011 角色管理鋪的選單授權寫側、015 補完的授權治理島（撤銷可復原＋受保護核心防誤撤＋精準重載＋多副本收斂），**延伸到另外兩個授權維度——操作按鈕（button）與 API 端點（endpoint）**，補完三維 RBAC 的 runtime 編輯。超級管理員可在角色管理頁編輯某角色「能用哪些操作按鈕、能呼叫哪些 API 端點」，全納入既有治理島的安全保證。一項拍板：scope C（button＋endpoint 完整 runtime 編輯，user 親決 2026-06-22）。延續 015 A 拍板：**un-protect/re-protect 不做**＝受保護核心授權維持不可經 UI 撤銷（防誤鎖核心存取）。**零資料庫結構變更**（按鈕／端點授權項、編輯端點、受保護核心標記全已存在於基線 schema）。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 角色操作按鈕權限編輯：可復原、即時生效 (Priority: P1) 🎯 MVP

超級管理員在維護某角色時，**編輯該角色的「操作按鈕權限」**——即該角色的使用者在各管理頁能看到/使用哪些操作按鈕（新增／編輯／刪除等）。管理員可**授予**新按鈕權限，或**撤銷**既有按鈕權限；撤銷的按鈕權限**不會永久刪除，而是移入授權回收桶**（可日後復原）。變更**立即生效**：該角色的使用者下次取得自身權限時即反映新的按鈕集。今天這個按鈕授權編輯介面是一個**不能用的空殼（mock）**，本故事把它接成真功能。

**Why this priority**: 按鈕層級權限編輯是最常用、最實用的 RBAC 管理需求（決定每個角色在介面上能做哪些操作）；目前的按鈕授權彈窗是一個假資料空殼、完全不能用，補成真功能是高價值、低風險的核心交付（撤銷按鈕只影響介面可見性、不會把任何人鎖出系統，且可從回收桶復原）。構成本功能的最小可交付核心（MVP），不依賴端點維度或多副本即可獨立驗證。

**Independent Test**: 對某角色撤銷一個操作按鈕權限→確認該角色的使用者權限不再含該按鈕、且該按鈕進回收桶；授予一個按鈕權限→確認該角色使用者權限新增該按鈕；從回收桶復原→確認回到現役。全程不需端點維度或多副本即可驗。

**Acceptance Scenarios**:

1. **Given** 某角色現役持有一條操作按鈕權限，**When** 管理員撤銷它，**Then** 該角色的使用者權限不再含該按鈕、且該按鈕權限完整移入回收桶（可復原），此移除與封存**同時成立、不會半套**。
2. **Given** 管理員為某角色授予一條新按鈕權限，**When** 提交，**Then** 該角色的使用者立即取得該按鈕權限。
3. **Given** 回收桶內有一條已撤銷的按鈕權限，**When** 管理員復原它，**Then** 它移回現役、重新生效、回收桶不再有它。

### User Story 2 - 角色 API 端點存取權限編輯：受保護核心防誤鎖、可復原 (Priority: P2)

超級管理員可**編輯某角色的「API 端點存取權限」**——即該角色能呼叫哪些後端 API 端點（以「路徑＋方法」標識）。管理員可授予或撤銷某角色對某端點的呼叫權；撤銷後該角色再呼叫該端點即被拒。**關鍵安全防護**：若管理員嘗試撤銷的批次中**含有受保護的核心端點**（維繫管理員自身的「編輯／恢復」能力的端點，如授權編輯端點、回收桶端點等），系統**整批拒絕、零變更**，避免管理員手滑把自己（或超管）**鎖出核心存取**而再也無法經介面修復。撤銷的端點權限同樣進回收桶可復原。

**Why this priority**: 端點層級（API 存取）編輯補完整個授權模型的最後一維。它比按鈕風險高——直接決定能不能呼叫 API，若誤撤核心端點可能造成無法挽回的鎖死；因此**受保護核心防誤鎖**是本故事的核心價值與必要安全網。優先級 P2，因為它建立在 US1 的治理核心之上、且風險面更高。

**Independent Test**: 對某角色撤銷一個非保護端點權限→確認該角色呼叫該端點被拒、且進回收桶；嘗試撤銷一個含受保護核心端點的批次→整批被拒、零變更、回業務錯誤、管理員的恢復路徑仍在；復原被撤端點→恢復呼叫權。可獨立驗（不影響按鈕維度）。

**Acceptance Scenarios**:

1. **Given** 某角色現役持有對某端點的呼叫權，**When** 管理員撤銷它，**Then** 該角色再呼叫該端點被拒、且該端點權限移入回收桶（可復原）。
2. **Given** 一批待撤銷端點權限中含**受保護核心端點**（維繫編輯/恢復能力者），**When** 管理員提交，**Then** 系統**整批拒絕、零變更**、回業務錯誤——管理員自身的恢復路徑保持完好（不會被鎖出）。
3. **Given** 回收桶內有一條已撤銷端點權限，**When** 管理員復原它，**Then** 該端點呼叫權移回現役、重新生效。

### User Story 3 - 三維授權治理統一：回收桶涵蓋三維＋跨副本一致收斂 (Priority: P3)

授權回收桶（治理面）現在**統一涵蓋三個授權維度**（選單可見性／操作按鈕／API 端點）——被撤的按鈕與端點授權都出現在同一個回收桶、**可依維度區分**、皆可復原。同時，在系統以**多副本**運行時，任一副本上的按鈕／端點授權變更都能讓**所有副本一致收斂**（與既有選單維度同款機制）；變更通知通道短暫斷線後可恢復。

**Why this priority**: 把治理（回收桶＋跨副本收斂）統一延伸到三維，是治理完整性與部署就緒度的收斂層。優先級 P3，因為它建立在 US1/US2 之上、屬治理面的一致性完善，而非獨立的編輯使用者價值面。

**Independent Test**: 撤銷按鈕／端點授權→開回收桶看到它們、可依維度（按鈕／端點）區分、皆可復原；起 2 副本共享儲存→在副本 A 改某角色按鈕/端點授權→副本 B 的授權判斷依最新收斂。可獨立驗。

**Acceptance Scenarios**:

1. **Given** 已撤銷的按鈕與端點授權，**When** 管理員開回收桶，**Then** 它們皆列出、可依授權維度（按鈕／端點／選單）區分、且皆可復原。
2. **Given** 2 副本共享儲存，**When** 在副本 A 撤銷某角色的按鈕/端點授權，**Then** 副本 B 的後續授權判斷依**最新**收斂（跨副本一致）。
3. **Given** 副本間變更通知通道短暫中斷，**When** 通道恢復，**Then** 訂閱者重訂閱、後續授權變更仍跨副本收斂。

---

### Edge Cases

- **撤端點含受保護 vs 全非保護**：批次含任一受保護核心端點→整批拒、零變更；全非保護→正常移入回收桶。受保護判定在任何寫入之前。
- **撤按鈕無鎖出**：按鈕授權無受保護項（撤按鈕僅影響介面可見性、不影響 API 存取）→ 按鈕撤銷一律可行、可復原、不會鎖死任何人。
- **非保護端點被撤＝可逆（恢復走回收桶）**：撤掉某角色的非核心端點權是可逆的；一般可經受保護的授權編輯端點改回，但**若被撤者是守著管理 UI 入口的端點（如角色列表查詢），該角色的管理介面（編輯抽屜）會載不出、無法經抽屜重編——此時恢復路徑＝授權回收桶頁的 restore**（該頁為獨立入口、其選單與回收桶讀寫端點皆受保護、不受 UI-gateway 端點被撤影響、恆可達）。故仍可逆、**非硬鎖出**。
- **復原已現役**：對一個指向「目前已現役」之授權的回收桶項復原→視為**成功的無操作**（消費回收桶項、不重複、不報錯）。
- **精準重載**：撤銷被拒、復原無操作、查無等不改變授權者→不觸發多餘的重載與跨副本通知；空白變更（送與現狀相同的集合）仍重載（沿既有精準語意）。
- **跨副本通知抖動**：通道短暫不可達時本副本仍正確落地、通道恢復後重訂閱、後續變更恢復收斂。
- **零回歸**：既有選單授權編輯（及其治理：回收桶／受保護核心／精準重載／跨副本）行為不變。
- **受保護核心不可經 UI 撤銷（by-design）**：受保護核心端點沒有「解除保護後再撤」的 UI 路徑（延續既有拍板）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：系統 MUST 允許超級管理員**逐角色編輯該角色的操作按鈕權限集**（授予／撤銷）；變更 MUST **立即生效**於該角色的授權判斷（其使用者下次取得自身權限即反映）。
- **FR-002**：系統 MUST 允許超級管理員**逐角色編輯該角色的 API 端點存取權限集**（以「路徑＋方法」標識、授予／撤銷）；變更 MUST **立即生效**於該角色對端點的呼叫授權。
- **FR-003**：任何授權編輯**撤銷**一條或多條授權時，被撤者 MUST **移入可復原的授權回收桶**（封存其角色／目標／維度與原建立資訊、記撤銷時間/人/原因），而**非永久刪除**；此「自現役移除」與「封存」MUST 屬**同一原子交易**。
- **FR-004**：端點授權編輯若嘗試撤銷的批次含**受保護核心端點**（維繫管理員自身的編輯／恢復能力者），系統 MUST **整批拒絕、零變更**、回**業務錯誤**——使管理員**無法經 UI 把自己鎖出核心存取**（恢復路徑恆保留）。
- **FR-005**：授權回收桶 MUST 統一呈現**三個維度**（選單／操作按鈕／API 端點）的已撤銷授權、**可依維度區分**，並允許**復原**其中任一條回現役。
- **FR-006**：任何授權變更（撤銷／復原／授予）MUST 與其**審計記錄屬同一原子交易**（一起成立或一起不留）；復原審計 MUST 記其角色／目標／維度。
- **FR-007**：系統 MUST 僅在授權**實際發生結構性變更**時才重載授權判斷並通知其他副本（精準重載）；對未改變授權者（撤銷被拒、復原無操作、查無）MUST **不重載、不通知**。
- **FR-008**：以**多副本**共享同一資料儲存運行時，任一副本的按鈕／端點授權變更 MUST 讓所有副本的授權判斷**跨副本一致收斂**；變更通知通道短暫中斷後 MUST 能恢復（重新訂閱）。
- **FR-009**：按鈕／端點授權編輯介面與其讀寫能力 MUST 僅限有對應權限的管理員（超級管理員）可達。
- **FR-010**：系統 MUST 保留所有既有授權／角色／選單／稽核行為**零回歸**——既有選單授權編輯及其治理（回收桶／受保護核心／精準重載／跨副本）行為不變。
- **FR-011**：本功能 MUST **不需任何資料庫結構變更**（按鈕／端點授權項、6 個編輯/讀取端點、受保護核心標記皆已存在於基線 schema；無新表、無欄位變更、無 migration）。
- **FR-012**：撤銷一條**操作按鈕**授權 MUST 僅影響該角色使用者在介面上看到/可用的按鈕（按鈕授權無受保護項），且 MUST 可自由復原（不造成任何鎖死）。

### Key Entities *(include if feature involves data)*

- **操作按鈕授權（button authorization）**：一條「某角色可使用某操作按鈕（以按鈕代碼標識）」的授權；有「現役」與「已封存於回收桶」兩種所在；皆非受保護（撤之僅影響介面可見性）。
- **API 端點授權（endpoint authorization）**：一條「某角色可呼叫某 API 端點（以路徑＋方法標識）」的授權；有「現役」與「已封存」兩種所在；可能被標記為**受保護核心**（種子既定、維繫管理員的編輯/恢復路徑、不可經 UI 撤銷）。
- **授權回收桶項（archived authorization）**：一條已撤銷授權規則的封存，**統一涵蓋選單／按鈕／端點三維**、可依維度區分；保留原規則內容＋撤銷時間／執行者／原因；可被復原；不提供永久清除。
- **可授權登錄（authorizable registry）**：可授予的按鈕（全部操作按鈕代碼）與端點（全部可授權的路徑＋方法）之全集，供編輯介面勾選。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：角色操作按鈕權限編輯（授予／撤銷）正確反映於該角色有效授權的比例 **100%**；撤銷的按鈕進回收桶可復原、且兩者同時成立（原子）。
- **SC-002**：角色 API 端點存取權限編輯正確反映於該角色對端點的實際呼叫授權（撤的端點呼叫被拒）的比例 **100%**；撤的端點進回收桶可復原。
- **SC-003**：撤銷批次含受保護核心端點→整批拒、零變更的比例 **100%**——管理員的恢復路徑**永遠無法經 UI 移除**（鎖出事故率 **0%**）。
- **SC-004**：未實際改變授權的操作（撤銷被拒／復原無操作／查無）觸發多餘重載或跨副本通知的比例 **0%**；確實改變授權者觸發重載＋通知的比例 **100%**。
- **SC-005**：以 **2 副本**共享儲存運行時，一副本的按鈕／端點授權變更於另一副本後續授權判斷**一致收斂**（驗證情境中觀察不到跨副本不一致）；變更通知通道斷線後可恢復重訂閱。
- **SC-006**：授權回收桶端到端（列出＋復原）涵蓋按鈕與端點授權、可依維度區分，且**僅超級管理員可達**——端到端驗證通過。
- **SC-007**：既有授權／角色／選單／稽核功能**零回歸**；正式環境映像建置成功。
- **SC-008**：本功能**零資料庫結構變更**（無新表、無欄位變更、無 migration）。

## Assumptions

- **建立在既有授權治理之上**：選單維度的授權編輯與其治理（可復原回收桶／受保護核心防誤撤／精準重載／跨副本收斂）已由前序功能建立，本功能將同款治理**復用延伸**到按鈕與端點維度。
- **授權內容與編輯能力已就緒、零 migration**：按鈕／端點授權項、按鈕與端點授權的編輯及查詢能力、受保護核心端點標記**皆已存在於基線 schema 種子**；本功能只需把既有編輯能力接成真功能、不新增表／欄／migration、不新增程式套件。
- **按鈕定義內嵌於選單**：操作按鈕定義隨選單定義一併儲存（無獨立按鈕登錄表）；可授權按鈕全集由選單定義萃取。
- **受保護核心端點為種子既定且足以防鎖出**：維繫管理員編輯／恢復路徑的核心端點於基線種子既定且**足以涵蓋鎖出防護**；本功能不新增受保護標記，亦不額外保護全部超管端點（恢復路徑已護、保留編輯彈性）。此外**授權回收桶頁為獨立入口、受保護的【通用恢復後盾】**：任何被撤授權（含守 UI 入口的非保護端點如角色列表查詢）皆可在回收桶頁 restore，故無硬鎖出。
- **按鈕授權無受保護項**：撤銷按鈕僅影響介面可見性、不造成鎖死，故按鈕維度無受保護核心。
- **多副本為驗證、非預設拓樸**：多副本僅作機制驗證（起 2 實例共享儲存），非預設部署。
- **明確不在範圍**：解除／重設「受保護」標記（un-protect／re-protect）——受保護核心端點**維持不可經 UI 撤銷**（延續既有拍板、要做須走憲法修訂）；漸進／灰度 rollout（授權編輯為整集合覆蓋、非漸進套用）；授權回收桶的**永久清除**（封存只進可復原、不提供 purge）；任何資料庫結構變更。
