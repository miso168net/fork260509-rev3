# Feature Specification: 个人中心（自助檢視/編輯資料 ＋ 修改密碼）

**Feature Branch**: `025-user-center`

**Created**: 2026-07-02

**Status**: Draft

**Input**: Phase 0 brainstorm — `docs/superpowers/025-user-center.md`（個人中心：帳號/角色唯讀顯示、性別/昵称/手机/邮箱自助編輯、修改密碼〔消費前一刀的管理員密碼政策〕、手机/邮箱驗證入口預留；「密碼政策 ＋ 個人中心」2 刀組的第 2 刀）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 檢視與編輯個人基本資料 (Priority: P1)

登入使用者進入個人中心，看到自己的帳號名稱與角色（唯讀、不可改），以及可編輯的性別、昵称、手机号、邮箱。使用者修改可編輯欄位並儲存，資料即被保存。

**Why this priority**: 這是個人中心的核心價值與 MVP——讓使用者自助維護自己的基本資料、無需麻煩管理員。

**Independent Test**: 以某使用者登入個人中心，修改昵称與性別並儲存，重新載入頁面，驗證顯示為新值；帳號名稱與角色欄位不可編輯。

**Acceptance Scenarios**:

1. **Given** 使用者在個人中心, **When** 檢視, **Then** 看到帳號名稱與角色（唯讀）＋性別/昵称/手机/邮箱（可編輯）。
2. **Given** 使用者修改昵称/性別/手机/邮箱, **When** 儲存, **Then** 變更持久、重新載入後維持。
3. **Given** 使用者檢視頁面, **When** 嘗試操作, **Then** 無法修改帳號名稱與角色（唯讀）。

---

### User Story 2 - 修改自己的密碼 (Priority: P2)

使用者在獨立的「修改密碼」區塊輸入舊密碼、新密碼、新密碼確認並提交。新密碼必須符合管理員設定的密碼複雜度政策；舊密碼須正確、兩次新密碼須一致。

**Why this priority**: 自助改密是帳號安全的關鍵自助能力；建於個人中心之上、消費既有的管理員密碼政策。

**Independent Test**: 以正確舊密碼＋符合政策的新密碼改密，登出後以新密碼登入成功；再以錯誤舊密碼、或不符政策的新密碼嘗試，被明確拒絕、密碼不變。

**Acceptance Scenarios**:

1. **Given** 舊密碼正確、新密碼符合政策且兩次一致, **When** 提交, **Then** 密碼更新、之後可用新密碼登入。
2. **Given** 舊密碼錯誤, **When** 提交, **Then** 以明確業務錯誤拒絕、密碼不變。
3. **Given** 新密碼不符管理員政策, **When** 提交, **Then** 以明確業務錯誤拒絕、密碼不變。
4. **Given** 新密碼與確認不一致, **When** 提交, **Then** 拒絕並提示不一致。

---

### User Story 3 - 檢視帳號建立與更新來源 (Priority: P3)

使用者在基本資料區看到帳號的建立時間與建立來源（系统建立／由管理员建立／本人建立）。若帳號曾被管理員（非本人）修改，也顯示該更新時間並標示「由管理员更新」；若最後修改者為本人 或 從未被修改，則不顯示更新資訊。任何情況都不顯示是「哪一位」管理員。

**Why this priority**: 讓使用者對自己帳號的來歷有透明度、特別是「是否被管理員動過」；屬增益資訊、非核心編輯能力。

**Independent Test**: 以種子帳號檢視→顯示「系统建立」；以管理員建立的帳號檢視→顯示「由管理员建立」；被管理員修改過的帳號→顯示「由管理员更新」＋時間；自行修改後→不顯示更新列；任何情況不顯示具體管理員身分。

**Acceptance Scenarios**:

1. **Given** 帳號由系统種子建立, **When** 檢視, **Then** 顯示建立時間＋「系统建立」。
2. **Given** 帳號由管理員建立, **When** 檢視, **Then** 顯示建立時間＋「由管理员建立」。
3. **Given** 帳號最後由管理員修改, **When** 檢視, **Then** 顯示更新時間＋「由管理员更新」。
4. **Given** 帳號最後由本人修改 或 從未修改, **When** 檢視, **Then** 不顯示更新資訊。

---

### User Story 4 - 手機/信箱驗證入口（預留） (Priority: P3)

手機與信箱各自的區塊，除了可編輯的值，還備有「發送驗證碼／驗證碼輸入／驗證」控件作為**預留佔位**——本階段不進行真實驗證（不接外部服務），為未來的簡訊/信箱驗證預留位置；使用者點擊時得到明確的「功能建置中」提示。

**Why this priority**: 為未來的手機簡訊驗證、信箱/第三方登入綁定預留 UI 位置、讓頁面結構到位；本階段無實際驗證功能、故列低優先。

**Independent Test**: 檢視手機/信箱區塊，確認驗證控件存在且為預留（點擊不進行真實驗證、明示建置中）；手機/信箱的「值」本身仍可正常編輯儲存。

**Acceptance Scenarios**:

1. **Given** 使用者在手機/信箱區塊, **When** 檢視, **Then** 見「發送驗證碼／驗證碼輸入／驗證」控件（預留）。
2. **Given** 使用者點擊驗證控件, **When** 點擊, **Then** 得到「功能建置中」明示、不進行真實驗證。
3. **Given** 使用者編輯手機/信箱的值, **When** 儲存, **Then** 值持久（與驗證流程無關）。

---

### Edge Cases

- **只作用於自己**：所有讀取/修改僅針對登入者本人；不得藉此讀取或修改他人資料。
- **新密碼與確認不一致**：提交前/後皆須攔截、明確提示。
- **政策變更即時性**：管理員調整密碼政策後，個人中心改密碼的規則提示須反映最新政策。
- **未設定的欄位**：手机/邮箱等可為空；顯示與儲存皆須容忍空值。
- **建立/更新來源隱私**：只顯示通用類別（系统/管理员/本人），絕不顯示具體管理員身分。
- **建立來源＝本人（罕見/不可達）**：本系統無自助註冊、帳號由管理員或系統建立，`created_by` 不會等於本人 →「本人建立」分類為**防禦性保留、目前不可達**（無專屬驗收路徑）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 使用者 MUST 能在個人中心檢視自己的：帳號名稱、角色（唯讀）＋性別、昵称、手机号、邮箱。
- **FR-002**: 使用者 MUST 能修改自己的 性別/昵称/手机号/邮箱 並持久保存。
- **FR-003**: 使用者 MUST NOT 能透過個人中心修改自己的 帳號名稱、角色、密碼（密碼另有專屬流程）。
- **FR-004**: 個人資料的讀取與修改 MUST 僅作用於「登入者本人」；MUST NOT 能讀取或修改他人資料。
- **FR-005**: 使用者 MUST 能修改自己的密碼，需提供 舊密碼、新密碼、新密碼確認。
- **FR-006**: 改密碼 MUST 驗證舊密碼正確；舊密碼錯誤 MUST 以明確業務錯誤拒絕、密碼不變。
- **FR-007**: 新密碼 MUST 符合「管理員設定的密碼複雜度政策」；不符 MUST 以明確業務錯誤拒絕、密碼不變。
- **FR-008**: 新密碼與確認不一致 MUST 被拒絕並提示。
- **FR-009**: 改密碼輸入時 MUST 即時依當前政策提示規則，並由系統最終把關（前端提示 ＋ 後端權威雙重）。
- **FR-010**: 手機/信箱區塊 MUST 提供「發送驗證碼／驗證碼輸入／驗證」控件作為**預留佔位**——本階段不接真實驗證、點擊 MUST 明示為建置中。
- **FR-011**: 使用者 MUST 能看到帳號的建立時間與建立來源，來源以通用類別呈現：系统建立／由管理员建立／本人建立。
- **FR-012**: 若帳號最後由**管理員**（非本人）修改，MUST 顯示更新時間並標示「由管理员更新」；若最後修改者為本人 或 從未修改，MUST NOT 顯示更新資訊。
  〔**as-built 勘誤（U-polish、user 收尾拍板推翻本條後半）**：修改时间列【一律顯示】——從未修改→「未修改」、本人修改→bare 時間（無標註）、管理員修改→`（管理员修改）`、系統修改→`（系统修改）`（`updatedBy` 與 `createdBy` 共用 system/self/admin 語意分類）。隱私不變（僅通用類別、不洩露哪個管理員）。詳 contract §2／research R6 as-built。〕
- **FR-013**: 顯示建立/更新來源 MUST NOT 洩露具體是「哪一位」管理員（僅通用類別、不含身分/名稱/識別碼）。
- **FR-014**: 個人中心 MUST 對任何已登入使用者可用（自助、不需額外角色授權）。
- **FR-015**: 本功能 MUST NOT 變更資料庫結構（沿用既有帳號欄位）。

### Key Entities

- **個人資料（Profile）**：登入者可見/可編輯的自身資料——帳號名稱·角色（唯讀）、性別/昵称/手机/邮箱（可編輯）、建立時間·建立來源、（若被管理員更新）更新時間·更新標示。
- **密碼變更（Password change）**：舊密碼·新密碼·新密碼確認；成功條件＝舊密碼正確 ＋ 新密碼符合政策 ＋ 兩次一致。
- **建立/更新來源（Origin）**：帳號被誰建立/更新的通用類別（系统／管理员／本人），不含具體身分。

## Success Criteria *(mandatory)*

- **SC-001**: 使用者可檢視並成功修改自己的 性別/昵称/手机/邮箱，重新載入後 100% 保留。
- **SC-002**: 使用者以正確舊密碼＋符合政策的新密碼成功改密，之後可用新密碼登入。
- **SC-003**: 舊密碼錯誤／新密碼不符政策／新密碼與確認不一致 → 100% 被拒、原密碼不變。
- **SC-004**: 管理員調整密碼政策後，個人中心改密碼的即時規則提示於下一次改密時反映最新政策。
- **SC-005**: 手機/信箱驗證控件呈現為預留（點擊不進行真實驗證、明示建置中）；同時手機/信箱的值可正常編輯儲存。
- **SC-006**: 建立來源正確顯示（種子帳號→系统建立、管理員建立→由管理员建立）；被管理員更新過→顯示「由管理员更新」、本人更新/未更新不顯示更新列；任何情況不顯示具體管理員身分。
- **SC-007**: 使用者無法透過個人中心讀取或修改他人資料（100%）。
- **SC-008**: 導入本功能後，既有登入與使用者資訊零回歸、資料庫結構無變更。

## Assumptions

- 個人中心沿用既有 `/user-center` 路由與頭像下拉入口，替換現有佔位頁（「敬请期待」）。
- 密碼複雜度政策沿用前一刀（管理員可設定）；本功能為其**消費端**、不定義政策內容。
- 手機/信箱「驗證」為**預留佔位**、本階段不接任何外部服務（未來接手機簡訊／信箱·第三方登入綁定）。
- 建立/更新來源以通用類別顯示（隱私：不揭露具體管理員）；種子帳號的建立者顯示為「系统」。
- 介面文字以 zh-CN 為主（繁體化屬未來）。
- 後端不新增資料表、不新增獨立程式模組單元（沿用既有帳號欄位）。
- **治理依賴（待 Constitution Check）**：個人中心為**非後台管理（非-manage）的頂層自助頁**；現有前端 view 變更授權軌道以「後台管理頁」為界、未涵蓋此頁 → 需新增軌道用途授權（brainstorm 已定方向；於 `/speckit-plan` 的 Constitution Check 正式確認/授權）。

## Dependencies

- **密碼複雜度政策功能**（前一刀）：管理員設定 + 系統驗證能力——改密碼消費之。
- 既有帳號資料（性別/昵称/手机/邮箱、建立·更新紀錄、角色關聯）。
- 既有登入身分機制（辨識登入者、確保只作用於本人）。
- 既有業務錯誤呈現通道（改密碼失敗、無效輸入的錯誤訊息）。
