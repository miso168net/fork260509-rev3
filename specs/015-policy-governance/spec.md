## User Scenarios & Testing *(mandatory)*

### User Story 1 - 授權規則回收桶：撤銷可復原、受保護核心防誤撤 (Priority: P1) 🎯 MVP

管理員在維護某角色的授權（例如某角色能看哪些選單）時，**取消授權某規則**——該規則**不會被永久刪除，而是移入「授權回收桶」**（保留它原本是「哪個角色、對哪個目標、哪個維度」的授權，以及撤銷的時間／執行者／原因）。管理員日後可在**授權回收桶頁面**看到所有被撤銷的授權規則，並**復原**任何一條（把它移回現役、重新生效）。同時，若管理員嘗試撤銷的批次中**含有受保護的核心授權規則**（系統種子既定、維繫核心管理頁存取），系統**整批拒絕、零變更**，避免手滑撤掉核心存取造成全站鎖死。

**Why this priority**: 「撤銷可復原」是把目前**一刪不可回頭**的授權治理變成**安全可逆**的核心價值——管理員敢於調整授權，因為撤錯可復原；受保護核心防誤撤則杜絕最危險的誤操作（鎖死自己）。兩者構成治理島的最小可交付核心（MVP），不依賴多副本或精準重載即可獨立交付驗證。

**Independent Test**: 撤銷某角色某非受保護授權→確認該規則進回收桶、現役不再有它；開回收桶頁→看到它→復原→確認回到現役、回收桶不再有它；撤銷一批含受保護核心的授權→整批被拒、現役與回收桶皆零變更。全程不需多副本即可驗。

**Acceptance Scenarios**:

1. **Given** 某角色現役持有一條非受保護授權規則，**When** 管理員撤銷它，**Then** 該規則自現役移除並完整封存入回收桶（保留角色／目標／維度／原建立資訊＋撤銷時間/人/原因），此移除與封存**同時成立、不會半套**。
2. **Given** 回收桶內有一條已撤銷授權規則，**When** 管理員在回收桶頁對它執行復原，**Then** 它被移回現役、重新生效、回收桶內不再有它，並留下一筆復原審計（記角色／目標／維度）。
3. **Given** 一批待撤銷授權中含**受保護核心規則**，**When** 管理員提交撤銷，**Then** 系統整批拒絕、現役與回收桶**零變更**、回業務錯誤（非系統錯誤）。
4. **Given** 一條規則其實**已經現役**（並非被撤銷狀態），**When** 管理員對某「指向同一規則」的回收桶項執行復原，**Then** 視為**成功的無操作**（消費該回收桶項、不重複建立現役、不報錯、不另記變更審計）。
5. **Given** 一個**不存在**的回收桶項，**When** 對它執行復原，**Then** 回業務錯誤、零變更、不留審計。

### User Story 2 - 多副本部署下授權變更跨副本一致收斂 (Priority: P2)

在系統以**多個副本**（水平擴展）共享同一資料儲存運行時，任一副本上發生的授權變更（撤銷或復原）都能讓**所有副本的授權判斷跟著更新**：在副本 A 撤銷某授權後，使用者送到副本 B 的請求也會依**最新**授權被判斷；復原亦然。即使副本之間的**變更通知通道短暫斷線**，機制也能恢復（重新訂閱），不因一次斷線永久脫鉤。

**Why this priority**: 授權判斷若只在「發生變更的那個副本」生效、其他副本仍用舊授權，會造成**跨副本授權不一致**（在 B 副本仍能存取已被撤銷的資源）——這是水平擴展就緒度的關鍵去風險點（設計風險序指定的打樣點）。優先級 P2，因為它建立在 US1 的治理核心之上、屬部署面韌性驗證。

**Independent Test**: 起 2 個副本共享同一資料儲存與通知通道；在副本 A 撤銷某授權→使用者在副本 B 的後續請求依最新授權被拒；在 A 復原→B 後續放行；中斷通知通道→恢復後變更仍能收斂。可獨立驗（不影響單副本行為）。

**Acceptance Scenarios**:

1. **Given** 2 副本共享儲存且某使用者經某授權可存取某資源，**When** 在副本 A 撤銷該授權，**Then** 該使用者送到副本 B 的後續請求依**最新**授權被拒（跨進程收斂）。
2. **Given** 同上但該授權已被撤銷，**When** 在副本 A 復原它，**Then** 副本 B 後續請求恢復放行。
3. **Given** 副本間的變更通知通道短暫中斷，**When** 通道恢復，**Then** 訂閱者自動重訂閱、後續授權變更仍能跨副本收斂（不因一次斷線永久脫鉤）。

### User Story 3 - 授權變更精準生效：只在真改變時重載與廣播 (Priority: P3)

系統在每次授權維護操作後，**只有在授權實際發生結構性變更時**才重載授權引擎並通知其他副本；對於**未改變授權**的情形——撤銷被拒（含受保護）、復原一條已現役的規則（無操作）、復原不存在的項、目標查無——系統**不做多餘的重載與跨副本廣播**，避免無謂擾動。

**Why this priority**: 精準重載是治理機的正確性與效率屬性——避免「明明什麼都沒改、卻廣播一輪讓所有副本重載」的無謂負載與噪音。屬第三優先，因為它建立在 US1/US2 之上、是行為正確性的收斂細節而非獨立的使用者價值面。

**Independent Test**: 對被拒/無操作/查無等不改變授權的操作各執行一次→確認系統不觸發重載、不發跨副本通知；對真正造成授權改變的撤銷/復原→確認必觸發重載＋通知。可獨立驗。

**Acceptance Scenarios**:

1. **Given** 一批撤銷因含受保護核心被整批拒，**When** 操作返回，**Then** 系統不重載授權引擎、不發跨副本通知（零變更⇒零廣播）。
2. **Given** 對一條已現役規則執行復原（無操作），**When** 操作返回，**Then** 同樣不重載、不通知。
3. **Given** 一次撤銷或復原**確實**改變了現役授權，**When** 操作返回，**Then** 系統重載授權引擎並通知其他副本（真變更⇒必收斂）。

---

### Edge Cases

- **撤銷含受保護 vs 全非受保護**：批次含任一受保護核心→整批拒、零變更；全非受保護→正常移入回收桶。受保護判定在任何寫入之前。
- **復原的三種結局**：目標規則目前不在現役（正常）→移回現役＋審計；目標其實已現役→無操作成功（消費回收桶項、不重複、不審計）；回收桶項不存在→業務錯誤、零變更。
- **撤銷／復原的原子性**：業務移動（現役⇄回收桶）與其審計記錄屬同一交易，一起成立或一起不留（不會出現「移了但沒審計」或反之）。
- **零變更不廣播**：被拒、無操作、查無等不改變授權者，不得觸發授權引擎重載或跨副本通知。
- **跨副本通知通道抖動**：通知通道短暫不可達時，授權變更在本副本仍正確落地；通道恢復後訂閱者重訂閱，後續變更恢復跨副本收斂（採韌性恢復、非永久脫鉤）。
- **既有角色授權治理零回歸**：撤銷由「永久刪除」改為「移入回收桶」後，**現役授權的最終狀態與先前一致**（被撤的規則一樣不在現役）——既有角色×選單授權流程行為不變。
- **受保護核心不可經 UI 撤銷（by-design）**：受保護核心授權規則沒有「解除保護後再撤」的 UI 路徑（A 拍板）；管理員授權給自訂角色的規則皆非受保護、可自由治理。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：撤銷一條授權規則時，系統 MUST 將它**移入授權回收桶**（封存其角色／目標／維度／原建立資訊，並記撤銷時間／執行者／原因），而**非永久刪除**；此「自現役移除」與「封存入回收桶」MUST 屬**同一原子交易**（一起成立或一起不留）。
- **FR-002**：系統 MUST 提供**列出授權回收桶**內已撤銷授權規則的能力（分頁；可按角色／維度檢視），呈現之資料 MUST 與底層封存內容逐項一致。
- **FR-003**：系統 MUST 提供**復原**——把回收桶內一條已撤銷授權規則移回現役並重新生效、消費該回收桶項，並記一筆復原審計（角色／目標／維度）。
- **FR-004**：復原一條**已經現役**的規則 MUST 視為**成功的無操作**（消費回收桶項、不重複建立現役、不報錯、不另記變更審計）；復原一個**不存在**的回收桶項 MUST 回**業務錯誤**、零變更、不留審計。
- **FR-005**：撤銷一批授權若含**受保護的核心規則**，系統 MUST **整批拒絕、零變更**（現役與回收桶皆不動）、回業務錯誤——既有行為，**零回歸**。
- **FR-006**：任何授權變更（撤銷／復原）MUST 與其**審計記錄屬同一原子交易**（一起成立或一起不留）；復原審計 MUST 記其角色／目標／維度（而非懸空的封存內部識別碼）。
- **FR-007**：系統 MUST 僅在授權**實際發生結構性變更**時才**重載授權引擎並通知其他副本**；對未改變授權者（撤銷被拒、復原已現役之無操作、復原查無、目標查無）MUST **不重載、不通知**。
- **FR-008**：以**多副本**共享同一資料儲存運行時，任一副本的授權變更 MUST 讓所有副本的授權判斷**跨副本一致收斂**；副本間的變更通知通道短暫中斷後 MUST 能恢復（重新訂閱），不永久脫鉤。
- **FR-009**：授權回收桶頁面 MUST 僅限有對應權限的管理員（超級管理員）可達。
- **FR-010**：系統 MUST 保留所有既有授權／角色／選單／稽核行為**零回歸**——撤銷改為移入回收桶後，**現役授權的最終狀態與先前一致**（被撤規則一樣不在現役）。
- **FR-011**：本功能 MUST **不需任何資料庫結構變更**（授權回收桶儲存已存在於基線 schema；無新表、無欄位變更、無 migration）。
- **FR-012**：授權引擎的寫入路徑 MUST **只動資料儲存的授權真相**（撤銷／復原皆以資料層移動為準），不得繞過資料真相直接操作記憶體中的授權引擎狀態——重載一律以重新讀取資料層為之。

### Key Entities *(include if feature involves data)*

- **授權規則（authorization policy）**：一條「某角色可存取某目標（選單／按鈕／端點等維度）」的規則；有「**現役**」與「**已封存於回收桶**」兩種所在；可能被標記為**受保護**（種子既定的核心規則、不可經 UI 撤銷）。管理員授權給自訂角色的規則皆非受保護。
- **授權回收桶項（archived policy）**：一條已撤銷授權規則的**封存**；保留原規則內容（角色／目標／維度／原建立資訊）＋撤銷時間／執行者／原因；可被**復原**（移回現役）或留存；本功能不提供永久清除。
- **授權引擎（policy engine）**：依**現役**授權規則判斷請求是否放行；授權規則變更後 MUST 重載最新現役規則；多副本各持一份、靠變更通知跨副本同步。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：撤銷一條非受保護授權→該規則進回收桶（含撤銷時間/人/原因）且現役不再有它、兩者同時成立（原子）的正確率 **100%**。
- **SC-002**：從回收桶復原→規則回到現役、回收桶項被消費、復原審計（角色/目標/維度）正確的比例 **100%**；復原已現役→無操作成功（不重複、不報錯）；復原不存在項→業務錯誤、零變更。
- **SC-003**：撤銷含受保護核心規則→整批拒、現役與回收桶**零變更**的比例 **100%**（防誤鎖核心存取）；既有角色授權治理行為**零回歸**（撤銷終態與先前一致）。
- **SC-004**：未實際改變授權的操作（被拒／復原已存在／查無）觸發多餘授權引擎重載或跨副本通知的比例 **0%**；確實改變授權者觸發重載＋通知的比例 **100%**。
- **SC-005**：以 **2 副本**共享儲存運行時，一副本的授權變更於另一副本後續授權判斷**一致收斂**（驗證情境中觀察不到跨副本不一致）；變更通知通道斷線後可恢復重訂閱。
- **SC-006**：授權回收桶頁端到端（列出＋復原）操作成功，且**僅超級管理員可達**——端到端驗證通過。
- **SC-007**：既有授權／角色／選單／稽核功能**零回歸**；正式環境映像建置成功。
- **SC-008**：本功能**零資料庫結構變更**（無新表、無欄位變更、無 migration）。

## Assumptions

- **schema 已就緒、零 migration**：授權回收桶儲存（封存表）**已存在於基線 schema**（波 0 一次全建），含原規則內容＋撤銷時間/人/原因欄；本功能不新增表／欄／migration。
- **建立在 011 角色管理之上**：011 已提供授權寫入（直寫授權儲存、不繞授權引擎）＋受保護核心拒撤＋寫後重載（單副本）；本功能在其上把治理機補完整（撤銷可復原＋精準重載＋跨副本＋回收桶頁）。
- **撤銷目前是永久刪除**：011 的撤銷為硬刪（不可復原）；本功能將其改為**移入回收桶**（可復原），且保證現役授權終態與先前一致（零回歸）。
- **跨副本通知復用既有機制**：會話端跨副本失效通知（已於前一功能建立）的**同款機制**用於授權端的跨副本收斂。
- **受保護核心為種子既定**：受保護的核心授權規則於基線種子既定（核心管理頁存取＋核心選單）；管理員授權給自訂角色的規則皆非受保護、可自由治理。
- **回收桶頁鏡像既有管理頁**：授權回收桶頁的選單入口已於基線種子既定（超級管理員可見）；頁面結構鏡像既有的列表＋還原類管理頁。
- **多副本為驗證、非預設拓樸**：多副本僅作**機制驗證**（起 2 實例共享儲存）、非預設部署；正式負載平衡與預設多副本留待真水平擴展。
- **明確不在範圍**：解除／重設「受保護」標記（un-protect／re-protect）——受保護核心**維持不可經 UI 撤銷**（A 拍板、user 親決 2026-06-22；要做須走憲法修訂）；按鈕／端點維度的授權**編輯**（後續獨立功能）；授權回收桶的**永久清除**（封存只進可復原、不提供 purge）；任何資料庫結構變更。
