- Q: 超級管理員編輯「自己」這筆時，是否要有防自鎖守門（禁止自我降權/自我停用）？ → A: 對稱守門（與 `cannot-delete-self` 同精神）：禁止超管透過自我編輯移除自身的超級管理員角色、或將自己設為停用；違反則整筆拒絕、回業務錯誤、不執行。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理員瀏覽與搜尋使用者 (Priority: P1) 🎯 MVP

授權管理員（超級管理員或一般管理員）要能在後台分頁瀏覽使用者清單，並依條件搜尋——帳號、暱稱、信箱用**部分比對**（輸入片段即可命中），電話、性別、啟用狀態用**精確比對**——以快速找到目標使用者。未填的搜尋條件一律視為「不套用」。

**Why this priority**: 「能看到並找到使用者」是使用者管理的最小前提；沒有讀就無從談增/改/刪。它是本刀最小可交付核心、可獨立先行，也是本刀首次行使「清單搜尋/分頁」這個橫切能力。

**Independent Test**: 以授權管理員登入 → 請求使用者清單（分頁）→ 取得當頁使用者列與正確總數；帶部分帳號片段可命中、帶精確電話可命中、留空條件不縮減結果；翻到超出總數的頁回空清單但總數仍正確。不依賴增/改/刪即可驗證。

**Acceptance Scenarios**:

1. **Given** 授權管理員，**When** 請求第 1 頁使用者清單，**Then** 回傳當頁使用者列（每列含帳號/暱稱/性別/電話/信箱/狀態/所屬角色）與符合條件的**真實總數**；回應**不含**任何密碼資料。
2. **Given** 以帳號片段（如 `us`）搜尋，**When** 查詢，**Then** 回傳帳號**包含**該片段的使用者（大小寫不敏感）；以精確電話搜尋只回完全相符者。
3. **Given** 所有搜尋條件留空，**When** 查詢，**Then** 回全部（未刪除）使用者、**不因空白條件而回零筆**。
4. **Given** 翻到超出總數的頁碼，**When** 查詢，**Then** 回空的使用者列、但總數仍為真實值。

### User Story 2 - 超級管理員新增使用者並指派角色 (Priority: P2)

超級管理員要能新增使用者，填入基本資料並指派一個或多個角色（角色由「目前啟用角色」下拉提供），系統以預設初始密碼建立帳號；帳號名稱在現存使用者中必須唯一，且每次新增都被完整審計。

**Why this priority**: 「能新增使用者」是管理的核心動作之一；建立在 US1（可瀏覽）之上。

**Independent Test**: 以超級管理員新增一名使用者並指派角色 → 該使用者出現在清單、其角色正確、以預設密碼可被驗證；同時留下恰一筆審計（操作者/真實來源 IP/關聯 id/時間）；以已存在的帳號名稱再新增 → 被明確拒絕、回在地化錯誤。

**Acceptance Scenarios**:

1. **Given** 超級管理員與合法表單（帳號、暱稱、性別、電話、信箱、狀態、角色集合），**When** 送出新增，**Then** 建立使用者（預設初始密碼）、指派所選角色、並留下恰一筆審計；使用者異動與角色指派**同成同敗**。
2. **Given** 帳號名稱與某現存（未刪除）使用者重複，**When** 送出新增，**Then** 被明確拒絕、回可讀在地化錯誤、不建立任何使用者。
3. **Given** 角色下拉，**When** 開啟新增表單，**Then** 可選項為系統**目前啟用**的角色全量。

---

### User Story 3 - 超級管理員修改使用者資料與角色 (Priority: P2)

超級管理員要能修改既有使用者的基本資料與所屬角色；但**帳號名稱與密碼不因此操作而改變**（兩者各有獨立治理）；每次修改都被完整審計。

**Why this priority**: 「能修改」與「能新增」同為核心維護動作；需明確界定「改什麼、不改什麼」以免誤改帳號/密碼。

**Independent Test**: 以超級管理員修改一名既有使用者的暱稱與角色 → 變更生效、角色被替換為新集合；該使用者的帳號名稱與密碼維持不變；留下恰一筆審計。

**Acceptance Scenarios**:

1. **Given** 超級管理員與一名既有使用者，**When** 送出修改（新暱稱/性別/電話/信箱/狀態/角色集合），**Then** 該使用者對應欄位被更新、角色被替換為新集合、留下恰一筆審計；**帳號名稱與密碼維持不變**。
2. **Given** 指定一個不存在（或已刪除）的使用者修改，**When** 送出，**Then** 明確失敗、回可讀錯誤、不靜默。
3. **Given** 角色集合包含未知或已刪除的角色，**When** 送出，**Then** 該等無效角色被略過、其餘有效角色正常指派（不整筆失敗）。
4. **Given** 超級管理員編輯**自己**這筆，**When** 嘗試移除自身的超級管理員角色、或將自己設為停用，**Then** 整筆被拒、回在地化業務錯誤、無任何變更（防自鎖；與不可刪自己對稱）。

---

### User Story 4 - 超級管理員刪除/批次刪除使用者（不可刪自己） (Priority: P2)

超級管理員要能單筆或批次刪除使用者（**可復原的軟刪除**，刪除後不再出現於清單）；但**不得刪除自己**——單筆刪自己、或批次清單中含自己，一律**整筆拒絕、不部分執行**；每次刪除都被審計。

**Why this priority**: 刪除是高風險動作；「不可刪自己」防止管理員自鎖、且批次須是全有全無以免半套狀態。

**Independent Test**: 以超級管理員刪除一名（非自己的）使用者 → 該使用者從清單消失（軟刪、可復原語意）、留下審計；嘗試刪除自己或批次含自己 → 整筆被拒、清單無任何變動。

**Acceptance Scenarios**:

1. **Given** 超級管理員與一名非自身使用者，**When** 刪除（單筆或批次），**Then** 該等使用者被軟刪除（不再出現於清單）、各留審計。
2. **Given** 刪除清單包含操作者自身 id（單筆即自己、或批次含自己），**When** 送出，**Then** **整筆**被拒、回在地化錯誤、**無任何**使用者被刪（不部分執行）。
3. **Given** 批次刪除清單含已不存在/已被他人刪除的 id（但不含自己），**When** 送出，**Then** 該等缺漏 id 被靜默略過、其餘有效使用者正常軟刪、各留審計（不因缺漏而整批失敗）。

---

### User Story 5 - 依角色授權存取（越權防護） (Priority: P2)

使用者管理是敏感操作：瀏覽清單限**超級管理員與一般管理員**；新增/修改/刪除限**超級管理員**。任何不具該權限者（含已登入的其他身分）一律被拒、不洩漏資料；授權一律依**系統當下**的角色判定。

**Why this priority**: 沿用波 1 建立的「受治理端點」防線；使用者資料外洩/誤改風險高，須以對抗式測試驗收。

**Independent Test**: 以一般使用者請求清單 → 被拒；以一般管理員請求新增/刪除 → 被拒（清單仍可讀）；以未認證請求 → 被既有認證守門拒絕；即便憑證內嵌過期/被竄改的角色，判定仍以系統當下角色為準。

**Acceptance Scenarios**:

1. **Given** 已認證但無對應權限者，**When** 存取受限操作（一般使用者讀清單、或一般管理員寫），**Then** 回 403 權限不足、回應不洩漏使用者資料。
2. **Given** 授權判定，**When** 進行，**Then** 依系統當下角色判定（不採信憑證內嵌角色宣告）。
3. **Given** 未帶/無效憑證，**When** 存取任一使用者管理操作，**Then** 被既有認證守門拒絕。

---

### User Story 6 - 停用使用者無法登入 (Priority: P3)

被設為「停用」狀態的使用者無法再登入系統；登入被拒時回**統一的登入失敗**結果（不透露「帳號存在但被停用」以防帳號枚舉）。已登入者的即時逐出不在本刀範圍（其憑證自然到期後即無法續用）。

**Why this priority**: 停用是管理使用者生命週期的安全動作；即時逐出涉及行為島狀態機、屬後續波次，故本刀只擋新登入、列 P3。

**Independent Test**: 將一名使用者設為停用 → 以其憑證重新登入被拒、且錯誤訊息與「帳號或密碼錯誤」一致（不洩停用狀態）；啟用狀態使用者登入正常。

**Acceptance Scenarios**:

1. **Given** 一名被停用的使用者，**When** 嘗試登入，**Then** 登入被拒、回統一登入失敗（不揭露其為「停用」）。
2. **Given** 一名啟用中的使用者，**When** 登入，**Then** 正常成功（停用 gate 不影響正常使用者）。

---

### Edge Cases

- **空白搜尋條件**：未填的篩選一律不套用；**全部留空回全部使用者、不得回零筆**（避免「整頁 0 列」）。
- **超範圍頁碼**：回空使用者列、但總數仍為真實值。
- **重複帳號名稱**：新增時與現存（未刪除）使用者撞名 → 被拒、回在地化錯誤、不建立（含並發同時新增同名的競態，亦不得以系統內部錯誤呈現）。
- **修改不存在/已刪除使用者**：明確失敗、不靜默。
- **角色集合含未知/已刪角色**：略過無效者、其餘正常（不整筆失敗）。
- **刪除自己（單筆或批次含自己）**：整筆拒絕、不部分執行。
- **自我降權/自我停用**：超管編輯自己時移除自身超管角色、或將自己設停用 → 整筆拒絕、回在地化業務錯誤、不執行（防 admin 自鎖；與不可刪自己對稱）。
- **批次含缺漏 id**：批次中已不存在/已被刪的 id 靜默略過、有效者照刪（idempotent；缺漏不致整批失敗；cannot-delete-self 仍為獨立整批拒絕）。
- **讀端密碼外洩**：任何讀/清單回應一律不含密碼或其雜湊。
- **非授權（已認證）讀/寫**：403、不洩資料；**未認證**：被既有認證守門拒絕。
- **寫入與審計/角色指派不可分割**：審計或角色指派失敗時，使用者異動一起回滾（不存在未被審計的異動、不存在使用者已改而角色未同步的半套）。
- **停用使用者登入**：擋下、回統一登入失敗（不洩停用狀態）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓授權管理員分頁瀏覽使用者清單，並支援搜尋：帳號/暱稱/信箱為**部分比對（大小寫不敏感）**、電話/性別/狀態為**精確比對**；未填的搜尋條件 MUST 視為不套用，且**全部留空時回全部（未刪除）使用者、不得回零筆**；超出總數的頁碼 MUST 回空清單但回真實總數。
- **FR-002**: 任何讀取/清單回應 MUST NOT 含使用者密碼或其雜湊。
- **FR-003**: 超級管理員 MUST 能新增使用者並指派一個或多個角色、以系統預設初始密碼建立；帳號名稱在現存（未刪除）使用者中 MUST 唯一，重複（含並發競態）MUST 被拒、回可讀在地化錯誤、不建立任何使用者，且 MUST NOT 以系統內部錯誤呈現此業務衝突。
- **FR-004**: 超級管理員 MUST 能修改既有使用者的基本資料與角色集合（角色為**整批替換**語意）；此操作 MUST NOT 變更帳號名稱與密碼；修改不存在/已刪除使用者 MUST 明確失敗、不靜默。此外，超級管理員 MUST NOT 透過此操作對**自己**移除自身的超級管理員角色、或將自己設為停用（防自鎖；違反則整筆拒絕、回在地化業務錯誤、不執行）。
- **FR-005**: 超級管理員 MUST 能單筆或批次軟刪除使用者（刪除後不出現於清單、保留可復原語意）；MUST NOT 允許刪除操作者自身——單筆刪自己或批次含自己一律**整筆拒絕、不部分執行**。批次中已不存在/已被刪除的 id MUST 被靜默略過（idempotent）、不影響其餘有效 id 的刪除（缺漏略過與 cannot-delete-self 整批拒絕為各自獨立規則）。
- **FR-006**: 每次新增/修改/刪除 MUST **原子地**連同寫入一筆不可竄改的審計（操作者 id／操作者真實來源 IP／關聯 id／時間／異動內容）；使用者異動、角色指派與其審計 MUST 同成同敗（不存在未被審計的異動、不存在使用者已改而角色未同步的半套）。
- **FR-007**: 系統 MUST 依角色授權——瀏覽清單限超級管理員與一般管理員；新增/修改/刪除限超級管理員；非授權者（含已認證之其他身分）MUST 被拒（403）且回應 MUST NOT 洩漏使用者資料；授權判定 MUST 依系統當下角色、MUST NOT 採信憑證內嵌的角色宣告。
- **FR-008**: 系統 MUST 提供「目前啟用角色」全量作為使用者表單的角色指派來源。
- **FR-009**: 被停用的使用者 MUST 無法重新登入、且回**統一登入失敗**結果（不洩「帳號存在但停用」以防枚舉）；已登入者之即時逐出 NOT in scope（憑證自然到期）。
- **FR-010**: 系統 MUST 以自動化檢查驗證「受保護端點 ↔ 授權檢查 ↔ 授權策略」三者一致（無端點漏掛授權、無漏設策略）。
- **FR-011**: 後台既有使用者管理頁的新增/修改/刪除/批次刪除 MUST 實際對後端發出請求並反映結果（MUST NOT 僅顯示成功提示而未實際異動）；操作鈕 MUST 依使用者權限顯隱；錯誤與成功訊息 MUST 在地化顯示。
- **FR-012**: 本功能 MUST NOT 變更任何既有資料結構（schema）、MUST NOT 回歸既有登入／身分／權限守門／健康探針／系統設定行為。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 授權管理員瀏覽/搜尋使用者 100% 正確——部分比對欄命中子字串、精確比對欄全等、空白條件不套用（全空回全部、非零筆）、超範圍頁回空清單但總數正確——由活體＋瀏覽器驗證證實。
- **SC-002**: 讀取/清單回應 100% 不含密碼資料——由活體驗證證實。
- **SC-003**: 超級管理員新增使用者 100% 成功建立＋指派角色＋留恰一筆審計（操作者／真實來源 IP／關聯 id）；重複帳號 100% 被拒且不建立、且不以系統內部錯誤呈現——由活體驗證證實。
- **SC-004**: 超級管理員修改使用者 100% 不更動帳號名稱與密碼、角色 100% 正確替換、留恰一筆審計；自我降權/自我停用 100% 被擋（防自鎖、整筆不執行）——由活體驗證證實。
- **SC-005**: 單筆/批次軟刪 100% 生效（被刪者不再出現於清單）；刪自己（單筆或批次含自己）100% 整筆被拒、無部分執行；批次含缺漏 id 100% 略過缺漏並刪有效者（idempotent）——由活體驗證證實。
- **SC-006**: 非授權讀/寫 100% 被拒（403）且不洩使用者資料；授權 100% 依系統當下角色判定——由活體＋瀏覽器驗證證實。
- **SC-007**: 被停用使用者 100% 無法重新登入、回統一登入失敗——由活體驗證證實。
- **SC-008**: 後台頁新增/修改/刪除/批次刪除 100% 實際對後端發出請求並反映結果（無「假成功」）、訊息在地化——由瀏覽器端到端驗證證實。
- **SC-009**: 受保護端點授權守恆 100% 通過（無端點漏掛授權／無漏設策略）——由自動化守恆檢查證實。
- **SC-010**: 既有登入／身分／權限守門／健康探針／系統設定行為 100% 零回歸；本功能**零 schema 變更**——由活體驗證＋變更比對證實。
- **SC-011**: 清單讀取 p95 < 300ms、寫入（含同交易審計）p95 < 500ms——對齊既有效能保守預設。

## Assumptions

- **既有基礎已就緒、本刀零重建**：使用者與使用者–角色關聯的資料結構、種子帳號與角色、角色授權策略、統一回應信封與業務錯誤碼/在地化鍵規約、資料異動的同交易審計機制、認證守門＋授權檢查分層、稽核上下文（操作者/真實來源 IP/關聯 id）皆已由前序波次建妥；本刀**不改 schema、不重建這些機制**，只新增使用者 CRUD 的讀/寫/前端與授權接線。
- **角色指派為整批替換語意**：送入的角色集合即為使用者的新角色狀態；未知/已刪除角色靜默略過（不整筆失敗）。
- **預設初始密碼沿既有約定**；**改密碼為獨立未來功能、不在本刀**（修改使用者刻意不動密碼）。
- **帳號名稱為身分鍵、修改使用者時不可變**（與密碼治理分離）。
- **停用之即時逐出延後**：本刀只擋被停用者的**新登入**；已發憑證之即時撤銷屬後續波次（行為島/session 機器）。
- **角色下拉為薄讀**：提供啟用角色全量供指派，**非完整角色管理功能**（角色 CRUD 為另一刀）。
- **使用者識別碼前後端一致呈現、不型別漂移**（沿既定識別碼序列化拍板）。
- **前端為既有頁接線**（非新頁）：將既有使用者管理頁由示意（mock）接上真實後端，沿既有後台慣例與在地化機制；操作鈕依權限顯隱。
- **清單搜尋/分頁為本功能首次行使的橫切能力**：含「空白條件不套用」守門與字串欄部分比對；驗收須涵蓋以乾淨查詢無法重現、必經瀏覽器/帶空白條件才能觸發的情境。
- **本刀範圍邊界（OUT）**：停用即時逐出（後續波次）／單一登入裝置策略設定（後續波次）／完整角色管理與角色×權限授權（另一刀）／選單與路由授權（另一刀）／改密碼（獨立未來功能）。
