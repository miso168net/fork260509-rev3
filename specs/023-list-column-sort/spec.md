# Feature Specification: 列表欄位排序（多欄、伺服端、可保留）

**Feature Branch**: `023-list-column-sort`

**Created**: 2026-06-30

**Status**: Draft

**Input**: Phase 0 brainstorm — `docs/superpowers/023-list-column-sort.md`（多欄 server-side 列表排序 ＋ 一鍵清除 ＋ 本機持久化；範圍 7 個分頁列表、menu 排除）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 依單一欄位排序整個列表 (Priority: P1)

使用者在某個分頁列表頁（如使用者管理、操作日誌）瀏覽資料，想依某一欄（例如建立時間、名稱）排序。使用者點擊該欄的標頭，整個資料集（不只當前頁）即依該欄排序；再點一次切換方向，第三次點取消該欄排序。

**Why this priority**: 這是本功能的核心價值與 MVP —— 沒有它，使用者完全無法依想要的欄位看資料。單欄、伺服端、整資料集排序是其餘所有能力的基礎。

**Independent Test**: 在一個資料超過一頁的列表，點擊某可排序欄標頭；驗證顯示的第一列是整個資料集在該欄的極值（與完整資料集比對），而非只重排原本可見的那一頁。

**Acceptance Scenarios**:

1. **Given** 某列表有多頁資料且無排序作用, **When** 使用者點擊某可排序欄標頭一次, **Then** 整個資料集依該欄降冪排序、列表回到第一頁、該欄顯示降冪指示。
2. **Given** 某欄已為降冪, **When** 使用者再次點擊該欄標頭, **Then** 改為升冪排序。
3. **Given** 某欄已為升冪, **When** 使用者第三次點擊該欄標頭, **Then** 取消該欄排序、列表回到預設順序、指示消失。

---

### User Story 2 - 多欄位排序（依點擊順序定優先序） (Priority: P2)

使用者想先依某欄、再於相同值內依另一欄排序（例如先依狀態、再於同狀態內依建立時間）。使用者依序點擊多個欄標頭，先點的欄為主排序、後點的為次排序，各欄方向可獨立切換。

**Why this priority**: 多欄排序是使用者「依當下想看的方式組合排序」的關鍵；建立於 P1 之上，提供顯著的查閱效率。

**Independent Test**: 先點欄 A 再點欄 B；驗證資料先依 A 排序、A 相同者再依 B 排序（A 為主、B 為次）。

**Acceptance Scenarios**:

1. **Given** 列表已依欄 A 排序, **When** 使用者再點擊欄 B 標頭, **Then** 資料依「A 為主、B 為次」排序。
2. **Given** 已有 A、B 多欄排序（A 為主）, **When** 使用者取消欄 A 的排序, **Then** 欄 B 遞補為主排序。

---

### User Story 3 - 一鍵清除全部排序 (Priority: P3)

使用者套用了多欄排序後，想快速回到列表的預設順序，而不需逐欄點到「取消」。使用者按一個「清除排序」控制項，所有作用中的排序立即清除、列表回預設順序。

**Why this priority**: 多欄排序後逐欄取消很繁瑣；一鍵清除是體驗上的明顯便利，但非核心查閱能力。

**Independent Test**: 套用 2 欄以上排序後，按「清除排序」；驗證列表回到預設順序、所有欄排序指示消失。

**Acceptance Scenarios**:

1. **Given** 某列表有一個以上欄位作用中排序, **When** 使用者按「清除排序」, **Then** 全部排序清除、列表以預設順序重新呈現、所有排序指示移除。

---

### User Story 4 - 排序在離開頁面後返回仍保留 (Priority: P3)

使用者排好某列表後，切到別的頁面再回來，期望先前的排序還在、不必重排。系統將每個列表頁的當前排序保存在使用者本機，返回時自動還原。

**Why this priority**: 避免重複操作、提升連續工作體驗；屬增益，非 MVP 必需。

**Independent Test**: 排序某列表 → 導航到另一頁 → 返回同一列表；驗證先前排序仍套用（資料順序＋欄位指示）。

**Acceptance Scenarios**:

1. **Given** 使用者已對某列表設定排序, **When** 使用者離開該頁再返回（同一瀏覽器）, **Then** 該列表自動以先前排序呈現、欄位指示還原。
2. **Given** 已保留的排序引用某個現已不可排序的欄位, **When** 使用者返回該頁, **Then** 系統忽略該無效欄位、以其餘有效排序呈現、不報錯。

---

### Edge Cases

- **空／未設排序**：請求未帶或帶空的排序內容 → 視為「無排序」、回該列表的預設順序。
- **無效欄位／方向**：排序引用未被允許的欄位、或非「升／降」之外的方向 → 以業務驗證錯誤拒絕，不回傳錯排資料、不造成伺服器錯誤。
- **重複欄位**：同一欄在單次排序請求中出現多次 → 視為無效、拒絕。
- **排序 × 篩選並存**：排序套用在「篩選後的結果集」上；使用者變更篩選條件時，當前排序仍保留。
- **樹狀列表**：選單管理為樹狀檢視、非分頁平表 → 不提供欄位排序（範圍外）。
- **多欄深度**：多欄排序的欄位數天然受「該列表可排序欄位數」上限約束，不會無限制膨脹。
- **保留狀態失效欄位**：本機保留的排序含某個已被移除／改為不可排序的欄位 → 還原時防禦性忽略該欄。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 使用者 MUST 能在每個範圍內的列表頁，點擊「可排序欄位」標頭來排序該列表。
- **FR-002**: 排序 MUST 套用於符合條件的「整個資料集」（跨所有分頁），而非只重排當前顯示的那一頁。
- **FR-003**: 連續點擊同一可排序欄標頭 MUST 依序循環：降冪 → 升冪 → 取消該欄排序。
- **FR-004**: 使用者 MUST 能同時依多個欄位排序；排序優先序 MUST 由「欄位被啟用的先後順序」決定（先啟用者為主排序）。
- **FR-005**: 每個可排序欄位 MUST 能獨立指定升冪或降冪。
- **FR-006**: 排序變更時，列表 MUST 回到第一頁並以新排序重新呈現。
- **FR-007**: 使用者 MUST 能以「單一操作」清除某列表的全部排序，使其回到預設順序。
- **FR-008**: 某列表的目前排序選擇 MUST 在使用者離開該頁後再返回時被保留（依「列表頁」為範圍區分）。
- **FR-009**: 排序的保留 MUST 為使用者瀏覽器本機層級、MUST NOT 影響其他使用者、MUST NOT 需要伺服器端儲存使用者偏好。
- **FR-010**: 當無任何排序作用時，列表 MUST 以其「既有預設順序」呈現（與本功能導入前一致、零回歸）。
- **FR-011**: 系統 MUST 僅接受每個列表「預先定義之允許欄位」上的排序；引用未允許欄位或非法方向的排序請求 MUST 被以業務驗證錯誤拒絕（不得導致伺服器錯誤、不得回傳錯排資料）。
- **FR-012**: 可排序欄位 MUST 限於「對應單一底層資料欄」的欄位；組合／衍生／操作類欄位（如角色徽章、操作按鈕、列序號）不可排序。
- **FR-013**: 本功能 MUST 套用於下列列表頁：使用者、角色、操作日誌、存取日誌、登入嘗試、政策封存、IP 規則。選單管理（樹狀檢視）明確排除。
- **FR-014**: 目前有排序的欄位 MUST 顯示排序方向指示；多欄排序時 MUST NOT 顯示優先序號碼。
- **FR-015**: 還原已保留的排序時，系統 MUST 防禦性忽略「已不存在或已不可排序」的欄位。
- **FR-016**: 對於具備 CSV 匯出的列表頁（如審計／日誌類），匯出的資料 MUST 反映使用者當前的排序（與畫面顯示一致）。

### Key Entities

- **排序規格（Sort specification）**：使用者對某列表的當前排序意圖，為一個「有序的（欄位, 方向）清單」。方向 ∈ {升冪, 降冪}；清單順序即優先序（首位為主排序）。
- **可排序欄位（Sortable column）**：某列表中被允許排序的欄位，對應單一底層資料欄；不含組合／衍生／操作類欄位。
- **已保留排序狀態（Persisted sort state）**：依「列表頁身分」保存於使用者本機的排序規格；用於返回頁面時還原。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在任一範圍內、資料超過一頁的列表，依某欄排序後顯示的第一列為整個資料集在該欄的極值（與完整資料集比對驗證），而非僅重排前一頁可見列。
- **SC-002**: 使用者能建立 2 欄以上的排序，且顯示順序在 100% 案例符合預期的主／次優先序。
- **SC-003**: 單一「清除排序」操作使列表回到預設順序並移除所有排序指示。
- **SC-004**: 排序後離開該頁再返回（同一瀏覽器）時，先前選擇的排序在 100% 案例仍被套用（資料順序＋欄位指示）。
- **SC-005**: 引用未允許欄位或非法方向的排序請求被以明確業務錯誤拒絕，且不回傳錯排資料、不造成伺服器錯誤。
- **SC-006**: 無排序作用的列表，其呈現順序與本功能導入前相同（既有預設排序零回歸）。
- **SC-007**: 對某已排序欄位每點擊一次，介面觀察到的 3-state 循環（降 → 升 → 取消）正確推進。

## Assumptions

- 每欄一次僅作用單一方向（升或降）；3-state 循環包含「無排序」狀態。
- 各列表的「預設（無排序）順序」＝既有順序（如日誌類為新到舊），本功能不變更之。
- 排序保留為 per-瀏覽器（本機）、跨頁面導航與瀏覽器重啟皆保留；不跨裝置／使用者同步；登出時不清除（視為無害 UI 偏好；planning 可重議）。
- 點擊循環以「降冪」起手（沿用平台內建表格行為——使用者拍板採原生、最簡，不自訂循環）。
- 各列表「確切可排序欄位清單」於 `/speckit-plan` 與 spec-review 定案（預設：對應單一資料欄的純量欄位；排除 join／衍生／操作欄）。
- 後端不新增資料表、不新增 workspace crate。**本刀含一支 index-only migration**：補 `sys_login_attempt.created_at` 的缺失索引（高基數、該表預設排序欄；operation/access 已有對應索引、login_attempt 漏補）。其餘排序效能為 **best-effort**：不為一般可排序欄另建索引（高基數欄排序少見、低基數欄加索引對排序無益），大型日誌表對非索引欄排序可能較慢，屬可接受取捨、日後個別欄證實慢再補。
- **治理依賴（待 Constitution Check 裁決）**：本功能須修改既有 base-web 列表檢視（inline）以掛載排序互動與「清除排序」控制項。依專案 constitution §I.1／§III 軌道授權，此屬 base-web inline 變更；現行 MODAL-WIRING ★ 授權用途 (a)~(e) 未涵蓋「列表排序掛載」。需於 `/speckit-plan` 的 Constitution Check 確認軌道授權，**很可能需 MODAL-WIRING ★ 新用途 (f) 之 Amendment（user 親決，§V.2）**。新增之 composable／service wrapper／typings 等新檔則落 ADAPT／WRAPPER 既有軌道。**另**：本刀含一支 index-only migration（補 `login_attempt.created_at`），屬 schema 變更、亦列 `/speckit-plan` Constitution Check —— §I.6 審計欄規則不適用（非新表、非加欄、僅加索引）。

## Dependencies

- 既有 7 個分頁列表頁與其後端列表查詢端點（使用者／角色／操作日誌／存取日誌／登入嘗試／政策封存／IP 規則）。
- 既有分頁機制（每頁 `current`／`size`）與既有空字串篩選守門慣例（未設參數序列化為空 → 視為未設）。
- 既有業務驗證錯誤通道（wire `2222`／i18n key）作為「無效排序」的拒絕載體（細節於 planning 對齊 §I.3 wire 契約）。
- 既有 CSV 匯出路徑（017）：須將當前排序帶入匯出查詢，使匯出順序與畫面一致（FR-016）。
