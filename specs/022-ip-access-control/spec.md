# Feature Specification: IP 存取控制閘（IP 白/黑名單）

**Feature Branch**: `022-ip-access-control`

**Created**: 2026-06-28

**Status**: Draft

**Input**: User description: 見 `docs/superpowers/022-ip-access-control.md`（Phase 0 brainstorm spec-design，已含 P1-P10 拍板 + 收尾獨立 cold-review 校正）。源：021 收刀後 user 提「IP 白名單加進系統管理」→ brainstorm 擴充為**全站每請求的 IP 存取控制閘**（白名單放行 ＞ 黑名單阻擋 ＞ 其餘放行、CIDR、DB 真相→記憶體判定）＋管理者手動解鎖＋通道（tunnel）直連部署的來源 IP 正確識別。承接 019-login-lockout §4.2「per-IP 信任白名單」與 021-login-lockout-redis-cache 預留之信任來源豁免接縫。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 依來源封鎖惡意存取（黑名單） (Priority: P1) 🎯 MVP

身為平台維運者／資安關係人，我要能**依來源網段封鎖已知惡意 IP** 對系統的存取。一旦某來源被列入黑名單，其後續每一次請求都應在進入任何業務處理前就被拒絕；未被列入的正常來源則照常放行（預設放行）。封鎖的「服務成本」必須有上限、與攻擊量無關——被封來源狂打 100 次或 100 萬次，每次評估成本相同，不得反成資源耗竭放大器。

**Why this priority**: 這是本功能的核心存取控制能力，單獨交付即可阻斷已知惡意來源、且因評估成本有界而本身具 DoS 韌性。是最小可交付價值。

**Independent Test**: 對某來源網段建立一條阻擋規則 → 自該網段送請求得到一致的拒絕回應、自其他來源送請求照常成功；對被封來源持續送大量請求，量測每次評估的後端工作量為固定常數、且系統其他功能維持可用。

**Acceptance Scenarios**:

1. **Given** 某來源網段已被列入黑名單，**When** 該來源送出任一請求，**Then** 請求在進入業務處理前即被以一般化拒絕回應擋下。
2. **Given** 某來源未被任何規則命中，**When** 該來源送出請求，**Then** 照常放行（預設放行）。
3. **Given** 黑名單來源持續送出大量請求，**When** 同時有其他正常操作進行，**Then** 其他操作不因此判定的負擔而劣化或失敗（每次評估成本為固定常數）。

---

### User Story 2 - 信任來源放行並免於登入鎖定（白名單） (Priority: P2)

身為維運者，我要能標記**受信任的來源網段**，使其一律放行，**並且免於登入失敗鎖定**。白名單優先於黑名單（同時命中時以放行為準）。此舉解決「分散式失敗聚合誤鎖合法的共用出口 / NAT IP」的問題（021 把鎖做硬後此風險升高）。

**Why this priority**: 兼顧「信任來源永遠可達」與「合法共用 IP 不被帳號-DoS 誤鎖」，是 019/021 既登記但未實作的補強；次於核心封鎖能力。

**Independent Test**: 對某來源建立白名單規則 → 即使該來源同時被某黑名單網段涵蓋仍放行；對該來源以錯誤密碼連續登入超過鎖定門檻 → 仍可繼續嘗試（不被鎖）。

**Acceptance Scenarios**:

1. **Given** 某來源同時落在一條白名單與一條黑名單網段內，**When** 該來源送請求，**Then** 以白名單為準放行（白優先於黑）。
2. **Given** 某來源在白名單內，**When** 該來源的登入失敗數累積超過既有鎖定門檻，**Then** 不觸發登入鎖定、仍可繼續嘗試。

---

### User Story 3 - 經系統管理維護 IP 名單 (Priority: P2)

身為維運者，我要能在**系統管理介面**新增、修改、（軟）刪除、復原 IP 規則；列表須**顯示全部規則（含已刪）並標示刪除狀態**、可搜尋與分頁；已刪規則可一鍵復原。系統須防止我把自己當前的來源 IP 加入黑名單而把自己鎖在門外。

**Why this priority**: 規則須可由維運者 runtime 管理才具實用性；列表含已刪供稽核可見性、復原供誤刪回復；自鎖防護是必要安全護欄。次於判定能力本身。

**Independent Test**: 經介面新增/修改/刪除/復原規則並確認列表正確反映（含已刪標示、搜尋、分頁、復原鈕）；嘗試新增一條會封鎖自己當前來源的阻擋規則 → 被拒絕。

**Acceptance Scenarios**:

1. **Given** 既有若干 active 與 soft-deleted 規則，**When** 維運者開啟 IP 名單頁，**Then** 列表顯示全部（含已刪、標示狀態）、可依條件搜尋與分頁。
2. **Given** 一條已軟刪的規則，**When** 維運者按復原，**Then** 該規則回到 active（若已存在同網段同型的 active 規則則拒絕復原）。
3. **Given** 維運者新增/修改一條會命中其【當前來源 IP】的阻擋規則，**When** 送出，**Then** 被拒絕（防自鎖）、規則不變更。

---

### User Story 4 - 管理者手動解除登入鎖定 (Priority: P3)

身為維運者，當合法使用者（或某共用來源）因失敗次數被登入鎖定時，我要能**立即手動解鎖**該帳號或該來源，無需等待鎖定時窗自然老化。

**Why this priority**: 提升維運可操作性（合法使用者被鎖時的即時救援）；附屬於登入鎖定機制、非核心存取控制，故 P3。

**Independent Test**: 令某帳號因連續失敗被鎖 → 維運者對該帳號執行手動解鎖 → 該帳號下一次以正確密碼登入即成功。

**Acceptance Scenarios**:

1. **Given** 某帳號目前處於登入鎖定中，**When** 維運者對該帳號手動解鎖，**Then** 該帳號可立即（下一次嘗試）正常登入。
2. **Given** 某來源同時於帳號維度與來源維度被鎖（分散式攻擊），**When** 維運者僅解其中一維，**Then** 另一維仍鎖（須兩維皆解才完全放行）。

---

### User Story 5 - 韌性、安全與零回歸 (Priority: P3)

身為平台維運者，此存取控制不得引入新的可用性風險或回歸：(a) 判定機制不可用時須**放行**（fail-OPEN、不得使入口不可用）；(b) 本機/私網位址與健康/監控探針**永遠可達**、不被任何規則阻擋（infra 與管理者恢復途徑）；(c) 系統須**正確識別真實來源 IP**，無論部署於既有反向代理之後或經由**通道（tunnel）直連繞過反向代理**，且不採信未受信來源的偽造來源標頭；(d) 未命中規則的正常請求與既有登入/授權行為與現行**完全一致**。

**Why this priority**: 確保硬化不引入永久封鎖、自我鎖死、來源誤判或回歸——是本功能可被信任部署的前提，且各為獨立可驗的屬性。

**Independent Test**: (a) 令規則無法評估 → 確認全放行；(b) 自本機/私網與探針端點請求 → 永遠可達（即使有涵蓋它們的阻擋規則）；(c) 模擬通道直連部署（繞過反向代理）→ 確認來源 IP 正確識別、且偽造來源標頭自未受信位置不被採信；(d) 跑既有正常登入/授權流程 → 行為與現行一致。

**Acceptance Scenarios**:

1. **Given** 規則暫時無法評估（載入/快取失效），**When** 任一請求進來，**Then** 放行（fail-OPEN）。
2. **Given** 一條涵蓋本機/私網或探針的阻擋規則存在，**When** 自本機/私網/探針請求，**Then** 仍放行（結構性豁免、不可被規則阻擋）。
3. **Given** 系統經通道直連部署（繞過反向代理），**When** 外部使用者請求，**Then** 以該使用者的真實來源 IP 判定；**And** 自內網但非通道入口的位置偽造來源標頭時，該偽造來源**不**被採信。
4. **Given** 一個未被任何規則命中的使用者，**When** 以正確或錯誤密碼登入，**Then** 結果與現行機制完全一致。

---

### Edge Cases

- **被阻擋的洪水**：被黑名單擋下的大量請求不得逐筆寫入持久稽核列（否則攻擊者順手灌爆稽核儲存）；遭阻擋之量級須以**有上限的節流摘要**保留供觀測。
- **白名單 ∩ 黑名單**：同一來源同時被白、黑名單涵蓋 → 以白名單為準放行（白優先）。
- **管理者自鎖**：以阻擋規則命中自己當前來源 → 寫入時即被拒絕；另以白名單優先與本機/私網結構豁免作為恢復途徑。
- **通道 vs 反向代理部署**：兩種入口拓樸的真實來源 IP 來源不同；判定須在兩者下皆正確，且偽造來源標頭不得自未受信位置繞過。
- **規則重複/復原衝突**：同網段同型的 active 規則至多一條；復原一條已刪規則時若已存在同型 active 規則 → 拒絕復原。
- **顯示排序 vs 判定**：規則的顯示排序僅供檢視、不影響放行/阻擋決策（判定為集合比對：白集任一命中即放行、黑集任一命中即阻擋）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 對每個進入的請求，依其**真實來源 IP** 判定放行或阻擋；判定順序＝**白名單命中→放行 ＞ 黑名單命中→阻擋 ＞ 其餘未命中→放行（default-allow）**。
- **FR-002**: 規則 MUST 支援 **CIDR 網段**（IPv4 與 IPv6），單一 IP 為其特例（/32、/128）。
- **FR-003**: 對已被阻擋之來源，系統評估每次請求的成本 MUST 為**有上限的固定量、與已累積的請求量無關**（不得隨請求量放大成資源耗竭）。
- **FR-004**: 白名單命中之來源 MUST 同時**豁免登入失敗鎖定**（承接 019/021），使合法的共用/NAT 出口 IP 不因聚合失敗被誤鎖。
- **FR-005**: 規則判定為**非權威加速**：當系統暫時無法評估（規則無法載入/失效）時 MUST **放行**（fail-OPEN、MUST NOT 使入口不可用）；既有身分驗證與授權仍為主防線。
- **FR-006**: 系統 MUST 提供**結構性豁免**——本機/私網位址與健康/監控探針端點 MUST **永遠可達**、不被任何規則阻擋（infra 與管理者恢復途徑）。此豁免**僅**作用於阻擋判定、不等同於登入鎖定豁免（後者僅由顯式白名單規則授予，FR-004）。
- **FR-007**: 維運者 MUST 能經系統管理介面**新增/修改/軟刪除/復原** IP 規則；規則變更 MUST 於有限時間內**生效於判定而無需重啟**。
- **FR-008**: 規則列表 MUST **顯示全部規則（含已軟刪）並標示刪除狀態**，且提供**搜尋與分頁**；已刪規則 MUST 可**一鍵復原**（復原與既有「同網段同型」active 規則衝突時 MUST 拒絕）。
- **FR-009**: 系統 MUST **防止管理者自鎖**——新增/修改一條會命中【操作者當前來源 IP】的阻擋規則 MUST 被拒絕、規則不變更。
- **FR-010**: 維運者 MUST 能**手動立即解除**某帳號或某來源維度的登入鎖定（無需等待鎖定時窗自然老化）；於帳號與來源兩維度皆被鎖時，MUST 能分別解除、兩維皆解才完全放行。
- **FR-011**: 每筆規則的新增/修改/刪除/復原與手動解鎖 MUST 留下**稽核軌**（操作者、時間、相關前後值）。
- **FR-012**: 被阻擋之請求 MUST 回覆**一般化的拒絕回應、不洩漏規則內容**（與既有授權拒絕無從區分）。
- **FR-013**: 系統 MUST NOT 為每一次**未認證**的被阻擋請求寫入持久稽核列（防阻擋洪水灌爆稽核儲存）；遭阻擋之量級 MUST 以**有上限的節流摘要**保留供觀測與告警。〔註：對【已認證但被阻擋】之請求，既有每請求存取稽核仍留一列〔含拒絕狀態〕＝刻意保留之鑑識痕跡、非每請求成正比放大。〕
- **FR-014**: 系統 MUST 正確識別請求的**真實來源 IP**，**不論部署於既有反向代理之後或經由通道（tunnel）直連（繞過反向代理）**；且 MUST NOT 採信來自**未受信來源**的偽造來源標頭（採信通道提供之來源標頭須限於**明確配置的窄通道入口**並具驗證、非泛指整個內網）。
- **FR-015**: 未被任何規則命中的正常請求，以及既有登入/授權行為 MUST 與現行**完全一致**（零回歸）。
- **FR-016**: 規則的**判定政策**（白優先於黑、CIDR 集合比對）MUST 與規則的**顯示排序**分離——顯示排序欄僅供管理檢視、MUST NOT 影響放行/阻擋決策。

### Key Entities *(include if feature involves data)*

- **IP 規則（IP Rule）**：一條依來源網段（CIDR）放行或阻擋的規則。屬性：型別（放行 allow／阻擋 deny）、網段（CIDR、v4/v6）、顯示排序（僅供檢視）、說明、稽核欄與軟刪標記。為存取判定之**真相來源**（持久）。同網段同型的 active 規則至多一條。
- **存取判定（Access Decision）**：對一次請求依其真實來源 IP 與當前 active 規則集得出的放行/阻擋結果。**非持久**（除遭阻擋之有上限節流摘要訊號）。
- **登入鎖定重置（Lockout Reset）**：管理者對某維度（帳號／來源）手動解鎖的標記，使既有失敗計數於該維度**自重置時點起重新計算**（不竄改既有失敗紀錄）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 對某已阻擋來源的**持續請求洪水**下，系統所有功能維持可用、無因此判定導致的劣化或失敗（單次評估的後端工作量為固定常數、與洪水量無關）。
- **SC-002**: 規則生效後，黑名單網段的請求 **100%** 被阻擋、白名單網段的請求 **100%** 放行且免登入鎖定、未列來源 **100%** 放行（default-allow）。
- **SC-003**: 維運者變更規則後，**5 秒內**生效於每請求判定，無需重啟服務。
- **SC-004**: 判定機制不可用時 **100%** 放行（fail-OPEN）；本機/私網位址與健康/監控探針 **100%** 永遠可達——任何規則錯誤皆不會使系統或管理者自我鎖死。
- **SC-005**: 管理者把自己當前來源加入阻擋規則的嘗試 **100%** 被攔下（自鎖防護）。
- **SC-006**: 管理者手動解鎖後，被鎖帳號/來源於**下一次嘗試**即可正常登入（兩維皆鎖時需兩維皆解）。
- **SC-007**: 真實來源 IP 在「反向代理之後」與「通道直連（繞過反向代理）」兩種部署下皆 **100%** 正確識別；自未受信位置偽造的來源標頭 **100%** 不被採信。
- **SC-008**: 未命中規則的正常請求與既有登入/授權行為 **0** 行為回歸。
- **SC-009**: 遭阻擋期間，持久稽核儲存的成長有**固定上限**（未認證阻擋 0 持久列；每來源每時間單位至多一筆節流摘要）、非與阻擋量成正比。

## Assumptions

- **承接 019/021**：登入失敗鎖定的**政策值**（門檻、時窗）沿用既定值、不在本功能調整；白名單豁免鎖定與手動解鎖為其補強。
- **既有基礎設施可重用**：系統已具備可重用的快速鍵值快取（與既有 session/鎖定加速同源）作為**非權威加速層與節流摘要落點**；本功能不引入新的外部相依。
- **既有真實來源 IP 解析為基礎**：系統已具備自轉發鏈解析真實 client IP 並只信任受配置代理的能力；本功能**補強「通道直連繞過反向代理」之來源識別**，並收窄通道來源標頭的採信邊界。
- **應用層存取控制**：本功能保護後端 API 入口；**網路/邊緣層（反向代理/CDN）封鎖、以及前端靜態資源存取，不在本功能範圍**（敏感操作皆經 API）。
- **部署前提**：後端服務埠不對外公開（僅經反向代理或通道達），為來源標頭可信之前提。
- **判定政策**：default-allow（未列來源放行）；白名單優先於黑名單；判定為集合比對（非 first-match 規則鏈、無優先級欄）。
- **v1 不做**：runtime 可調鎖定門檻、IPv6 前綴群組計數、CAPTCHA 軟挑戰、精確不同來源計數、具體告警規則配置（接地與遞延理由見 brainstorm §5）。
